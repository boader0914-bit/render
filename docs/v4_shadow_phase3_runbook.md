# Datalab V4 Shadow Worker Phase 3 Runbook

## Safety Boundary

- Baseline commit: `4e4e1906e2967fe58df66f8ad67f832043d2763b`
- Frozen collector: `scripts/gyeongnam_glamping_crawl.cjs`
- Required collector Git blob: `bcbe229998da3afa6f31ee04375fb0766019e56f`
- Shadow mode: fixture only
- External network: blocked by a required Node preload
- Operational publish and Web import: disabled by required zero-valued gates
- Services 1, 2, and 3: no changes

The supervisor refuses to start unless `V4_SHADOW_MODE=fixture`, all three
operational gates are exactly `0`, and the network blocker is active. It only
launches `v4_worker_once.cjs` with an approved offline fixture scenario. There is
no code path from the Phase 3 supervisor to the frozen live collector.

- Build: `npm ci --omit=dev --ignore-scripts --audit=false --fund=false`
- Start: `npm run start:v4-shadow`
- Local fixture enqueue: `npm run enqueue:v4-shadow-fixture`
- Full recovery checks: `npm run test:v4-recovery`
- Node: `26.5.0`

The lockfile is generated by npm `11.17.0` bundled with Node `26.5.0`.

## Shadow Flow

```text
built-in bootstrap or local fixture enqueue
  -> shadow-transport/inbox
  -> atomic claim + exclusive lease
  -> one-shot adapter
  -> network-blocked fixture collector
  -> atomic artifact promotion
  -> completed or failed terminal transport record
```

Concurrency is fixed at one. A second supervisor is rejected by the supervisor
lock. A claimed job receives a renewable lease. If a prior process disappears,
the next supervisor marks that claim `LEASE_RECOVERY_NO_RETRY`; it never requeues
the job automatically. Idempotency remains enforced by the one-shot adapter.

## Disk Layout

Only `/var/data/v4-worker` is mounted and supplied as `V4_WORKER_DATA_DIR`.

```text
/var/data/v4-worker/
  .v4-worker-root.json
  work/
  artifacts/
  idempotency/
  locks/
  shadow-transport/
    inbox/
    claimed/
    leases/
    completed/
    failed/
    locks/
    runtime/
      supervisor.lock
      supervisor-heartbeat.json
```

The proposal starts with 1 GB because Phase 3 writes only small fixtures. Do not
enable a live canary until actual artifact size and free-space limits are reviewed.
Render disks can be increased later but not reduced.

## Readiness

Render background workers do not have an HTTP health-check path. Treat the worker
as ready only when all of these are true:

1. The process is running and emitted `supervisor_ready`.
2. `supervisor-heartbeat.json` is valid and newer than its `expiresAt` window.
3. Its state is `idle` or `running`, concurrency is `1`, and all safety flags are false/blocked.
4. `completed/bootstrap-phase3-shadow-001.json` reports `completed`.
5. The fixture artifact contains `manifest.json` and `worker-envelope.json` with the approved collector blob.
6. Logs and files do not contain any test secret or provider credential value.

## Proposed Render Service

Use `render.v4-shadow.proposal.yaml` only after explicit approval to push and
deploy. It defines a new worker named `datalab-v4-shadow-worker`, auto-deploy off,
one instance, a 1 GB disk mounted at `/var/data/v4-worker`, and no provider API
credentials. The proposal deliberately is not named `render.yaml`.

## Stop Conditions

Stop Phase 3 and do not proceed to a live API canary if any of these occur:

- collector blob mismatch
- network blocker or any zero-valued safety gate rejected
- more than one artifact for the same idempotency key
- stale heartbeat or lease renewal failure
- write outside `/var/data/v4-worker`
- secret value in stdout, stderr, heartbeat, terminal records, or artifacts
- any reference to a production DB, service 2 import endpoint, or provider key
- unclean shutdown leaving an active claim that is automatically retried

## Still Out Of Scope

- Git push, pull request, Blueprint sync, deployment, restart, or service creation
- Naver, OTA, Tourism API, or any other live provider call
- production DB or service 2 result import
- signed Web-to-Worker transport
- automatic retry or fallback
- functional parity claims for live collection

The next approved phase must separate shadow deployment approval from live API
canary approval. A live canary also requires a new idempotency key, a provider
allowlist, zero production publishing, a strict request budget, and manual review
of the resulting local artifact before any integration work.
