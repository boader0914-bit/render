# 업체 상세 조회의 메모리 제어와 회차별 재사용

## 장애 근거와 진단 범위

2026-10-19 운영 `8156903` 검수에서 Render는 21:41, 21:44 KST에
서비스의 2GiB 메모리 초과를 기록했다. 당시 앱과 별도 감사 프로세스의
동시 최대 RSS/heap/external 기록은 없으므로, 특정 프로세스나 색인 누수를
단일 원인으로 확정할 수 없다. 장애 시간대 앱 로그에는 자동 재시작이
있으며 재시작 후 상세 색인은 같은 세대를 71ms/79ms에 재사용했다.
반복 전체 색인 생성이 원인이라는 근거는 확인되지 않았다.

복원한 `1f22801`의 별도 시점 관측은 앱 RSS 약 278MiB,
cgroup anon 약 247MiB, file 약 1,420MiB였다. 파일 캐시를 앱 heap으로
합산하거나, 이 복원 후 관측으로 장애 전 최대 메모리를 설명하지 않는다.

개선 전에는 상세/색인 준비, 기존 수집 결과의 전체 master·history 읽기,
월·업종 배경 준비가 각각 다른 대기열에서 실행될 수 있었다. 상세 복구는
최대 4회차 × 5개 CSV를 겹쳐 읽었다. 별도 감사도 메모리를 공유하며,
기존 감사의 revision-index checksum은 전체 파싱 객체를 복제·직렬화했다.
이 경로들의 중첩 가능성과 사고 당시의 확정 원인은 구분한다.

## 실행 제어

`heavy_work_scheduler.cjs`의 앱 공통 슬롯을 원본 기반 상세 생성, 상세 색인
생성/검증 정리, 기본자료 재생성, 전체 수집 결과 읽기, 월·업종 bootstrap,
기존 분석 source reader에 연결한다. 계산된 상세/기본자료 적중은 슬롯을
기다리지 않는다. 분석 source reader는 공통 슬롯을 받은 다음 자체 큐에
들어가며, 회차 투영도 같은 순서를 지켜 잠금 역전을 막는다.
외부 공통 큐에 실제 조회가 대기하면 배경 source의 협조 대기도 풀어,
화면의 interactive lease 만료를 불필요하게 기다리지 않는다.

호출자의 요청 문맥을 보존하고, 같은 작업의 재귀 호출은 재진입한다.
동일 작업에서 시작한 독립 형제/하위 큰 작업도 겹치지 않게 처리한다.
실패·대기 초과는 명시적 오류로 반환하고 정상 자료로 치환하지 않는다.

기본 정책은 동시 슬롯 1개, 메모리 예산 2GiB, 앱 RSS 사전 허용 범위 1GiB,
여유 256MiB이다. 이 수치는 사전 추정에 의한 실행 허용 정책이며 OS의 강제
메모리 상한 또는 2GiB 초과의 완전 방지를 보장하지 않는다. 100ms 표본은
짧은 순간의 최대값을 놓칠 수 있으므로 before/after와 함께 판단한다.

계측은 앱 RSS/heap/external/arrayBuffers와 cgroup anon/file/shmem을 구분한다.
운영자가 인증 후 `GET /api/analysis-work-status`로 현재 작업, 대기 사유,
제한값과 최근 작업의 표본 최대값을 읽을 수 있다. 원본 값·계정·쿠키·오류
stack을 계측에 담지 않는다. Linux cgroup이 없는 환경은 해당 값이 null이다.

선택적 협조형 프로세스 lease가 있으나 앱 기본 정책은 앱 내부 공통 슬롯이다.
기존 임의 Shell 감사나 독립 프로세스가 자동으로 통제되는 것은 아니다.
운영 감사는 API 상태 검사, 파일 전용 스트리밍 해시, 실제 화면 검수를
분리하고 무거운 하위 프로세스를 동시에 실행하지 않는다.

## 회차별 중간결과

`company_master/detail_run_projections/`는 업체 × 수집 회차의 읽기 전용
정규화 결과를 저장한다. 원본 수집 파일과 월별 통합 집계는 수정하지 않는다.
재시작하거나 최종 상세 캐시를 다시 만들 때, 검증된 회차 투영이 있으면
CSV/상품 원문을 다시 파싱하지 않고 최종 상세를 조립한다.

매번 업체 보정값·계산 버전과 회차 파일의 크기/수정시각/파일 정체성을
검사하며, 반환 직전과 게시 전후에도 다시 확인한다. TTL만으로 최신이라고
간주하지 않는다. 원본 또는 보정값이 바뀐 회차는 재생성한다. 생성·저장 실패,
원본 변경, 잘못된 캐시에서는 이전 정상 저장본을 보존하고 명시적으로 실패한다.

회차 생성은 직렬 처리하고, 저장 적중은 생성 대기열을 우회한다. 투영 한 건의
저장 크기 검사는 객실·상품 수량 제한과 별개이며, 수량이나 원문 행을 잘라
계산하지 않는다. 기존 20회차 대상 순서, 공통 최대 객실 수, 수동 보정,
예약·매출 계산과 월 통합 계산 callback은 유지한다.

## 검수와 성능 판정

`npm run test:company-detail-memory`와 `npm run test:company-detail-lightweight`로
동시 실행·재진입·실패 후 해제·원본 경쟁 상태·저장본 보존·실제 앱 재시작
재사용·선택 월과 통합 DOM/수치 유지 회귀를 확인한다.

`node scripts/benchmark_company_detail_reuse.cjs`는 외부 통신 없는 로컬 모의
20회차 × 31일 × 16객실 시험이다. 운영 월명 자료나 운영 2초 달성의 증거로
사용하지 않는다. 최종 캐시가 없는 최초 생성과 회차 투영이 준비된 재조립,
최종 캐시 적중, 재시작 적중을 구분한다.

운영은 아직 `1f22801`이다. 후속 배포 검수에서 실제 월명 자료로 서버 처리,
브라우저 수신, 상세 실제 표시 시간을 각각 측정해야 한다. 의도적으로 응답을
보류한 월·수치 유지 시험은 속도 시험과 분리하고, 대기 표시를 상세 완료로
세어 2초 목표를 달성했다고 하지 않는다.

2026-10-19 최종 개발 검증은 회귀 170개와 별도 앱 API 재시작 검사를 통과했다.
20회차 모의 시험의 마지막 측정은 최초 GET 599.485ms, 반복 22.120ms,
최종 캐시 삭제 후 회차 투영으로 재조립 417.426ms였다. 첫 프로세스의
전체 수명 maxRSS는 208,828KiB였고, 원본 62개·응답 의미·8개 주요 지표가
유지됐다. 이는 약 2.22MB 입력에 대한 로컬 시험이며 운영의 약 94MB 업체
원본과 약 165MB 이력을 재현하지 않는다. 월 통합 계산 callback 45개의
내용 지문은 기준 `1f22801`과 동일하다.
