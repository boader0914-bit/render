# 반복 재검증의 업종 집계 재시도 대기 개선

## 문제와 원인

2026-10-25 운영에서 업체 최신 원본 재확인 작업이 업종 집계 뒤에서
118,312ms 기다렸다. 최초 foreground 양보는 빨랐지만, 다음 업종 시도가
phase 10부터 다시 읽는 동안 기존 phase 70의 진행 기준을 넘을 때까지
양보가 금지되었다. HTTP 제한이나 새 수집의 지연과는 별개다.

## 보완 구조

- 업종 원본 계산을 마치고 카탈로그의 실제 최종 변경 검사를 통과한
  계산 후보를 상품별 객실 근거 게시 전에 압축 저장한다. 계산 후보는
  완료된 업종 집계가 아니며 고객에게 최신 결과로 공개하지 않는다.
  큰 계산값은 작은 압축 단위로 나누고, 전체 저장을 마친 경우에만
  검증용 목록을 원자적으로 교체한다. 원본 본문 전체를 JSON 문자열로
  복제하거나 여러 시도의 큰 객체를 메모리에 유지하지 않는다.
- 재시도는 새 카탈로그·원본 변경 경계와 상품별 객실 근거의 시간별
  증가 이력을 확인한 뒤 후보를 사용한다. 부분 게시된 업체별 근거는
  계산 당시 값 또는 그 계산이 게시할 값과 같아야 한다. 월말 최대값만
  같다는 이유로 과거 날짜가 바뀐 후보를 재사용하지 않는다.
- 과거 상품 복구는 영수증별 객실 근거와 계산 결과만 별도 gzip 단위로
  보관한다. 원본·검수값·계산 버전·해당 관측시점의 객실 근거가 바뀌면
  다시 검증한다. 상품 응답 본문을 장기 메모리 캐시에 넣지 않는다.
- 같은 활성 원본 검증 경계 안에서만 확인한 수집 폴더의 파일 목록
  해시를 재사용한다. 업체별 근거 파일의 체크섬·검수값 확인은 유지하며
  경계 종료 또는 양보 시 내부 증명은 모두 해제한다.
- 실제 원본 revision이 바뀌면 이전 원본의 재시도 진행 기준도 초기화한다.
  원본이 같으면 진행 기준은 유지해 업종 계산의 지속적인 밀림을 막는다.

파생 캐시의 손상·크기 초과·쓰기 실패는 기존 원본 검증 경로로 복귀한다.
일부 계산이나 양보된 시도는 정상 완료로 게시하지 않는다. 원본 수집,
이미 발행한 리포트, 수집 일정과 보호 설정은 변경하지 않는다.

## 검증 기준

첫 양보 후 재시도 앞부분에 다시 업체 조회를 넣는 경우를 반드시 시험한다.
계산 후보/복구 캐시 재사용 횟수와 실제 foreground의 queueWaitMs를 함께
기록한다. 저장 화면 표시 시간과 최신 자료 계산 시간은 구분한다.
원본·검수값·이전 날짜의 객실 근거 변경, 손상, 재시작과 부분 게시 후
재시도를 시험하고, 고객 화면에서 저장 자료가 유지되며 최신 확인 시각이
추가 클릭 없이 갱신되는지 확인한다. 기존 집계는 최종 성공 전까지 유지한다.

## 업체 월 계산과 첫 표시 보완

남은 운영 조회 대기 3,811ms는 업체 월 계산의 현재월·전월 연속 실행 뒤에서
발생했다. background company-month도 현재월, 비교월, 집계, 게시의 네 단계에서
안전하게 양보한다. 각 재시도는 업체 검수값과 원본 revision을 다시 읽으며, 완성한
업체별 계산 후보는 별도 최대 64개·64MiB 파생 저장소에서 검증 후 재사용한다.
실제 index·증명·월 결과 게시 묶음 중에는 양보하지 않는다.

객실 근거의 최종 revision 계산은 업체별 근거를 한 번 분류하고 해당 업체의 값만
변환한다. 기존 전체 재변환과 결과·동률 순서·경고·해시가 같음을 검증한다.
합성 400개 업체·8,000개 근거에서 동기 작업은 2,267ms에서 12ms로 감소했다.
이는 운영에서 관측한 일시 502의 직접 원인을 증명하는 수치가 아니다.

관리자 GET /api/analytical-work의 responsiveness에 이벤트 루프 지연을 30초별
최대 8구간 기록한다. 측정 전 값은 null이며 사용자·요청·업체 정보를 저장하지 않는다.
502가 재발하면 같은 시각의 process uptime, 지연, 메모리와 Render 로그를 대조한다.

운영 재검수에서 관리자 통합월 첫 표시는 3,108.5ms였으며 그중 원본 확인 증명
조회가 2,240ms였다. 관리자에게 인증된 `view=saved` 첫 GET은 기존 정상 저장본을
먼저 반환하고 최신 검증 완료로 표시하지 않는다. 화면에 표시한 뒤 일반 GET으로
기존 증명을 확인하며 갱신한다. 실패하면 이전 수치와 미확인 표시를 유지한다.
임의 관측 마감일을 새로 계산하는 요청에는 저장 미리보기 옵션을 적용하지 않는다.

상세 조회 완료 후 JSON 변환을 별도로 승인받는 과정에서도 업종 재시도가 사이에
진입해 4,117ms를 기다렸다. 상세 조회와 크기 제한 JSON 변환은 같은 작업권에서
완료하고, 제한된 Buffer만 반환한다. 네트워크 전송과 느린 소켓의 대기는 작업권을
해제한 뒤 처리하며 기존 16MiB 응답·32MiB 전체 응답 예약 한도를 유지한다.

전체 새로고침에서 남은 5,563ms는 저장 미리보기의 업체 메타자료 조회가 파생
객실 기준 파일 변경 뒤의 재구성을 기다린 경우다. 정상 검증을 통과한 기존 8MiB
이내 업체 메타자료는 원본 업체 파일의 현재 지문을 두 번 확인한 미리보기에만
사용한다. 원본 삭제·병합·수정, 검증 실패, 캐시 미준비, 무효화 세대 변경 시에는
기존 전체 검사로 돌아간다. 이 경로는 최신 검증 완료를 의미하지 않으며 일반
GET·객실 검수·계산·수집 경로의 검증은 생략하지 않는다.
