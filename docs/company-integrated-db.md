# 업체 통합 DB

작성 기준: 2026-10-10 개발 작업본. 이 문서는 구현·사용·운영 기준이며, 운영 배포 완료를 의미하지 않는다. 실제 배포 커밋, 최초 가공 결과 및 인증된 운영 화면은 배포 단계에서 별도로 확인한다.

## 목적과 자료 구조

키워드별 수집 원본을 보존하고, 여러 키워드에서 관측된 같은 업체를 업체 고유번호로 통합한다. 데이터랩 업체 DB, 월간 리포트, 인사이트는 같은 계산 결과와 객실 기준을 사용한다.

| 자료 | 기준 | 보관·사용 방식 |
| --- | --- | --- |
| 키워드별 수집 원본 | 키워드·수집 회차·업체·상품·숙박일 | 당시 수집값과 검색 순위를 보존한다. 통합 가공이 원본을 수정하지 않는다. |
| 전체 관측 이력 | 업체 고유번호·관측 시각·숙박일·상품 유형 | 같은 숙박일을 여러 번 관측한 기록을 보존해 예약 변화를 분석한다. |
| 업체 통합 DB | 업체 고유번호·숙박월 | 날짜별 채택값, 월별 합계, 분석 지표, 제외 사유와 출처를 재계산 가능한 형태로 저장한다. |
| 발행 리포트 | 리포트 ID·발행 버전 | 발행 당시의 숫자·메모·근거를 고정한다. 이후 통합 DB 갱신으로 덮어쓰지 않는다. |

예를 들어 경남글램핑과 산청글램핑에서 수집한 월명이 같은 `companyId`이면 하나의 업체에 연결한다. 같은 이름이라는 이유만으로 다른 업체를 합치지 않는다. 키워드별 순위·수집 회차는 업체 통합 이후에도 별도로 조회한다.

## 날짜와 합산 규칙

1. 월별 집계의 기준은 **숙박일**이다. 수집한 달과 숙박하는 달을 구분한다.
2. 같은 업체 고유번호·숙박일·상품 유형에서 **최신 유효 관측 한 건**을 채택한다. 반복 수집값을 합산하지 않는다.
3. 관측 시각은 한국시간으로 판정하며, 관측 마감일 이후의 관측과 숙박일 이후의 관측은 제외한다.
4. 기본 관측 마감일은 오늘과 해당 월 말일 중 이른 날짜다. 미래 숙박월도 현재까지 확보한 선행 관측을 보여줄 수 있다.
5. 원본 이력에 실제로 보존된 가장 이른 관측부터 처리한다. 과거에 수집하지 않았거나 보존하지 않은 값을 만들어 넣지 않는다.
6. 일부 상품만 새로 관측됐을 때 과거의 나머지 상품과 조합해 새 정상 관측처럼 취급하지 않는다. 사용 가능한 부분 금액은 정상 합계와 분리한다.

오늘부터 12일 범위를 수집하고 내일 다시 12일 범위를 수집하는 경우, 겹치는 숙박일의 대표값은 내일의 유효 관측으로 갱신한다. 오늘의 관측은 예약 증감 분석용으로 남긴다. 새 숙박일은 추가하고, 내일 실패한 날짜에는 이전 정상값과 그 관측일을 유지한다.

### 정상 0과 미확인

- 정상 관측의 예약 0실·매출 0원은 그대로 표시한다.
- 응답 오류, 접근 제한, 상품 누락, 재고 불일치, 수집 품질 미확인은 0으로 대체하지 않는다.
- 최신 시도가 실패해도 이전 유효 관측이 있으면 보존한다. `latestAttempts`와 `failedAttempts`에 최신 시도와 마지막 정상 관측을 따로 제공한다.
- 과거 자료의 정상 응답 상태 또는 재고 근거 버전이 확인되지 않으면 월간 정상 합계에서 제외한다. 자료 검토 화면에 사유를 남긴다.
- 사전 관측만 있는 숙박일은 “○일 전 관측”으로 표시한다. 모든 날짜에 관측이 있어도 실제 최종 예약·결제 매출을 확인했다는 의미는 아니다.

## 객실 기준

관리자 DB 검수값을 최우선으로 적용한다. 검수값이 없다면 사용 가능한 기존 관측 최대값을 최초 기준으로 고정하고, 이후 수집만으로 기준을 계속 높이거나 낮추지 않는다.

별도 기준 기록에는 객실 수, 출처, 수정 버전, 갱신 시각과 이전 기준 이력이 저장된다. 관측 최대값을 이력에서 추가로 찾을 때는 정상으로 사용할 수 있는 숙박 관측의 `rawTotal`을 사용한다. 이미 추정이 포함될 수 있는 `supply`·`total`을 그대로 새 기준으로 확장하지 않는다. 상품별 서로 다른 날짜의 최대값을 더해 총 객실을 만들지 않는다.

미검수 최대 관측값으로 고정된 기준보다 큰 수량이 새로 발견되면 기존 기준을 유지하고 관리자 검토 경고를 표시한다. 수량·재고 모순은 월간 계산의 품질 검증에서도 제외 또는 경고 대상으로 처리한다. 객실 수의 일괄 상한을 두어 원본 수량을 잘라내지 않는다.

월명처럼 16실이 검수된 업체는 해당 검수값을 공통 계산에 적용한다. 검수값 변경은 저장된 과거 자료의 보정으로 취급해 관련 월을 다시 계산한다. **실제 증설·감실의 시행일을 따로 지정하는 기간별 객실 기준은 현재 구현에 포함하지 않는다.** 이 구분이 필요한 경우 시행일 모델을 추가하기 전까지 과거 전체에 자동 적용하지 않도록 검토해야 한다.

인사이트 고객이 입력하는 실제 매출·수정 요청은 기존의 별도 저장을 유지한다. 이번 통합 기능이 고객 입력값을 수집 원본에 덮어쓰거나 자동으로 합산 우선순위를 바꾸지는 않는다.

## 자동 가공 시점

| 시점 | 동작 |
| --- | --- |
| 웹 서버 시작 | 업체별 대상 월과 저장 결과의 원본 버전을 비교한다. 동일한 결과는 재사용하고 변경·누락·구버전인 월만 작업을 등록한다. |
| 새 관측 이력 저장 완료 | 영속 이력 저장 뒤 영향을 받는 업체의 월별 가공을 등록한다. |
| 업체 DB 저장·검수 보정 | 변경된 업체를 찾아 해당 업체의 관련 월을 갱신한다. |
| 월별 캐시가 없는 최초 조회 | 저장 자료에서 만들 가공 작업을 등록하고 `refreshing` 상태를 반환한다. |
| 계산 버전·관측 마감일·월 종료 상태 변경 | 해당 월의 저장된 집계가 오래됐으면 갱신한다. |
| 이전 월 자료 변경 | 그 달을 비교 기준으로 사용하는 다음 달의 기존 캐시도 갱신한다. |

가공은 웹 서버의 별도 직렬 작업 큐에서 실행한다. 외부 수집 워커에 새 네이버 요청을 보내는 작업이 아니다. 자동 수집 일정을 만들거나 기존 일정의 활성 상태를 바꾸지 않는다.

원본·조건·객실 보정·계산 버전의 해시가 동일하면 이미 저장된 월별 결과를 다시 쓰지 않는다. 가공 도중 새 변경이 들어오면 작업 세대 번호로 과거 작업의 결과가 최신값을 덮어쓰지 않게 한다. 결과는 임시 파일에 쓴 뒤 교체한다.

### 재시작 시 저장 집계 재사용

재사용 여부는 무거운 예약 원본을 읽기 **전에** 판정한다. 원본 변경 색인은 파일의 변경 정보를 먼저 확인하고, 실제 내용이 변경된 업체 기본자료와 관측 이력만 다시 해석하여 업체·숙박월별 지문을 만든다. 같은 원본으로 재시작한 경우 마감월의 예약 자료를 다시 조회하거나 월별 파일·계산 시각을 다시 쓰지 않는다. 저장 결과를 검증하기 위한 가벼운 파일 검사까지 없애는 방식은 아니다.

변경 색인 v2는 파일의 크기·수정시각·파일번호·장치번호와 **내용 SHA256**을 별도로 저장한다. 배포·디스크 연결·동일 내용 파일 교체로 파일 정보만 바뀌면 64KiB 단위로 실제 내용을 확인하고 색인만 갱신한다. 내용이 같으면 업체 자료와 이력을 다시 해석하거나 월별 계산을 등록하지 않는다. 파일 정보까지 그대로인 다음 재시작은 저장된 내용 지문을 재사용하므로 원본 내용도 다시 읽지 않는다. 관광·검색·KOSIS·특일정보·수집 결과의 영속 변경 기준에 파일번호나 장치번호를 직접 섞지 않는다.

파일을 읽는 도중 내용이 바뀌거나 읽기에 실패하면 새 지문으로 승인하지 않고 마지막 검증 색인과 정상 집계를 보존한다. 삭제된 파일과 빈 파일도 구분한다. 디렉터리의 나열 순서가 바뀌어도 동일한 내용의 지문은 유지된다. 실제 공통 연휴 자료·계산 산식·공통 품질 진단이 바뀌면 이에 연결된 여러 업체의 월을 갱신하는 것이 정상이다.

- 같은 업체·숙박월의 당월 및 전월 관측, 객실 검수값·고정 총량, 계산 버전, 관측 마감일과 월 종료 상태가 일치해야 재사용한다.
- 관광·검색·KOSIS는 해당 업체 소재지의 저장 자료, 특일정보는 관련 연도의 저장 자료를 검사한다. 정확한 지역·기간을 알 수 없는 자료나 공통 품질 진단은 보수적으로 공통 변경 대상으로 취급한다.
- 새 관측은 관련 업체·월을, 객실 검수 보정은 해당 업체의 관련 월을 갱신한다. 전월 비교를 포함하는 다음 저장월도 검사한다. 현재·미래월은 한국시간 기준일이 바뀌면 갱신하며 마감월은 그대로 재사용한다.
- 마지막 원본 관측이 사라진 업체도 기존 가공 월을 검사한다. 업체가 삭제·병합되었으면 예전 파일이 남아 있더라도 활성 업체 자료로 제공하지 않는다.
- 신규 지문이 있는 월별 파일은 내부 업체·월 조건과 결과 무결성 지문을 함께 확인한다. 손상된 결과나 다른 업체의 결과를 재사용하지 않는다. 이 지문은 파생 파일의 손상 검사이며 공식 원본 인증을 대신하지 않는다.
- 계산 전후 원본 버전이 달라지거나 변경 검사가 실패하면 해당 계산을 최신 결과로 게시하지 않는다. 마지막 정상 집계와 안전한 오류 코드를 유지하며 무한 재시도하지 않는다.
- 원본 검사 실패 후 특정 업체·월의 명시적 갱신이 정상 검증되면 그 범위는 복구한다. 아직 검증하지 않은 다른 업체·월까지 정상으로 바꾸지는 않는다.

재사용 지문이 없는 월별 파일이나 내용 지문이 없는 **v1 색인은 첫 적용 때 한 번 검증·전환**한다. v1의 무결성 검사를 먼저 통과해야 하며, 예전 파일 정보만으로 내용이 같았다고 인증하지 않는다. 새 변경 색인과 계산 버전의 지문을 붙이는 동안 마지막 정상 집계는 표시하고, 이후 같은 자료의 재시작부터 무거운 재조회가 생략된다. 진행·대기·실패 작업의 재시작 복구는 유지한다. 작업 상태의 `bootstrap`에는 검사 시각과 재사용 월·새 작업·복구 작업 수를 남기며, `checked`는 변경 검사를 마쳤다는 뜻이다. 모든 가공 작업 완료나 모든 날짜의 정상 관측을 뜻하지 않는다.

업체 DB 저장 시에는 프로세스 메모리의 빈 목록 대신 **저장 전후 업체 자료**를 비교한다. 서버 재시작 후 첫 저장이라는 이유만으로 전체 업체를 다시 등록하지 않는다. 원본 변경 색인·월별 집계·발행 리포트는 각각 별도의 저장 자료이며, 재사용은 외부 API나 네이버 수집을 실행하지 않는다.

계산에 쓰는 모듈과 앱 내부의 명시된 보정·자료 투영 함수도 변경 검사에 포함한다. 무관한 화면 문구를 바꾼 배포까지 전체 업체 재계산으로 이어지지 않도록 서버 파일 전체를 계산 지문으로 사용하지 않는다. 목록 밖의 계산 상수나 새로운 하위 계산 함수를 추가할 때는 `companyIntegratedCalculationFingerprint()`의 목록을 확장하거나 그 선언의 계산 버전을 갱신해야 한다. 계산 산식 버전 변경도 기존과 같이 관리한다.

서버 재시작 시 저장된 대기·처리 중·실패 작업은 재가공 대기로 복구된다. 한 프로세스에서 가공에 실패한 작업을 화면 조회마다 무한 재실행하지 않는다. 실패 시 마지막 정상 가공본과 안전한 오류 코드를 제공한다.

### 최초 계산 시간

첫 적용 시 업체 수·보존 월 수·상품별 원본 크기에 따라 시간이 늘어날 수 있다. 이전 월 비교 자료도 읽으므로 업체 수만으로 처리 시간을 단정하지 않는다. 현재 운영 실측 시간이 없어 고정 완료 시간을 표시하지 않는다.

처음에는 “통합 중”, 기존 가공본이 있으면 마지막 정상 가공 자료를 함께 표시한다. 화면은 실제 가공 중인 `refreshing`/`updating` 상태에 한해 3초 간격으로 상태를 조회한다. `ready`, `failed`, `pending` 상태에서는 반복 조회하지 않는다. 업체·월을 바꾸거나 화면을 나가면 이전 요청과 폴링을 정리한다.

`ready`는 가공 결과를 조회할 수 있다는 뜻이다. 모든 날짜가 정상 수집됐다는 뜻은 아니므로, 월별 자료 충족률·미관측 일수·제외 사유를 함께 확인한다.

## 데이터랩 사용 화면

관리자 **DB → 업체 DB → 업체 선택**에서 기존 업체 기본자료·예약채널 아래의 **월별 통합 분석**을 사용한다. 기존 최근 관측·수정·검수 도구는 유지한다.

| 메뉴 | 내용 |
| --- | --- |
| 월별 결산 | 객실 기준, 예약 실·박, 추정 매출, 관측 예약률, 날짜별 예약 그래프, 매출 캘린더·표 |
| 예약 흐름 분석 | 예약 증가 관측 구간, 증가·감소 수량, D-14·D-7·D-3·D-1 진행률, 요일별 지표, 연속 관측 변화 |
| 관측 이력 | 키워드별 수집 회차·순위·상태·원본 바로가기, 숙박일별 채택값 |
| 자료 검토 | 객실 기준과 갱신 상태, 최근 실패·제한, 제외 사유, 부분 관측 자료, 계산 기준 |

숙박월 선택은 네 메뉴에 공통으로 적용된다. 날짜를 누르면 채택 관측 시각·수집 원본·제외된 관측 표본을 확인할 수 있다. 제외 사유 표본은 전체 원본 이력 그 자체가 아니며, 월간 집계가 제공하는 표본 범위다.

공개 네이버 예약은 녹색, 타채널 예약 추정은 보라색이다. 타채널 수량이 1실 이상인 날짜에만 보라색 캘린더 표시·막대를 사용한다. 정상 0은 작은 점 또는 0으로, 미확인은 별도 공백 표식으로 구분한다. 다크·라이트 모드와 모바일을 함께 지원한다.

“이 월로 리포트 열기”는 업체 고유번호와 선택한 월을 월간 리포트 작성 화면에 전달한다. 리포트를 자동 저장·발행하지 않는다.

## 분석 지표의 해석

- 월 예약량은 날짜별 예약 수량의 합인 `실·박`이다. 실제 객실 규모인 `실`과 다르다.
- 관측 예약률은 유효 관측에서 계산한 예약 합계 / 같은 관측의 공급 합계다. 미확인 날짜를 미판매 0으로 채운 월 전체 점유율이 아니다.
- 매출은 상품별 관측 가격과 예약 추정 수량을 사용한다. 결제 매출이 아니며 가격 보완·누락은 따로 표시한다.
- 타채널 예약 추정에는 재고로 추정한 전화·다른 채널 예약이 포함될 수 있다. 실제 타채널 판매를 확인한 값으로 표현하지 않는다.
- 공유 객실인 데이유즈는 숙박 객실과 중복 합산하지 않는다. 숙박은 실·박, 데이유즈는 별도 이용 수량으로 취급한다.
- 리드타임은 예약 증가를 확인한 두 관측 사이의 숙박일 전 구간이다. 최초 관측 전에 이미 예약된 수량의 예약 접수일은 알 수 없다.
- 증가·감소는 관측 수량의 변화다. 감소를 취소 거래 건수로, 가격 보정을 신규 예약 매출로 간주하지 않는다.
- D별 진행률은 해당 선행일의 관측이 있는 표본만 사용한다. 서로 다른 표본의 D별 차이를 그대로 신규 예약량으로 빼지 않는다.

세부 월간 계산·발행 기준은 [월간 리포트](monthly-reports.md)를 함께 참고한다.

## 인사이트 연결과 권한

인사이트는 데이터랩의 통합 DB를 인증된 서버 API로 조회한다. 브라우저가 데이터랩 저장 파일이나 내부 DB에 직접 접근하지 않는다. 인사이트에 별도의 예약·매출 합산 엔진을 만들지 않는다.

기존 인사이트 업체 자료 API에 `month=YYYY-MM` 조회를 연결한다. 서버 간 서비스 인증과 고객 세션 검사를 거치고, 고객에게 등록된 내 업체·경쟁업체만 허용한다. 고객용 월 선택은 확인된 수집 이력의 숙박월 또는 현재 월에 한한다.

고객 응답은 필요한 객실 기준·월별 숫자·날짜별 관측·분석 지표만 허용 목록으로 전달한다. 원본 경로·전체 수집 응답·관리자 메모 등 내부 정보는 전달하지 않는다. 업체 고유번호·대상 월을 고객 경계에서 다시 확인한다.

같은 업체·월·관측 마감일·계산 버전이면 데이터랩과 인사이트의 수치는 같은 공통 계산을 사용한다. 통합 자료가 준비되지 않았거나 실패하면 그 상태를 전달한다. 이전의 개별 회차·별도 합산값을 정상 통합값으로 조용히 바꿔 보여주지 않는다.

인사이트 표시는 공통 `refreshing` 상태를 `updating`으로 전달할 수 있다. 두 상태 모두 “통합 중”을 뜻한다.

## 저장 위치와 API

`DATA_DIR/company_integrated/`는 영속 데이터 경로에 둔다.

| 경로 | 내용 |
| --- | --- |
| `queue.json` | 업체별 가공 작업 상태·세대 번호·안전한 오류 코드 |
| `capacity-bases.json` | 고정 객실 기준과 수정 이력 |
| `revision-index.json` | 재사용 판정용 원본 변경 색인·업체 및 월별 지문. 수집 원본이 아닌 재구축 가능한 파생 자료 |
| `catalog.json` | 업체 월 조회용 경량 메타데이터. 정규화된 객실 기준·검수 보정·키워드 순위 이력·회차 품질만 보관하는 재구축 가능한 캐시 |
| `<companyId 해시>/index.json` | 업체별 가공된 숙박월 목록 |
| `<companyId 해시>/YYYY-MM.json` | 날짜별 채택값·월간 스냅샷·출처·실패 시도·계산 버전 |

재계산으로 만드는 월별 결과와 객실 기준 기록은 성격이 다르다. **재구축을 이유로 `capacity-bases.json`을 임의 삭제하면 고정 기준 이력이 사라질 수 있으므로 삭제하지 않는다.** 운영 원본이나 통합 폴더를 수작업으로 지우는 절차는 제공하지 않는다.

관리자 조회:

```http
GET /api/company-master/integrated?companyId=cmp_place_35644668&month=2026-09
```

관리자 인증이 필요하다. 선택적 `cutoffDate=YYYY-MM-DD`는 미래가 아닌 유효 날짜만 허용한다. 기본 월 캐시와 다른 마감일의 조회는 해당 조건으로 계산하며 기본 월별 캐시를 덮어쓰지 않는다.

조회 메서드는 GET이지만 **캐시가 없거나 오래됐으면 가공 큐와 파생 캐시를 기록할 수 있다.** 외부 수집은 실행하지 않지만, 파일 변경까지 금지한 엄격한 읽기 전용 운영 점검에서는 이 점을 고려해야 한다.

### 최초 업체 조회의 불필요한 전체 자료 읽기 방지

업체 월 조회는 `catalog.json`의 검증된 경량 정보를 사용한다. 정상 캐시 조회는 전체 업체 원본의 파싱·복제, 객실 기준 준비, 관측 이력 읽기를 다시 수행하거나 배경 원본 읽기 대기열에 합류하지 않는다. 응답의 예약·매출·자료 품질은 기존 월 파일과 공통 계산 엔진을 그대로 사용한다.

서버는 요청을 받기 전에 경량 정보의 저장본을 확인하거나 최초 생성한다. 이 최초 준비 시간과 준비 후 첫 업체 조회 시간을 분리해 기록한다. 준비 실패는 `company_integrated_catalog_prepare_failed`에 안전한 오류 코드로 남으며, 기존 정상값을 최신으로 인증하거나 자료 없음·0으로 바꾸지 않는다.

매 조회마다 업체 원본·관측 이력·객실 기준 파일의 변경 정보, 저장 회차 목록·manifest, 지역 기준을 확인한다. 검수 수정·새 수집·회차 품질 변경·삭제·병합 등이 있으면 원래의 정규화 과정을 거쳐 경량 저장본만 갱신한다. 오류나 연속 변경 중에는 마지막 저장본을 보존하고 조회 실패를 명시한다. 전체 업체 재구성 결과는 메모리에 보관하지 않으며 캐시 크기는 8MiB로 제한한다.

진행 중인 전체 업체 조회를 공유할 때도 그 조회가 시작되기 전부터 원본 변경을 확인한다. 수정 전 시작된 느린 조회가 수정 후 완료되면 재검증·재시도하며, 수정 전 정보를 새 변경 지문으로 저장하지 않는다. 반복해서 원본이 바뀌면 재시도를 끝내고 실패를 표시한다.

이 조회 최적화만으로 월별 계산 지문을 바꾸지 않는다. `company_integrated_db.cjs`와 계산 의존 파일은 그대로 두고, 경량 캐시는 별도 투영 버전으로 관리한다. 운영 검수에서는 최초 GET·재조회 시간과 전체 업체/객실 준비/이력 추가 읽기 횟수, 마감월 값·계산시각·파일 수정시각 보존을 함께 확인한다. 로컬 모의자료의 2초 통과를 운영 자료나 브라우저 표시 2초 통과로 표현하지 않는다.

주요 응답 필드:

```text
schemaVersion, companyId, calculationVersion, calculatedAt
status: ready | refreshing | failed | pending
selectedMonth, months, roomBasis, snapshot
keywords, latestAttempts, failedAttempts, freshness, errorCode
```

고객 서버 API:

```http
GET /api/insight/v1/companies/{companyId}/collection?month=YYYY-MM
```

기존 서버 간 인증과 고객 인증을 그대로 사용한다. 운영 키·세션 값은 문서·로그·브라우저 코드에 넣지 않는다.

## 재계산과 발행본

업체 통합 DB는 원본과 검수 기준으로 재계산할 수 있는 현재 조회용 자료다. 검수 보정이나 계산 변경이 있으면 관련 월을 갱신할 수 있다.

발행된 월간 리포트는 별도 저장소의 고정 스냅샷이다. 통합 DB의 값이 바뀌었다고 기존 발행본을 자동 변경하지 않는다. 수정이 필요하면 기존 리포트에서 수정본 생성·재집계·검토·발행 절차를 수행한다. 발행 전 미리보기와 현재 업체 DB를 비교할 때는 업체·숙박월·마감일·객실 기준·계산 버전을 함께 맞춘다.

## 검증과 운영 적용 구분

개발 검증은 보존 자료를 읽거나 외부 통신 없는 모의 자료를 사용한다. 주요 회귀 항목은 다음과 같다.

- 두 키워드의 동일 업체·숙박일 중복 제외와 원본 보존
- 고정 객실 기준, 검수 보정 우선, 새 초과 관측 경고
- 정상 0 / 실패 / 미관측 구분과 이전 정상 관측 유지
- 여러 월 최초 가공·새 이력 갱신·재시작 복구·계산 버전 변경
- 느린 이전 조회가 선택한 새 업체·월을 덮어쓰지 않는지 확인
- 데이터랩과 인사이트의 공통 수치 및 등록 업체 접근 권한
- 과거 근거 미확인 자료의 제외 사유, 발행본 불변

관련 검증 파일:

```text
scripts/test_company_integrated_db.cjs
scripts/test_company_integrated_sources.cjs
scripts/test_company_integrated_source_revision.cjs
scripts/test_company_integrated_restart.cjs
scripts/test_company_integrated_restart_api.cjs
scripts/test_company_integrated_catalog.cjs
scripts/test_company_integrated_catalog_api.cjs
scripts/test_company_integrated_api.cjs
scripts/test_company_integrated_ui.cjs
scripts/test_monthly_reports_ui.cjs
```

개발 테스트 통과, 로컬 화면 검수, 운영 배포, 운영 최초 가공 완료는 각각 다른 상태다. 현재 문서 작성 시점에는 운영 배포를 수행하지 않았다. 실제 운영 적용 시 배포 커밋·서비스 정상 응답·인증된 업체 화면·첫 가공 상태·인사이트 동일 월 수치까지 확인한 후 완료로 기록한다.
