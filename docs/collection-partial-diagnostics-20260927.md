## 원인 표시와 기록 원칙

- 수집 기록과 결과 보관함에서 원인 확인을 펼쳐 저장된 근거를 조회한다. 진단 조회는 수집·재수집·외부 API 요청·업체 DB 갱신을 하지 않는다.
- 상품 수 제한, 조회 누락, 요청 실패, 접근 제한, 보관 자료 부족을 구분한다. 정상 응답의 예약 0은 실패로 세지 않는다.
- 업체, 상품, 날짜, 건수와 안전한 오류코드만 표시한다. 상품 수와 상품·날짜 건수를 섞어 합산하지 않는다.
- 과거 자료에 상세 오류가 없으면 세부 원인 기록 없음으로 표시한다. 시간 초과나 접근 제한으로 추정하지 않는다.
- 신규 예약 일정 상세에는 `collectionErrorCode`, `responseStatus`, `collectionPhase`를 보존한다. 원문 응답·오류 메시지·쿠키·토큰·요청 URL은 추가 저장하지 않는다.
- 객실 수 보정과 매출 추정의 불확실성은 수집 실행의 일부 완료 원인과 구분한다.

이번 개선은 원인 기록·조회 기능이다. 기존 40/20 상품 상한, 요청 속도, 차단 시 중단, 재시도, 예약 일정은 변경하지 않는다. 과거 결과를 완료로 바꾸거나 재수집하지 않는다.

## 구현 및 검증

관리자 `GET /api/runs/{runId}/diagnostics`는 저장된 manifest, 전체 순위 CSV와 상세 JSON을 읽어 `collectionDiagnostics`를 반환한다. 경로·파일 크기·표시 필드를 제한하며 관리자 이외의 접근은 거절한다. 원인 카드는 펼칠 때 조회하고 같은 결과는 재사용한다. 요청 실패 시 카드의 다시 확인 버튼으로 읽기 요청만 재시도한다.

검증 명령: `npm run test:collection-diagnostics`. 인증, 경로 이탈, 상품 제한과 날짜 단위 구분, 과거 기록 호환, 정상 0과 실패 0, 안전한 오류코드, 조회 전후 원본·DB·이력 불변을 포함한다. 별도로 `node scripts/test_worker_cards_integration.cjs`로 세 수집기의 중앙 저장 계약을 외부 수집 없이 검증한다.
