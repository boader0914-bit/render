# 수집 전용 워커 전환

> 2026-09-23 역할 분리 개발의 최신 설정은 [수동워커·예약워커 개발 결과](collector-roles-development.md)를 참고한다. 아래는 최초 단일 워커 전환 기록이며, 새 구성에서는 워커별 대기열·인증을 분리하고 예약워커도 즉시수집을 지원한다.

2026-09-22 개발. 기본 실행 방식은 기존 `local`이며, 이 문서나 코드 추가만으로 Render 서비스가 재개되거나 수집 위치가 변경되지 않는다.

## 역할

| 운영 웹 서버 | 수집 워커 |
| --- | --- |
| 로그인·화면·분석·업체 수정·기존 API 지표 | 네이버/OTA 수집 프로그램 실행 |
| 오후 2시 일정과 수동 수집 대기열을 한 곳에서 관리 | 서버가 배정한 작업 한 건씩 처리 |
| 작업 상태·결과 파일·이력·기준 DB 보관 | 결과를 해시와 함께 전송하고 서버 저장 확인 후 임시 복사본 제거 |

자동·관리자 수동·B2B 수집은 모두 기존 대기열을 거쳐 같은 워커에 전달된다. 워커는 별도의 일정을 만들지 않는다. 지역 관광 API 갱신 등 기존 웹 서버의 업무는 유지한다. 기존 13개 키워드·순서·14시·precision/revenue_detail·1~20위·31일 정책은 별도 일정 설정이다. 2026-09-23의 워커 기본 속도 복원은 비활성 상태인 기존 일일 일정이나 그 일정에 저장된 명시적 요청량 제한 설정을 변경하거나 재활성화하지 않는다.

수집 전용 서버는 접근 제한 해제 수단이 아니다. Render는 같은 지역 서비스에 공통 출발 IP 범위를 사용한다([공식 문서](https://render.com/docs/outbound-ip-addresses)). 두 서비스가 분리되어도 네이버가 서로 독립된 이용자로 취급한다고 보장할 수 없다.

## 대상 서비스와 설정

기존 서비스를 재사용한다. `render.yaml`을 적용해 새 서비스를 만들지 않는다.

- 운영 웹: `glamping-datalab-v2`, `srv-da9q6don74is738t7id0`, `https://staydatalab.kr`, 기존 `/var/data` 디스크.
- 수집 워커: `lodging-datalab-collector-preview`, `srv-d9q6mrfavr4c73atllf0`, Background Worker. 구형 배포를 그대로 재개하지 않고 검증한 동일 커밋으로 교체한다.
- 워커 시작 명령: `npm run start:collector-worker`. 빌드: `npm install`.

| 변수 | 웹 서버 | 워커 |
| --- | --- | --- |
| `COLLECTOR_EXECUTION_MODE` | 전환 때 `worker`, 기본 `local` | 사용 안 함 |
| `COLLECTOR_WORKER_ENABLED` | 사용 안 함 | 승인 후 `1`, 기본 비활성 |
| `COLLECTOR_SERVER_URL` | 사용 안 함 | `https://staydatalab.kr` |
| `COLLECTOR_WORKER_ID` | `staydatalab-collector` | 같은 값 |
| `COLLECTOR_WORKER_TOKEN` | 새 무작위 비밀값 | 웹 서버와 같은 비밀값 |
| `COLLECTOR_WORK_DIR` | 사용 안 함 | 생략 시 OS 임시 폴더 |

토큰은 32자 이상의 충분한 무작위값을 Render 비밀 환경변수로 저장하고 코드·문서·로그에 기록하지 않는다. 기존 관리자 계정, 쿠키, 회원 정보, 관광·검색광고 API 키를 워커에 복사하지 않는다. 워커 인증은 수집 작업 수령·진행 보고·해당 작업 파일 전송만 허용하며 관리자 로그인 권한을 주지 않는다. `COLLECTOR_ALLOW_LOCAL_HTTP`는 로컬 테스트용이며 운영에는 설정하지 않는다.

## 보호와 결과 판정

- 작업은 웹 서버가 영속 저장한 뒤 한 워커에 60초 사용권으로 배정한다. 워커는 10초마다 연결을 확인한다. 연결 확인 실패·인증 실패·중지 요청 시 실행 중인 수집을 종료한다.
- 웹 서버 재시작·작업 사용권 만료는 중단 상태로 기록하고 전체 워커 배정을 보류한다. 같은 작업을 자동 재수집하지 않으며 워커 장애 때 웹 서버 수집으로 자동 전환하지 않는다.
- 파일 전송과 완료 확인만 제한적으로 재시도한다. 완료 확인 응답이 유실되어도 같은 수집을 다시 시작하지 않는다.
- 서버는 파일별 SHA-256·크기·경로·manifest 참조를 검증한다. 한 파일 64MiB, 한 결과 256MiB 한도. 검증 중 파일은 공개 결과 폴더 밖에 놓고 완료 시 한 번에 이동한다. 같은 runId의 기존 결과를 덮어쓰지 않는다.
- 수집 수치가 부족하거나 접근 제한된 결과도 증거로 보관하지만, 정상 완료 자료로 표시하거나 업체 기준값·매출 이력·기준 DB에 자동 반영하지 않는다.
- 2026-09-23 워커 기본 속도는 전역 요청 간격·동시 요청 수 제한을 적용하지 않는 기존 방식으로 복원한다. 상세 업체는 2곳, 업체별 상품 일정은 4개, 외부 예약채널 관측은 2곳까지 동시 처리하며 상품별 기존 0·35·70·105ms 분산 대기는 유지한다. 이 수치는 개별 처리 단계의 상한이며 전체 네이버 HTTP 동시 요청 수를 뜻하지 않는다.
- 요청 속도 제한과 접근 제한 감지는 분리한다. 기본 속도에서도 HTTP 403·429 및 HTTP 200 응답의 `BookingAPITooManyRequests`를 감지하면 새 네이버 요청을 중단하고 보호 상태를 유지한다. 이미 전송된 요청은 회수할 수 없다. 파일·조건·결과 수치 검증과 불완전한 자료의 파생 데이터 반영 금지도 그대로 유지한다.
- 명시적으로 `NAVER_REQUEST_PACING_ENABLED=1`을 전달하면 전역 요청 간격·동시 요청 제한을 적용할 수 있다. `NAVER_REQUEST_MIN_INTERVAL_MS`와 `NAVER_REQUEST_MAX_CONCURRENCY`의 명시 값 및 일정이 전달한 설정을 보존한다. 비활성인 기존 일일 일정의 최소 200ms·동시 최대 2개 설정은 이번 기본값 변경으로 덮어쓰지 않는다.
- 기본 속도의 manifest `requestPacing`은 `enabled:false`, `guardEnabled:true`, `pacingEnabled:false`, `minIntervalMs:0`, `maxConcurrentRequests:null`을 기록한다. HTTP 요청 수·실제 최소 시작 간격·최대 동시 요청 수와 차단 상태는 계속 계측한다. `enabled:false`는 속도 제한 해제를 뜻하며 차단 보호가 꺼졌다는 의미가 아니다. 과거 `enabled:true` 형식도 결과 검증에서 계속 인정한다.
- 예전 수집에서 확보한 예약 사업자 ID 보완은 숫자 형태의 업체 ID/예약 사업자 ID 쌍만 전달한다. 기존 결과 전체나 로그인 관련 정보는 전달하지 않는다.
- 워커 임시 저장공간은 영구 보관소가 아니다. 전송 실패한 임시 자료는 자동 삭제하지 않지만 재배포·호스트 교체 때 사라질 수 있다. 서버에 저장 확인된 결과만 영속 보관이 확인된 것으로 판단한다.

## 검증 및 전환 순서

1. `npm run test:collector-worker`, `npm run test:daily-collection`, 관련 회귀 검사를 실행한다. 모의 수집기만 사용하며 네이버 요청을 보내지 않는다.
2. 승인된 동일 커밋을 별도 검증 환경에서 모의 자료로 확인한다. 이 저장소는 운영 전환과 독립적인 개발 브랜치다.
3. 진행·대기 중 수집이 없는 시간을 택한다. 당일 일정 상태를 보존한다. 워커 코드와 설정을 준비하고 웹 서버에 같은 코드 및 새 인증값을 배포한다. 운영 전환에서는 기존 자동 수집 일정 파일을 다시 등록하지 않는다.
4. 웹 서버를 `worker` 모드로 전환한 뒤 올바른 코드의 워커를 활성화한다. 다음 수집 시간 전에 관리자 상태에서 `configured`, `workerLastSeenAt`, `halted`를 확인한다. 인증/상태 확인만으로 네이버 접근 제한 해제를 선언하지 않는다.
5. 다음 승인된 수집에서 동일 jobId/runId·웹 서버 결과 저장·완료 품질·실제 시간·메모리·디스크 여유를 확인한다. 저사양 워커에서 실제 수집 메모리 여유와 시간은 아직 측정되지 않았다.

현재 개발 완료와 Render 전환 완료를 구분한다. 모의 검증은 실제 네이버 수집 성공, 네이버 제한 해제, 워커 512MB 메모리 적합성을 증명하지 않는다.

2026-09-22 로컬 검증: 워커 관련 단위/계약 검사 45개(배정 5, broker 19, worker 14, crawler 7)와 실제 앱 서버를 사용하는 모의 워커 통합 검사를 통과했다. 기존 일정·품질·요청 간격·시간 비교·객실 계산 관련 검사도 통과했다. 전체 package 검사에서는 기존 `test_master_db.cjs`가 필요로 하는 회사 샘플 22건/과거 관측 105건이 새 작업 폴더에 없어 회사 건수 0에서 중단됐다. 해당 샘플을 운영 데이터로 대신 채우거나 전체 검사가 통과했다고 처리하지 않았다.

## 조회와 장애 대응

### 보존 결과의 등록 복구 (2026-09-24)

같은 업체가 전체·광고·지역 목록에 반복 등장해도 상세 JSON은 경로별로 한 번만 쓰고 manifest에 한 번만 등록한다. 파일 내용이나 업체 식별자가 충돌하면 합치지 않고 오류로 처리한다. 전송 실패 기록은 `failurePhase`와 허용된 `brokerErrorCode`를 보존하여 네이버 차단과 내부 저장 검증 실패를 구분한다.

관리자 `POST /api/collector-recover`는 실패한 외부 워커 작업의 영속 staging 자료만 대상으로 한다. JSON에 `confirm: "recover-retained-result"`, `workerKey`, `jobId`, `requestId`, 원본 `manifestSha256`, 원 수집 조건 `expected`를 지정한다. 원 요청·중복 확인 장부의 수집 조건·작업 식별자와 모든 파일 해시를 확인하고, 상세 JSON의 완전히 일치하는 중복 참조만 제거한다. 접근 제한 또는 불완전한 수집은 복구하지 않는다.

검증을 통과하면 결과 폴더를 새로 게시하고 외부 API 호출 없이 업체 DB·누적 이력을 반영한다. 원본 staging, 실패한 broker 기록과 종료 시각은 보존하며 별도 복구 영수증을 남긴다. 요청 카드는 결과 링크가 있는 `복구 완료`로 표시한다. 같은 복구를 반복해도 결과를 덮어쓰거나 이력을 중복 추가하지 않는다. SQLite shadow 모드에서는 별도 동기화 완료도 확인한다. 복구 API는 수집을 재실행하거나 워커 보호를 해제하지 않는다. 자료와 DB 반영을 확인한 후 기존 관리자 보호 해제 API를 사용한다.

- 관리자 `GET /api/collector-status`: 실행 위치, 설정 여부, 보호 상태, 실행 중 작업, 워커 마지막 연결 시각. 비밀값 제외.
- 관리자 `GET /api/crawl-status`: 기존 수집 진행 상태와 `executionMode`.
- 관리자 `GET /api/collection-schedule`: 기존 날짜별 일정/품질 상태. API 지표의 활성 상태와 워커의 실제 수집 상태는 구분한다.
- 작업 장부는 웹 서버의 `DATA_DIR/collector` 아래에 저장한다. 실행 중 상태 파일을 직접 수정하거나 다른 broker 프로세스로 열어 복구하지 않는다.
- 보호 해제는 원인·기존 워커 종료·미완료 자료를 확인한 후 로그인한 관리자만 `POST /api/collector-reset-halt`에 JSON `{"confirm":"resume-after-review"}`로 요청한다. 진행/대기 작업이 있으면 거절한다. 이 API는 과거 작업을 다시 등록하지 않지만 보호가 풀리면 기존 일정의 향후 작업을 받을 수 있다. 네이버 제한이 유지되면 해제하지 않는다.
- 롤백은 먼저 워커 수집 종료와 배정 중단을 확인하고 웹 서버 실행 모드를 `local`로 변경한다. 진행 중 자동 전환하지 않는다. 결과·장부·일정 파일을 삭제하지 않는다.

공통 인증값 발급/적용, 유료 워커 재개 및 운영 배포는 별도의 실제 운영 변경이다. 이 문서에 적힌 절차는 해당 변경을 이미 수행했다는 뜻이 아니다.
