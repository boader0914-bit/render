# 업체 이력 처리·보관함 조회 최적화 · 2026-10-21

## 범위와 실제 기준

운영의 10/21 정상 예약 검수에서 웹 서울근교글램핑과 BG 경주글램핑은 각각
20업체·420관측이었다. 수집 종료에서 예약 완료 기록까지 약25ms/284ms,
업체 DB 반영 완료까지195,607ms/372,724ms였으며, 이 중 history 단계는
193,931ms/372,178ms였다. 웹 종료시각은 정렬 확인한 collector-web 상태에서
추론한 것으로 BG broker 영수증과 동일한 독립 증거는 아니다.
BG 검수 때 보관함 목록 GET은2,843.427ms였다. 감사 수행 시간은 이 시간과 다르다.

위 수치는 개선 전 운영 기준이다. 이번 작업은 로컬 개발·격리 검증이며 운영 배포,
수집·재수집, 예약·보호 설정 변경, 운영 원본·DB 수정은 하지 않았다.

## 변경

- 업체 마스터 저장·이력 추가에서 `queueRun`으로 전체 업체/객실 기준/누적 이력을
  다시 읽던 경로를 제거했다. 실제 마스터에서 확인한 활성 업체 ID만
  `queueCompany`의 allMonths 작업으로 영속 기록한다. 기존 저장 월·새 관측 월과
  비교 의존 월 검색은 배경 worker가 수행한다. 원본 관측과 집계 계산 규칙은 유지한다.
- 배경 작업의 월 검색도 업체마다 전체 원본을 다시 읽지 않는다. 객실 기준을 준비하지 않는
  `targetCatalog`에서 필요한 신원·기간만 읽고, 같은 원본 변경 토큰의 업체별 월 목록을
  공유한다. 업체/이력/회차가 바뀌면 재확인하며 원본 객체는 캐시에 보관하지 않는다.
- 이력 저장 범위에 참조 횟수 방식의 `deferProcessing`을 적용했다. 새 배경 집계의
  시작만 미루며 진행 중 작업의 세대 검사와 마지막 정상 결과 보존은 유지한다.
  중첩 호출·실패는 finally에서 해제한다. hold 내부에서 drain을 기다리지 않는다.
- 같은 쓰기 잠금 안에서 후보 관측 ID만 streaming 검사한다. 전체 이력 객체와 전체
  ID 목록을 메모리에 만들지 않는다. 256행마다 이벤트 처리를 양보한다.
  파일 부재만 빈 결과이고 읽기 실패는 저장 실패로 전파한다. 손상된 기존 마지막 행의
  원문은 보존하고 개행으로 새 관측을 분리한다. 손상 행 자체를 복구했다고 표현하지 않는다.
- 동일 place의 첫 유효 자료를 유지하면서, 이미 채택한 업체의 뒤따르는 순위/플랫폼 행은
  상품 JSON을 다시 읽기 전에 제외한다. 먼저 나온 무효 행은 다음 유효 자료를 막지 않는다.
- 이력 처리에서 이미 쓰기 잠금 안에 읽은 업체 마스터를 upsert에 재사용한다. 일반 조회는
  이 경로를 사용하지 않아 수동 검토값과 오래된 읽기가 충돌하지 않도록 한다.
- 보관함은 최대8개 폴더를 병렬 검사하고 동시 조회를 공유한다. 디렉터리·manifest의
  크기/수정시각/변경시각/파일 식별자가 같으면 목록 투영만 재사용한다. 레거시·미완성
  항목은 파일 목록을 직접 다시 검사한다. 생성·삭제·품질 변경을 다음 조회에 반영한다.
  원본·manifest·상품 응답은 수정하거나 재가공하지 않는다.
- 캐시는 프로세스 내 최대2,048항목/16MiB이며 보관함 전체 결과를 자르지 않는다.
  재시작하면 차가운 병렬 조회를 수행한다. 후처리 상태는 목록 캐시 밖에서 매번 붙인다.
  읽기 실패를 빈 목록·실제0·가짜 완료로 바꾸지 않으며 화면의 기존 결과 보존을 유지한다.
  원본이 조회 도중 바뀌면 한 번 재확인하고 계속 바뀌면503으로 표시한다.

## 계측·주의

`historyWriteWaitMs`는 쓰기 대기, `historyLoadMs`는 결과 해석·업체 저장,
`historyIdScanMs`, `historyAppendMs`, `historyIntegrationQueueMs`는 각 세부 단계다.
전체 `historyMs`에 포함되므로 전체와 세부 시간을 더하지 않는다.
보관함 응답 `Server-Timing`의 `archive-list`와 `archive-state`로 목록 읽기와
후처리 상태 연결을 구분한다. HTTP 왕복·다운로드·브라우저 표시 시간은 별도 측정한다.

16MiB는 캐시 보관량 한도이며 모든 동시 manifest 파싱의 메모리 상한을 뜻하지 않는다.
실제 운영 최초 조회·배경 작업 중 응답과 RSS 검수가 남아 있다. 집계 모듈 파일 변경은
기존 계산 버전 검사에 포함되어 최초 배포에서 저장 결과 확인/갱신이 발생할 수 있다.
그 과정에서도 선택 월과 마지막 정상 집계는 기존 저장·세대 검증 정책을 유지한다.

## 검증

`npm run test:collection-performance`는 파일 변경 감지·동시 조회·원본 보존,
후보 ID streaming·읽기 실패·재시작, 새 배경 작업 보류·세대 교체·월 범위,
중복 추가 방지·부분 저장 후 재시도, 예약 완료/후처리 상태 구분과 실제 HTTP
20업체×21일 경로를 검증한다. 외부 API와 수집 실행은 guard로 차단한다.

`npm run benchmark:collection-performance -- --output <새 JSON 경로>`는
500개 합성 보관 결과·535업체·누적10만 행·신규420행의 로컬 시험이다.
HTTP 목록은 실제 앱 경로이며, 별도 이력 replay의 loadRun/관측 생성은 합성 입력이다.
전체 업체 초기 집계 완료·상품 파싱·운영 속도·브라우저 paint 증거로 확대 해석하지 않는다.
동일 입력의 순차 I/O 대조는 이전 운영 버전의 실측값이 아니다.
