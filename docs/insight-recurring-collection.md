# 인사이트 경쟁업체 정기 수집

이 기능은 고객의 경쟁업체 자료 요청을 관리자 승인 후 데이터랩의 지정 수집기로 처리한다. 고객 요청이나 관리자 승인 시점에 수집을 즉시 실행하지 않는다.

## 기본 정책

- 활성 계정의 승인된 경쟁업체 관계만 신청할 수 있다. 내 매장·확인 대기·해제된 관계는 대상이 아니다. 수집 직전에도 관계와 계정 상태를 다시 확인한다.
- 최초 요청은 승인 대기다. 승인은 한국시간 **다음 날 14:00**부터 적용한다. 관리자는 승인 시각을 바꿀 수 있다. 거절 후 새 요청 번호로 재신청하면 다시 승인 대기가 된다. 일시중지는 고객 신청으로 해제되지 않는다.
- 범위는 관측일 포함 **30개 숙박일**, 성인 2명, `precision/revenue_detail`, 전체 상품, 데이유즈 상세, 상세 1위 한 업체다. `checkOut`은 숙박 시작일의 다음 날이며 조회 기간은 별도의 `bookingRangeDays=30`이다.
- 승인된 단일 `companyId`와 양의 정수 플레이스 번호를 고정한다. 동명 업체를 키워드만으로 같은 업체라고 판단하지 않는다. 승인 이후 플레이스 번호가 바뀌면 검토가 필요하다.
- 지정된 수집기만 사용한다. 현재 운영 연결값은 서버 설정을 따르며 다른 수집기로 자동 전환하지 않는다. 기존 접근 제한·디스크·오프라인 보호와 접수 전 검사를 유지한다.
- 같은 업체를 여러 고객이 신청하면 승인된 정기 주기를 공유한다. 고객별 신청은 따로 남기며 조회만으로 새 신청이 생기지 않는다.
- 놓친 날은 소급 수집하지 않는다. 같은 날 실패·부분 완료·차단·접수 불명인 작업을 자동 재실행하지 않는다.

## 화면과 운영 연결

고객은 경쟁업체 등록 카드 또는 해당 업체 상세 상단의 `정기수집 요청`을 누른다. 업체 등록 자체는 수집 신청이 아니다. 저장된 업체 자료는 신청 여부와 관계없이 기존 권한으로 계속 조회한다. 고객 화면에는 승인 상태, 최근 실행 결과와 사유, 마지막 정상 정기수집일, 다음 실행 시각이 구분되어 표시된다. 열린 경쟁분석·경쟁업체 상세에서는 최대 3곳의 신청 상태만 60초 간격으로 갱신하고, 다른 화면이나 숨긴 탭에서는 불필요한 조회를 멈춘다.

승인은 데이터랩 `인사이트 이용자`의 정기수집 요청 목록과 인사이트 관리자 페이지 양쪽에서 처리할 수 있다. 처리 사유와 요청 번호를 저장하며 승인·반려·일시중지가 가능하다. 일시중지는 이후 신규 실행을 막으며 이미 접수한 작업을 강제로 종료하는 기능이 아니다.

신규 실행은 승인한 플레이스 번호를 `targetPlaceId` / `NAVER_TARGET_PLACE_ID`로 전달한다. 서버 계획·워커 접수·환경값·실제 수집 결과의 번호가 같아야 하며, 검색 결과에서 해당 번호만 남긴 뒤 상세를 조회한다. 이름이 같은 다른 업체가 먼저 검색되거나 승인 업체의 검색 순위가 1위가 아니어도 임의의 다른 업체를 대신 수집하지 않는다. 검색 시 원래 순위는 보존한다. 승인 번호를 찾지 못하면 상세 조회 전에 종료하고 사유를 남긴다.

현재 운영 수집 연결은 서버의 기존 `INSIGHT_COLLECTION_WORKER_KEY=manual`인 BG worker를 사용한다. 결과 보관·업체 DB 반영·인사이트 조회는 기존 경로를 그대로 사용한다. 기존 순환예약, 다른 수집기의 보호 상태와 요청 속도는 이 기능에서 변경하지 않는다.

이 변경은 중앙 데이터랩, BG 수집 실행 서비스, 인사이트 고객 서비스에 배포한다. 새 타깃 환경값을 구형 워커에 보내지 않도록 BG부터 반영하고 중앙·인사이트를 이어서 반영한다. 승인 이력이 없는 기존 등록 업체를 일괄 자동 승인하지 않는다.

## 영속 저장과 중복 방지

기본 저장 위치는 `DATA_DIR/customer_insight/recurring_collections.sqlite`다. 운영에서는 영속 디스크에 연결된 `DATA_DIR`을 사용해야 한다. WAL 모드와 5초 잠금 대기를 적용한다.

저장소에는 업체별 승인 상태, 고객별 요청, 요청 번호별 멱등 명령, 관리자 검토 기록, 업체·한국시간 날짜별 실행 영수증을 따로 저장한다. 실행 영수증의 `(company_id, observation_day)` 기본키를 `BEGIN IMMEDIATE` 트랜잭션에서 먼저 확보한 후 수집 요청을 보낸다. 서로 다른 고객·동시 요청·서버 인스턴스도 같은 업체를 같은 날 다시 실행하지 않는다. 영수증과 검토 이력은 자동 삭제하지 않는다.

매 점검에서 종료된 전체 이력을 읽지 않고 상태 인덱스로 `dispatching`, `queued`, `collecting`, `verifying` 영수증만 조회한다. 서버 재시작 후 이미 있는 영수증을 근거로 새 작업을 재접수하지 않는다. 접수 영수증을 찾을 수 없으면 `needs_review`로 남긴다. 접수 직전 다른 인스턴스가 잠시 기록을 확인하는 경합을 위해 생성 후 60초 동안 상태 조회를 미룰 수 있지만 실행권을 다시 부여하지 않는다.

한국시간 자정을 넘긴 비동기 검사 결과로 전날 신규 작업을 시작하지 않는다. 이미 시작된 작업의 결과 저장 확인은 날짜가 바뀌어도 계속할 수 있다.

인사이트의 기존 즉시 자료 준비도 `claimExternal(job)`으로 같은 업체·날짜 영수증을 공유한다. 일반 데이터랩 키워드 수집은 실행 전에 개별 업체가 확정되지 않을 수 있으므로, 연결부의 `inspectToday(companyId, scope, day)`가 실제 업체 번호로 연결된 당일 이력을 확인한다. 같은 조건의 완전 자료는 재사용하고, 진행 중인 자료는 기다리며, 부분·실패·차단·다른 조건의 자료가 있으면 추가 수집을 보류한다. 키워드 글자만 같은 자료는 재사용 근거가 아니다. 개별 업체 번호를 모르는 일반 키워드 실행의 동시 진입까지 이 저장소의 업체 잠금이 대신하는 것은 아니며 기존 실행 대기열과 수집기 보호를 함께 유지한다.

## 완료 기준

`approved`는 일정 승인 상태이며 실제 수집 성공을 뜻하지 않는다. `lastCollectedAt`과 `lastCollectedDay`는 다음 조건을 모두 만족한 **30일 상세 범위**에 한해 바뀐다.

1. 수집 영수증 또는 재사용 자료가 완전 완료이고 유효한 수집 번호가 있다.
2. 결과 보관과 업체 DB 반영이 `complete`다. 대기·실행 중이면 계속 확인하고, 실패·상태 미확인이면 검토 상태로 남긴다.
3. 주입된 저장 검증기가 업체 번호, 플레이스 번호, 관측일, 정확한 30일 범위, 상품·인원·데이유즈 조건을 확인한다.

HTTP 200, 프로세스 종료, 결과 파일 생성만으로 완료로 표시하지 않는다. 14일 또는 숙박만 수집한 외부 작업은 그 작업의 실행 이력으로 보존하되 30일 상세 정기 수집의 검증일로 승격하지 않는다.

## 연결 계약

`createInsightRecurringCollection`은 `file` 또는 `dataDir`, `store`, `catalog`, `collectorRequests`, `verifyStored`, `readPostprocess`, `findReusable`, `inspectToday`, `isBusy`, `workerKey`, `now`를 받는다. 운영 연결부는 별도 관리자 인증과 고객 인증·CSRF 검사를 수행한다.

- `request(customerId, {companyId, requestKey}, actor)`는 단건 고객 상태를 반환한다.
- `get(customerId, companyId)`, `forCustomer(customerId)`는 동기 조회이며 해당 고객의 신청이 없으면 각각 `null`, 빈 배열이다.
- `review({companyId, decision, reason, time, requestKey}, actor)`는 관리자 상태를 반환한다. `decision`은 `approve/reject/pause`, 사유는 공백을 제외한 1~500자다.
- `adminState()`는 `{requests, defaults}`, `adminList()`는 업체별 관리자 목록을 반환한다.
- `getDayClaim(companyId, day)`는 실행 번호와 범위가 포함된 내부용 영수증 요약이다. 고객 응답으로 그대로 내보내지 않는다.
- `claimExternal(job)`은 `{state:'new'|'reusable'|'busy'|'review', runId?, errorCode?}`다. `new`에서만 새 수집을 접수한다. 접수 후 `refreshClaim(jobId)`로 영수증 상태를 연결한다.
- `tick/start/stop/close`는 수집기 자체가 아닌 이 영속 일정 점검기의 수명 주기를 관리한다. 반복 시작해도 타이머가 중복되지 않는다. 실행 중 작업이 없으면 `close()` 호출 즉시 SQLite 핸들을 닫는다.

고객 상태에는 회사와 자신의 신청 상태, 다음 시각, 마지막 정상 수집일, 안전한 실행 상태만 노출한다. 다른 고객 정보와 내부 수집 요청 번호는 포함하지 않는다. 관리자 목록은 요청자 수와 관리자 검토에 필요한 고객 식별자·사용자명·요청일만 추가한다.
