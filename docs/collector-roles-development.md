# 수동워커·예약워커 개발 결과

2026-09-23. 개발 기준 커밋 `e1cfcfd5075a4f19b777389470b87919b9d8d7d3`. 이 작업에서는 코드와 로컬 모의 검증만 수행했다. Render 배포, 서비스 재개, 실제 수집, 운영 일정 활성화, Codex 자동 점검 재개는 하지 않았다.

## 화면과 처리 방식

- 관리자 **수집 → 검색·시장 수집**의 `실행할 수집기`에서 0922 수동워커 또는 0923 예약워커를 선택한다. 기본값은 0922이며 B2B 경로도 기존 기본값을 유지한다.
- `수집기 상태` 아래 예약워커 설정은 접고 펼칠 수 있다. 키워드, 한국시간 실행일·시각, 매일·평일·한 번, 관측 기간, 순위, 인원, 요청 속도를 저장한다.
- **조건 저장 / 예약 켜기·일시정지 / 저장 조건으로 지금 수집**은 별도 동작이다. 저장은 활성 여부를 바꾸지 않고, 즉시수집은 다음 예약 시각을 바꾸지 않는다. 신규 설정 기본값은 꺼짐이며 키워드는 비어 있다.
- 상단 즉시수집과 저장 조건 즉시수집 모두 실행 영수증 저장 후 접수 응답을 반환한다. 요청을 접수하면 입력 잠금을 풀어 다른 조건을 확인할 수 있다. 상단 즉시수집 요청 번호는 계정별로 브라우저에 보관해 새로고침 뒤에도 상태를 확인한다. 응답 유실이나 결과 조회 실패가 자동 재수집으로 이어지지 않는다.
- `즉시수집 최근 요청`과 `예약 조건 실행 기록`을 나누어 표시하고 `결과 보기`로 저장된 결과를 연다. 부분·실패·차단을 정상 완료로 안내하지 않는다. 페이지를 닫아도 접수된 서버 작업은 별개로 진행한다.
- 워커 카드에 현재 키워드·경과 시간·대기 수를 표시한다. 최근 연결이 90초 넘게 갱신되지 않았거나 보호·미연결 상태이면 시작 버튼에 실행 불가 사유를 표시한다. 조건 저장과 활성 예약 일시정지는 가능하다.
- 일시정지는 아직 시작하지 않은 예약 작업과 후속 키워드를 중단한다. 이미 실행권을 받아 진행 중인 작업과 다른 수동 요청이 함께 기다리는 작업은 유지한다. 예약 작업의 실행권 발급과 일시정지가 겹쳐도 대기 상태인 작업만 철회한다.
- 유효한 다음 예약 시각을 미리 표시한다. 관측 날짜가 지난 설정은 활성화와 즉시수집을 막는다. 한 번 예약의 실행 시각만 지났고 관측 날짜는 유효하면, 예약 재활성화는 막되 저장 조건 즉시수집은 가능하다.
- 각 워커는 한 작업씩 처리하며 서로 다른 키워드는 별도 대기열에서 처리할 수 있다. 실행을 시작하지 않은 대기 작업 중 예약 시각이 도래한 작업을 우선한다. 실행 중인 작업을 예약 작업이 빼앗지 않는다.
- 예약 발생일이 지나도록 시작하지 못한 예약 작업은 실행권 발급 전에도 만료를 확인해 중단한다. 이미 실행 중인 작업을 자정이라는 이유로 중단하지 않는다.
- 기존 오후 2시·13키워드 일정은 별도 파일에 보존한다. 새 예약으로 자동 복사하거나 재활성화하지 않는다. 새 일정을 활성화하기 전 기존 일정이 비활성인지 확인해야 한다.

## 같은 날 중복 방지

두 워커 앞에 공통 KST 날짜별 기록을 둔다. 같은 키워드·충족하는 조건의 진행 중 작업은 함께 기다리고, 검증된 당일 완료 자료와 실제 파일이 있으면 재사용한다. 재사용은 새 관측·새 매출 이력으로 만들지 않는다.

도착·출발일, 인원, 검색 의도와 범위, 수집 목적은 같아야 한다. 기간별 업체 수에 상한이 있는 결과는 순위 범위를 임의로 바꾸어 재사용하지 않는다. 상한이 선택 순위 전체를 포함하면 전체 범위로 취급한다. 실제 상품·날짜 누락이 있는 결과는 정상 재사용 대상에서 제외한다.

같은 날 범위가 달라지거나 실패·부분·중단 기록이 있으면 먼저 검토를 요구한다. 관리자가 `당일 다시 수집해야 하는 경우`를 열어 명시적으로 선택하고 4자 이상의 사유를 적은 경우에만 별도 실행을 허용한다. 이 선택도 접근 제한 보호를 해제하지 않는다. 재시작 시 미확정 작업은 중단 기록으로 남기며 자동 재수집하지 않는다.

## 아카이브 기반 수집기

0923의 진입점은 `scripts/archive_keyword_collector.cjs`이다. 아카이브와 같은 계열의 현재 공통 수집 코어를 호출하며, 구형 아카이브 전체 실행물을 복제하지 않는다. 현재의 최대 관측 객실 기준, 0과 미확인 구분, 데이유즈 공유 객실 처리, 접근 제한 감지, 결과 전송·검증을 유지한다.

결과에는 `schemaVersion=2`, `workerKey`, `trigger`, `jobId`, `collectorEngine`, 실제 시작·관측 시각을 기록한다. 엔진은 `current-manual-v2` 또는 `archive-keyword-adapted-v2`이다. 고유 작업 토큰을 결과 폴더에 포함해 두 워커의 동시 완료도 기존 결과를 덮어쓰지 않는다.

숙박 상품 40개·데이유즈 20개 상한은 상품별·날짜별 수집 범위 기록에 명시한다. 발견·대상·조회·성공·실패·제외·잘린 수를 구분하고, 범위가 불완전하면 부분 결과로 처리한다. HTTP 200의 CAPTCHA 응답도 공통 접근 제한 감지에 포함한다. 차단 표시는 즉시 운영 웹에 전달되어 다른 워커의 새 요청과 진행 작업 중단을 요청한다. 이미 전송된 외부 요청을 회수한다고 보장하지 않는다.

## 운영 연결에 필요한 설정

현재 서비스는 수정하지 않았다. 배포 시 웹·두 워커를 동일 검증 커밋으로 맞춘다. 기존 0922와 다른 인증값으로 0923을 설정한다. 아래는 변수 이름만이며 실제 인증값을 문서·로그에 저장하지 않는다.

| 항목 | 운영 웹 | 0922 | 0923 |
| --- | --- | --- | --- |
| 시작 명령 | `npm start` | `npm run start:collector-worker` | `npm run start:collector-worker-web` |
| 실행 방식 | `COLLECTOR_EXECUTION_MODE=worker` | - | - |
| 역할 | - | `COLLECTOR_WORKER_KEY=manual` | `COLLECTOR_WORKER_KEY=scheduled` |
| 워커 ID | `COLLECTOR_WORKER_ID`, `COLLECTOR_SCHEDULED_WORKER_ID` | 웹의 수동 ID를 `COLLECTOR_WORKER_ID`에 | 웹의 예약 ID를 `COLLECTOR_WORKER_ID`에 |
| 인증 | `COLLECTOR_WORKER_TOKEN`, `COLLECTOR_SCHEDULED_WORKER_TOKEN` | 수동 토큰을 `COLLECTOR_WORKER_TOKEN`에 | 예약 토큰을 `COLLECTOR_WORKER_TOKEN`에 |
| 작업 수령 | - | `COLLECTOR_WORKER_ENABLED` | `COLLECTOR_WORKER_ENABLED` |
| 배정 서버 | - | `COLLECTOR_SERVER_URL=https://staydatalab.kr` | 동일 |

0923은 기존 Web Service 유형을 유지할 수 있도록 `$PORT`에서 `/health`와 `/api/health`만 제공한다. 공개 수집 실행·파일 조회·관리자 API는 제공하지 않는다. 작업 수령 비활성은 정상 대기 상태로 표시한다. 워커 루프가 비정상 종료하면 건강 상태를 실패로 처리한다. Render Health Check Path는 배포 때 `/health`로 확인한다.

웹의 영속 기록: `collector/`, `collector-scheduled/`, `config/keyword-worker-schedule.json`, `history/keyword-worker-schedule/`, `history/collector-requests/`, `history/collection-reuse.json`. 수집 결과는 기존 `outputs/`에 검증 후 공개된다. 웹은 단일 인스턴스/단일 쓰기 프로세스를 전제로 하며 업체 정보·이력·처리 시간·B2B 이력 변경을 공통 잠금으로 직렬화한다. 웹을 여러 인스턴스로 늘리려면 외부 DB 잠금과 공통 작업 저장소 전환이 먼저 필요하다.

## API

| 관리자 API | 용도 |
| --- | --- |
| `GET /api/collector-status` | 두 워커 `workers[]`와 기존 수동 상태 호환 필드 |
| `GET /api/crawl-status?workerKey=manual\|scheduled` | 선택 워커 실제 실행·대기 상태 |
| `POST /api/crawl` | `workerKey`를 선택한 즉시수집. 실행 방식은 서버가 manual로 고정 |
| `POST /api/crawl?async=1` | 상단 수집 화면. `clientRequestId`로 접수 기록을 저장한 뒤 HTTP 202. 같은 ID 재전송은 동일 기록, 다른 조건이면 충돌 거절 |
| `GET /api/crawl-requests` | 관리자 즉시수집 최근 요청 목록 |
| `GET /api/crawl-requests/{requestId}` | 새로고침·응답 유실 후 동일 요청의 처리 상태와 결과 확인 |
| `GET /api/worker-schedule` | 설정·다음 예약·오늘 및 최근 실행 영수증 |
| `PUT /api/worker-schedule` | 조건 저장. enabled 변경은 거절 |
| `POST /api/worker-schedule/enabled` | `{enabled:true\|false}` 명시 전환 |
| `POST /api/worker-schedule/run-now` | `{requestId}` 기준 한 번 접수. 동일 ID 재요청은 같은 영수증 |

워커 API 경로는 `/api/collector-worker/*`, `/api/collector-worker-scheduled/*`로 분리한다. 역할·토큰·작업 ID·엔진·전송 해시·완료 확인을 검증한다. 관리자 수집·예약 변경은 JSON 및 요청 출처를 검사한다. 신규 화면 수집은 연결·보호·디스크 검사를 통과해야 접수 기록을 만든다. 이미 접수한 요청의 동일 ID 재조회는 연결 상태가 바뀌어도 기존 기록을 반환한다.

대기 시간만 길다는 이유로 전체 워커를 멈추지 않는다. 차단으로 취소된 작업은 안전한 차단 오류코드를 유지해 일반 중단과 구분한다. 접근 제한 보호 해제는 기존 관리자 확인 API에서 진행·대기·실행권이 모두 종료됐을 때만 허용하며, 공통 차단이면 두 워커에 함께 적용한다. 자동 해제나 자동 재시도는 없다.

## 검증

`npm run test:collector-worker`, `npm run test:collector-roles`, `npm run test:daily-collection`, `npm run test:shared-inventory`, `node scripts/test_master_db_incremental.cjs` 및 관련 화면/시각 검사로 검증한다.

로컬 HTTP 통합검사에서는 실제 앱 서버와 모의 워커를 연결하고 외부 HTTP와 실제 crawler 프로세스 실행을 차단했다. 서로 다른 키워드의 동시 처리, 동일 키워드 작업 공유, 당일 완료 재사용, 역할별 인증, 예약 저장·활성화 분리, 요청 ID 중복 방지, 다른 워커까지 차단 전달을 검증했다. 로컬 브라우저에서 수집기 선택과 접기·펼치기, 모바일 배치, 조건 저장 후 예약 꺼짐 유지도 확인했다.

후속 수집 화면 검수에서는 비동기 요청 영속성·복원, 사전 연결 확인, 대기 작업만 취소, 예약 만료 안내, 차단 오류 유지, 관리자 전용 조회, 외부 출처·잘못된 형식 거절을 추가 검증했다. 모바일 다크·데스크톱 라이트 화면에서 예약 설정 열기와 워커 선택 연동, 키워드 중복 제거 안내, 저장 후 예약 꺼짐 유지도 확인했다. 로컬 번들에 npm 실행 파일이 없어 package.json에 정의된 Node 명령을 번들 Node로 직접 실행했다.

이 검증은 운영 네이버 접근 성공, 512MB 환경에서 장시간 수집의 메모리 여유, 실제 수집 속도를 입증하지 않는다. 운영 전환 후에는 별도 승인된 작은 범위 수집과 영속 결과 조회로 확인해야 한다.
