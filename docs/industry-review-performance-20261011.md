# 업종분석 조회 속도 및 자료 검토 개선

## 목표와 기준

업종분석에서 저장 집계를 빠르게 읽고, 관리자가 관측 공백과 제외 사유를 찾아 업체 DB에서 검토할 수 있게 한다. 기준은 업종·실제 소재지·숙박월·관측 기준일이 동일한 네이버 플레이스 1~20위 표본이다. 복합 시설의 업종 중복 포함 및 업종 안의 업체 중복 제거 기준은 유지한다.

2026-10-11 운영 커밋 `71d8aa4`의 사천·글램핑·9월 집계는 첫 계산 120.766초, 원본 변경 확인을 포함한 저장 조회 4,475ms, 바로 이어진 재조회 23ms였다. 새로운 조건의 첫 계산과 이미 저장한 조건의 조회 시간을 구분한다. 목표는 저장 조회 2초 이내이며, 운영 측정 전에는 달성했다고 보고하지 않는다.

## 1. 저장 결과 조회 속도

- 원본 파일 목록과 수정 시각 확인이 직렬로 반복되는 경로를 최대 16개의 제한된 병렬 작업으로 바꾼다.
- 파일의 크기·수정 시각·교체 시각과 전체 파일 목록이 동일할 때만 월별 연결·해시 집계 결과를 재사용한다.
- 신규 회차, 파일 추가·수정·삭제, 폴더 안 파일만 수정한 경우를 모두 감지한다. 입력을 읽는 중 파일이 바뀌면 재검사하고 정상 집계를 덮어쓰지 않는다.
- 입력 확인이 끝났고 변경이 없으면 동일한 대기열 상태를 불필요하게 다시 저장하지 않는다.
- 동일 검사 요청은 하나의 진행 작업을 공유한다. 제한된 병렬 처리는 파일 정보 확인에 적용하며, 큰 원본 파싱과 월별 계산은 기존 메모리 보호 기준을 따른다.

## 2. 자료 검토 화면

기존 업종분석 탭에 `자료 검토`를 추가한다. 화면 순서는 날짜별 확보 현황, 검색·문제 유형 필터, 업체별 상세 목록이다.

| 화면 | 표시 내용 | 동작 |
| --- | --- | --- |
| 날짜별 요약 | 확보 업체·미확인 업체·매출 근거 부족 업체 수 | 선택 날짜의 업체로 범위를 좁힌다 |
| 검토 필터 | 업체명, 전체/미확인/오류·차단/가격·객실 기준 검토 | 현재 업종·지역·월 안에서만 필터링한다 |
| 업체 목록 | 업체명·주소지·객실 기준·확보율·문제 일수 | 문제 업체를 먼저 표시하고 20개씩 페이지를 나눈다 |
| 날짜 상세 | 상태·실제 관측시각·최근 미확인 시도·제외 사유 | 접기/펼치기, 해당 결과와 업체 DB로 이동한다 |

업체 DB 바로가기는 중앙 `companyId`를 사용한다. 저장 결과 바로가기와 DB 검수 화면의 용도를 구분한다. PC와 모바일 모두 동일한 이름과 의미를 사용하고, 밝은 화면과 어두운 화면에서 색상과 문구로 상태를 함께 전달한다.

## 3. 날짜와 제외 사유

- **정상 관측:** 검증된 예약 0도 유효한 관측으로 포함한다.
- **수집자료 없음:** 해당 날짜의 근거가 없으면 공백으로 표시한다. 오류 기록이 없는데 차단이나 실패라고 추측하지 않는다.
- **계산 제외:** 예약 오류·차단·누락·재고 불일치 등 실제 검증에서 제외한 이유를 표시한다.
- **일부 관측:** 예약은 사용하지만 가격 근거가 부족한 날짜처럼 사용할 수 있는 지표와 사용할 수 없는 지표를 구분한다.
- **이전 정상 관측 + 최근 미확인:** 최근 실패 때문에 보존된 유효 관측을 0이나 공백으로 바꾸지 않는다. 사용한 자료의 확인시각과 최근 시도의 상태를 별도 표시한다.
- 여러 사유가 같은 날짜에 있을 수 있으므로 사유별 수치를 단순 합산한 값이 전체 공백 수와 같다고 설명하지 않는다.

공통 월간 계산 엔진이 실제 제외 단계에서 제공하는 선택적 진단 콜백을 사용한다. 검증 규칙을 화면용으로 다시 복제하지 않으며, 원본 행 전체를 화면이나 저장 집계에 노출하지 않는다. 사유·업체 ID·숙박일·관측시각·회차 ID와 필요한 수량만 축약한다.

## 4. 저장 구조와 기존 결과

- 날짜별 검토 근거를 업종 집계 결과의 `review`에 함께 저장한다. 검토 탭 진입 시 원본 전체를 다시 읽는 별도 API는 만들지 않는다.
- `review.schemaVersion=1`로 구조를 관리하고, 업체별·날짜별 상태와 사유별 요약을 동일한 선택 범위에서 산출한다.
- 검토 근거가 없는 기존 정상 결과는 표시를 유지하면서 새 구조의 집계를 준비한다. 새 계산 완료 전에는 날짜별 근거를 확인했다고 표시하지 않는다.
- 새 구조로 보완할 때도 직전 정상 결과를 먼저 보관한다. 보관 또는 새 계산이 실패하면 이전 정상 결과를 유지한다.
- 선택 업종 이외 업체에서 발생한 제외 수나 경고가 선택 업종의 확보율과 섞이지 않게 한다.
- 업체 고유번호 미확정·플레이스 번호 중복 등 전체 원본의 경고는 `저장 자료 전체 참고`에 별도 표시한다. 현재 선택 업종의 공백으로 합산하지 않는다.
- 자동 갱신 중 검색창의 커서·선택 영역을 유지하고, 한글 조합 중에는 화면 교체를 미룬다.

## 개발 및 로컬 검증 결과

원본 변경 검사, 검토 근거 가공·저장, 기존 결과 구조 보완, 자료 검토 UI의 개발을 완료했다. 첫 운영 배포에서 메모리 부족이 확인돼 직전 안정 버전으로 복원했다. 아래 운영 검수와 보완 결과를 로컬 검증과 구분한다.

### 원본 변경 검사 성능

같은 모의 자료 240회차·9,840파일(회차별 manifest 1개·상세 JSON 40개)에서 기존 커밋 `71d8aa4`와 개선 리더의 `periodRevisions()`를 각각 순차로 4회 호출했다. 월별·전역 변경 토큰은 모두 동일했다.

| 측정 | 기존 | 개선 |
| --- | ---: | ---: |
| 리더 첫 호출 | 380.2ms | 117.2ms |
| 반복 3회 중앙값 | 318.8ms | 90.8ms |

반복 검사 중앙값 기준 71.5% 단축됐다. 이는 로컬 파일 검사 실측이며 운영 HTTP 조회 시간에 그대로 적용할 수 없다. 첫 호출은 리더 캐시가 없는 상태이며 디스크 캐시가 없는 상태를 뜻하지 않는다.

별도의 48회차·1,969파일, 파일 정보 호출에 2ms 지연을 둔 회귀에서도 직렬 31,346.4ms, 병렬 1,879.0ms, 최대 동시 실행 16을 확인했다. 이 지연은 시험 조건이며 운영 지연이 아니다. 내부 옵션에 32를 입력해도 16을 넘지 않는다. 모든 파일 확인과 내부 파일 수정·추가·삭제, 회차 폴더 삭제를 감지했다.

### 계산·저장·화면 검증

- 업종·저장·원본·UI·월간 공통 엔진 회귀 100개 통과. 이후 UI 보완 회귀 30개 및 동시 처리 상한 회귀 1개를 추가 확인했다.
- 실제 로컬 HTTP 통합 검증 통과: 검토 근거 저장, 구형 집계의 이전 정상 결과 표시·보관, 재시작 재사용, 다른 월 수집의 마감월 재사용, 객실 검수 갱신, 관리자 권한 제한, 원본 보존, 외부 요청 금지.
- 정상 예약 0, 원본 없는 날짜, 재고 충돌 제외, 금액 미확인, 최근 실패 뒤 이전 정상 예약 유지가 구별된다. 명시적인 차단 증거가 없는 HTTP 200만으로 차단이라고 판정하지 않는다.
- PC 1,280px 및 모바일 390px에서 날짜·업체명·문제 필터, 접기·펼치기, 밝은/어두운 화면, 업체 DB 바로가기 확인. 모의 업체의 중앙 ID에 맞는 DB 상세로 이동했고 가로 넘침이 없었다. 페이지당 20곳 및 한글 조합 중 자동 갱신은 UI 회귀로 검증했다.
- 브라우저 검수 자료는 격리된 모의 자료다. 운영 업체의 현재 수치나 접근 상태를 검증한 자료로 사용하지 않는다.

## 메모리 보완 및 재배포 전 검증

- 완료된 원본 월 캐시는 최대 1개로 제한하고, 직렬 대기열의 다음 읽기가 시작되기 전에 이전 월·만료된 원본을 해제한다. 만료 캐시를 지역 변수로 보존한 채 새 읽기를 기다리지 않도록 조회를 짧은 동기 함수로 분리했다. 동일 월의 진행 중 읽기 공유와 유효 캐시 재사용은 유지한다.
- 회사·지역·업종의 원천 읽기에서는 키워드 소속 판정에만 필요했던 진단 원본 복사를 보관하지 않는다. 키워드 보고서의 소속 판정·진단은 그대로 유지하며, 미식별 행은 실제 사용되는 후보 ID와 건수만 남긴다.
- 파일 정보 확인은 최대 16개를 유지하지만 manifest JSON은 한 번에 1개만 읽고 공표 월·예약 범위의 축약된 연결 정보만 보관한다. 원본 파일 수정 시각·크기·교체 시각을 계속 확인하므로 축약 대상 밖의 manifest 내용 수정도 감지한다.
- 회귀 111개가 통과했다. 동일 업체·키워드·지역의 집계 수치, 검수 재계산·순위·정상 0·실패/누락 구별과 기존 정상 결과 보존을 포함한다. 이후 캐시 조회 helper 보강의 관련 회귀를 추가 확인한다.
- 제한 heap 시험 `node scripts/test_industry_memory.cjs --compare-baseline 71d8aa4`는 외부 요청 없는 별도 자식 프로세스에서 실행한다. 143업체·유효 관측 103업체, 읽기별 24,000개의 독립 원문 가격근거를 사용하며 old-space 120 MiB·semi-space 4 MiB다. 기존 캐시는 월 전환 후 이전 원본들을 붙잡은 상태에서 heap 오류가 재현됐고, 보완판은 동일월 다른지역 재사용·만료 동일키 재읽기·10월·9월 재진입을 모두 통과했다.
- 새 읽기 직전 이전 원문 배열의 잔존이 없음을 테스트 전용 WeakRef/GC로 확인했다. 원문 해시가 변하지 않았으며 재진입한 집계는 generatedAt을 제외한 검토·품질·전체 수치가 일치했다. 실제 운영에 강제 GC를 사용하지 않는다. 이 모의 시험의 최고 RSS 173 MiB는 운영 최고 메모리나 운영 안전성을 보장하는 수치가 아니다.
- 변경 동결 후 업종 25개, 업종·월간·업체 통합 HTTP 검사 3개와 기본 검사 76개 명령을 추가 통과했다. npm.cmd가 없어 package.json의 동일 check 명령을 지정 Node로 실행했다. GitHub Actions 실행 기록이 없는 저장소이므로 CI 통과로 표현하지 않는다.

### 실제 신규 집계 및 월 전환 검수

- 외부 수집 없이 저장 자료로 새 조건 두 개를 차례로 계산했다. 9월 전체 지역 글램핑은 23:24:15 KST `ready`로 조회됐으며 관측 소요 92.056초였다. 대상 183업체·관측 1,025/5,490 업체·일, 검토 구조 v1이 저장됐다. 업체 수는 각 키워드·수집회차의 1~20위 합집합이며 한 검색의 순위 제한을 늘린 수치가 아니다.
- 이어 10월 전체 지역 캠핑·관측마감 10월 11일은 23:26:47 KST `ready`로 조회됐다. 관측 소요 151.227초, 대상 41업체·관측 461/1,271 업체·일, 검토 구조 v1이 저장됐다. 소요시간에는 5초 간격 완료 확인의 지연이 포함된다. 새 계산 시간은 저장 조회 2초 목표와 구분한다.
- 두 월의 계산 동안 서버 PID 64·시작 tick `1617228296`이 유지됐으며 오류·재시작 없이 완료됐다. 9월 종료 직후 RSS 884,844 KiB에서 10월 계산 시작 시 675,968 KiB로 감소했다. 이전 원문 객체의 해제는 로컬 WeakRef 시험으로 검증했고 운영 RSS 감소만으로 특정 객체 해제를 단정하지 않는다.
- 실제 계산 검수의 관측 최고 cgroup은 1,875,337,216 bytes(약 1.75 GiB), 서버 HWM은 1,147,316 KiB였다. 2 GiB 서비스의 모든 조건·동시 부하에 대한 안전성을 보장하지 않는다. 큰 원천 읽기는 직렬이며 과도한 동시 계산을 추가하지 않았다.

- 23:29:04 KST 최종 검사에서도 원본 관측·업체 DB·일일 설정·BG 예약 설정의 SHA256 네 개가 배포 전과 같았다. 파생 집계의 두 새 조건은 `ready`, 현재 계산·수집 대기는 없었다. 세 워커 실행·대기 0, BG 예약 `enabled=false`, 키워드 빈 목록, 다음 실행 없음 및 기존 일일 수집 비활성을 확인했다. 디스크 여유 8,000.2 MiB다.
