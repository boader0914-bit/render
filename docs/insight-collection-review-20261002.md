# 인사이트 업체 수집·결과·수정 요청

## 사용자 흐름

내 매장/경쟁 분석의 `수집하기 · 결과 확인` → 숙박 시작일, 1/7/14/31일, 데이유즈 유무 확인/숙박만/상세 수집 → `수집하기` → 접수 상태와 저장 결과 → 업체 또는 상품 검수 요청.

- 기본 데이유즈 범위는 유무 확인. 인원 2명, 업체명 검색, 상세 1위, 전체 상품, `scheduled` 수집기(AWS worker 표기)는 서버에서 결정한다. 고객은 수집기나 고유번호를 덮어쓸 수 없다.
- 요청 접수와 결과 저장 완료를 구분한다. 대기·진행 중에는 활동 표시와 상태 갱신을 제공한다. 계측되지 않은 퍼센트나 남은 시간을 만들지 않는다.
- 완료는 수집 품질·업체 식별자·숙박 범위·결과 저장·업체 DB 연결 확인 후 표시한다. 부분/실패/차단의 runId와 원인 코드를 보존한다. 현재 요청과 이전 보존 자료는 별도로 표시한다.
- 동일 업체·한국시간 당일·같은 조건은 고객 간에도 한 작업을 공유한다. 지역 키워드 결과에 포함된 해당 업체도 고유번호와 조회 조건·자료 충족 여부가 일치하면 재사용한다. DB 검수값과 관측값의 충돌 자체는 재수집 사유가 아니다.
- 접수 여부가 불명확한 요청을 재실행하거나 다른 수집기로 돌리지 않는다. 기존 차단 보호·워커 연결·저장공간 검사를 유지한다.

## 결과와 검수

- 업체 총 객실 수(DB 검수값 우선), 관측 최대 수량, 상품 개수를 구분한다. 40개 객실·상품 제한을 추가하지 않는다. 기존 신뢰도 경고를 표시한다.
- 한 업체/한 run의 상품·숙박일 자료만 전달한다. 같은 이름이어도 다른 플레이스/예약 사업자 번호의 자료를 합치지 않는다. 원본 파일·내부 메모·다른 업체의 진단 내용은 전달하지 않는다.
- 공개 예약은 녹색, 방막기 추정은 보라색. 다크/라이트 테마에서 색과 텍스트를 함께 사용한다. 매출은 실제 결제액이 아닌 추정값이다.
- 정상 응답의 0과 오류·누락·데이유즈 미조회는 구분한다. 공개 예약은 명시된 bookingCount만 표시한다. 판매 중지는 `판매중지 미확정`이다.
- 상품 카드는 접어두며 날짜별 표와 수정 폼도 펼쳐서 본다. 모바일 표만 가로로 스크롤한다.
- 업체 수정(객실 총량·매장명·주소·데이유즈 공유 구분·시설)과 상품 수정(날짜별 객실 재고·상품 구분)은 **검수 요청**으로 저장한다. 고객 입력이 즉시 공통 DB나 매출을 변경하지 않는다.
- 상품 요청은 runId, 상품 번호/키, 숙박일, 원래 값, 제안값, 근거와 버전을 보존한다. 오류 응답은 정상 재고로 보정 요청할 수 없다. 회사 정보 요청과 상품별 요청은 서로 대체하지 않는다.
- 관리자는 데이터랩 `인사이트 이용자 → 업체 정보 검수 요청`에서 원본/제안값과 상품·날짜를 확인하고 기존 공통 DB 수정 도구에서 반영한다. `DB 반영값 확인`은 실제 현재 값이 제안과 일치할 때만 허용된다. 상품 구분/공유 여부도 단순 요청 접수만으로 확정되거나 자동 반영되지 않는다.
- 현재 DB 검수값을 읽어 기존 수량·매출 산출식을 다시 적용한다. 원본 CSV/스냅샷은 덮어쓰지 않는다.

## 연결 경로

- 고객 BFF: `GET /api/customer/v1/companies/:companyId/collection`, 기존 POST commands의 `collect`, `product-correction`.
- 관리자 고객 보기: 동일 경로를 `/api/insight-admin/v1/customer-view` 아래에서 제공한다. 관리자 세션과 별도 고객 프로필 권한을 매번 확인한다.
- 중앙: `insight_http.cjs` → `insight_preparation.cjs` / `insight_collection_results.cjs` → 저장 run을 읽기 전용으로 조회하는 `readInsightCompanyEvidence`.
- 웹/인사이트 두 서비스 변경이다. 수집 워커의 실행 코드·속도·일정은 변경하지 않았다.
