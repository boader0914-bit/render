# 인사이트 일별 검수 결과와 발행 리포트 장기 보관

## 저장 위치와 역할

Render에서는 `/var/data/insight-archive`를 사용한다. `INSIGHT_ARCHIVE_DIR`로 전용 절대 경로를 지정할 수 있다. 기존 운영의 `DATA_DIR=/var/data/legacy`와 조회 캐시 경로를 변경하지 않는다. 로컬에서는 `DATA_DIR` 또는 명시적 보관 경로가 없으면 보관 기능이 비활성화된다.

한 디렉터리의 불변 기록을 `daily-review`, `published-report`로 구분한다. 파일명에는 중앙 서버·고객·공개 주소·고객/관리자 화면 구분의 해시와 기록 번호만 쓴다. 원본 계정 번호·세션·토큰·쿠키·개인 연락처는 보관하지 않는다. 자료 본문은 고객에게 허용된 업체 지표의 명시적 필드 목록으로만 구성한다.

조회 캐시는 최대 7일 재사용하는 빠른 표시 자료다. 이 장기 보관소에는 날짜 만료·건수에 따른 자동 삭제 기능이 없다. 메모리에는 목록 정보만 유지하며 본문은 열람할 때 검증해 읽는다. 이 보관소가 외부 백업을 대체하지는 않는다.

기존 업체 조회 캐시의 표시 버전 지문은 유지한다. 선택적인 원본 근거 필드만 추가하므로 배포 전 저장본도 즉시 표시할 수 있다. 근거가 없는 과거 캐시에 수집 번호를 만들어 붙이지 않으며 최신 중앙 응답을 검증한 후에만 장기 보관한다.

## 일별 검수 결과

정상 업체 조회의 최신 중앙 응답을 받은 시점에, 정확한 원본 연결이 가능한 업체·숙박월을 자동 보관한다. 같은 한국시간 검수일·동일 내용은 한 번 보관하고, 다음 날 또는 원본·계산·검수값이 달라지면 새 기록으로 남긴다. 보관함의 **검수 결과 보관**으로 과거 숙박월의 중앙 저장 자료를 명시적으로 읽고 보관할 수도 있다.

중앙 통합 월별 응답은 실제 선택된 날짜별 `companyId`, `runId`, `collectedAt`, `runQuality`와 `calculationVersion`, 전체 계산 근거 `runIds`를 제공한다. 현재 최신 수집 번호를 이전 월이나 다른 날짜의 원본으로 대신 붙이지 않는다. 동일 날짜의 근거가 중복되면 연결 불완전으로 표시한다.

기록은 자동 검사 결과임을 `review.basis=automatic_validation`으로 명시한다. 사람의 검수 완료나 실제 결제 매출로 표현하지 않는다. 정상 수량·가격을 확인한 날짜와 미확인 날짜를 함께 보존하되 상태를 구분한다. 정상 0은 0, 미확인은 null로 유지한다. 대기·갱신 중·실패·계산 미리보기·업체/월/계산 버전 불일치는 정상 보관 자료로 승격하지 않는다.

이 변경은 기존 수집 완료 이후 자료를 받는 연결에 대한 저장 기능이다. 새로운 크롤링, 고객별 매일 수집 일정 또는 서버 간 완료 알림 전송을 등록하지 않는다. 고객이 조회하지 않아도 수집 완료 시 즉시 전달하는 기능은 후속 일일 수집 대기열과 연결할 별도 단계다.

## 주간·월간 발행본

리포트 화면의 현재 30일 브리핑과 발행본을 구분한다. **발행본 보관**은 선택 숙박 기준일이 속한 월요일~일요일 또는 달력 월의 자료를 대상으로 한다. 고객이 보관한 업체·숙박월 검수 결과만 읽으며 수집이나 중앙 재계산을 시작하지 않는다.

업체·숙박월별 최신 보관 검수 결과 한 건을 사용하고, 선택 기간의 날짜를 각각 한 번만 포함한다. 내 매장과 경쟁업체의 수량·매출을 서로 합산하지 않는다. 일부 날짜만 확인한 경우 전체 기간 합계는 null, `knownSold`·`knownEstimatedRevenue`는 확인된 부분 합계로 구분한다. 기간 전체가 미확인이면 발행을 보류한다. 누락된 경쟁업체는 0으로 보정하지 않고 누락으로 표시한다.

발행 기록에는 다음 연결 정보를 고정한다.

- 회사별 중앙 `companyId`, 원본 `runIds`, 중앙 `calculationVersion`, 근거 해시
- 사용한 일별 보관 기록의 번호와 체크섬
- 발행 계산 버전, 대상 숙박기간, 생성 시각, 자료 확보 상태

원본이 갱신되어도 이전 발행본을 수정하지 않는다. 새 요청 번호는 새 발행본을 만들며, 동일 요청 번호 재전송은 기존 발행본을 반환한다. 같은 번호로 조건을 바꾼 요청과 동시 요청의 조건 충돌은 거절한다. 전송 응답을 확인하지 못했을 때 화면은 먼저 보관 목록을 확인하도록 안내하며 POST를 자동 재실행하지 않는다.

이번 발행본의 내용은 보관된 업체별 예약·매출 표와 출처다. 지역 분석 및 행동 제안이 있는 현재 브리핑은 별도 화면으로 유지한다. 고객에게 외부 메일·메시지를 보내거나 공개 링크를 생성하지 않는다.

### 부분 가격의 새 발행 기준

새 발행은 `insight-period-publication-v2-price-evidence`를 사용한다. `knownEstimatedRevenue`는 가격이 완전히 확인된 날짜의 소계로 유지한다. `knownRevenueSubtotal`은 여기에 수량 검수를 통과하고 공개·타채널 금액이 합계와 일치하는 부분 가격 날짜의 확인 금액을 더한다. 해당 부분만 `partialPriceKnownRevenue`에 별도로 보관한다. 전부 미확인인 금액을 0원으로 바꾸거나 수량 검수를 통과하지 못한 행의 금액을 더하지 않는다.

업체별 `uncertainty`에는 관측 미확인 날짜와 가격 미확인 날짜를 나눠 보관하며, 알 수 없는 추가 금액은 `null`이다. 화면은 이 날짜를 별도 표로 표시하고 정상 0원과 구별한다. 이전 v1 발행본은 저장 내용과 기존 표시 기준을 그대로 유지한다. 새 발행 요청과 새 번호로만 v2 발행본을 추가한다.

## 인증·저장 보호

목록·상세·보관·발행마다 중앙 로그인과 현재 등록 업체를 확인한다. 고객 계정, 고객/관리자 화면, 공개 주소와 중앙 서버별 자료를 구분한다. 업체 연결이 해제되면 파일을 지우지 않으며 현재 권한으로 열람할 수 없도록 한다. POST에는 동일 Origin과 현재 로그인 CSRF 값이 필요하다. 클라이언트는 계산 수치나 임의 출처를 제출할 수 없다.

기록은 SHA-256 체크섬을 검사하고, 임시 파일 동기화 후 덮어쓰지 않는 원자적 커밋으로 확정한다. 파일당 기본 2MiB, 새 저장 후 여유 200MiB를 보호한다. 공간 부족·훼손·전송 실패 때 이전 기록은 보존하며 오류를 표시한다. 저장소 오류와 정상적인 빈 목록을 구분한다. 디스크 증설이나 기존 자료 삭제를 자동으로 하지 않는다.

## API

고객 기본 경로는 `/api/customer/v1`, 관리자 고객 화면은 `/api/insight-admin/v1/customer-view`이다.

| 메서드 | 경로 | 기능 |
| --- | --- | --- |
| GET | `/archives?kind=...&limit=100&offset=0` | 보관 목록·저장소 상태·페이지 조회 |
| GET | `/archives/{id}` | 원본 연결을 포함한 고정 본문 조회 |
| POST | `/archives/reviews` | 등록 업체 번호와 숙박월의 중앙 저장 자료 보관 |
| POST | `/archives/reports` | 주간/월간·숙박 기준일·내 매장·요청 번호로 발행본 보관 |

## 적용과 검증

인사이트 서버에는 보관소·API·화면을, 데이터랩 서버에는 `insight_company_integrated.cjs`의 원본 연결 필드 추가를 적용해야 한다. 이 연결 정보가 없는 응답은 화면 조회는 가능하지만 장기 검수 결과로 확정하지 않는다. 중앙 집계 계산식·수집 엔진·워커·예약 설정은 변경하지 않는다.

검증은 1년 후 재시작 복원, 파일 훼손, 공간 부족, 프로세스 간 동시 저장, 고객 간 격리, 현재 권한 해제, CSRF, 원본 불일치, 정상 0/미확인, 월 경계 주간 집계, 발행 후 원본 변경, 같은 요청 번호 재시도를 포함한다. 개발 검증은 가상 자료와 임시 디렉터리만 사용하며 실제 수집이나 운영 저장소 쓰기를 실행하지 않는다.
