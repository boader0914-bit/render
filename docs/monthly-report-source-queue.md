# 월간 리포트 저장자료 읽기 순서

월간 리포트 미리보기와 업체 DB·업종의 저장 집계 갱신은 같은 원본을 읽습니다. 원본을 동시에 재구성하면 전체 이력과 업체 목록이 여러 번 메모리에 올라가므로, 읽기는 한 번에 하나만 실행합니다.

- 사용자가 요청한 리포트와 업체 DB의 지정 마감일 조회는 `foreground`입니다.
- 업체 DB의 시작 시 정리·변경 반영과 업종 집계 갱신은 `background`입니다.
- 이미 실행 중인 읽기는 완료합니다. 대기 중인 사용자 조회를 다음 순서로 우선 배정합니다.
- 사용자 조회가 연속해서 대기하더라도 최대 4건 뒤에는 대기 중인 갱신을 1건 실행합니다. 각 분류 안에서는 먼저 들어온 순서를 지킵니다.
- 읽기 오류는 해당 요청에 전달하고 다음 작업을 진행합니다. 성공 자료·원본·마감월·결측 판정과 계산 방식은 바꾸지 않습니다.

이는 네이버 요청 속도나 수집기 동시 실행을 변경하는 기능이 아닙니다. 외부 요청을 만들지 않는 저장자료 읽기 순서만 다룹니다. 현재 진행 중인 큰 읽기 1건은 기다려야 하며, 저장 집계 재사용과 함께 실제 생성 시간을 별도로 측정합니다.

업체 DB는 시작 시 원본 변경을 확인하는 기존 정리를 유지합니다. 정상 저장월이라는 이유만으로 시작 정리를 생략하면 서버가 꺼져 있던 동안 바뀐 원본이나 검수값을 놓칠 수 있습니다. 생략하려면 별도의 영속 원본 버전 확인이 선행되어야 합니다.

서버는 기존 수집기 조정 상태를 복원한 뒤, 월간 리포트 선택 목록의 저장본을 검증하거나 새로 준비하고 나서 요청을 받습니다. 준비가 끝나면 기존 업체 DB·업종의 시작 정리와 모든 예약 기능을 이어서 시작합니다. 목록 준비가 실패해도 서버는 시작하되 짧은 오류코드를 남기며, 이후 실제 목록 조회에서 다시 검사합니다. 준비 실패를 정상 빈 목록으로 저장하지 않습니다. 운영 조회 2초 목표는 서버가 정상 응답을 시작한 뒤 측정하며, 배포 후 목록 준비에 걸린 시작 대기시간도 별도로 기록합니다. 새 조건의 예약·매출 미리보기 전체 계산을 미리 완료하는 기능은 아닙니다.

검증: `node --test scripts/test_source_read_scheduler.cjs`와 업체 DB·업종 회귀검증. 단일 실행, 사용자 조회 우선, 갱신 작업의 진행 보장, 오류 이후 대기열 복구를 확인합니다.

## 선택 목록과 업체 이력 검색의 메모리 보호

2026-10-16 운영 화면 검수 중 15:06:50 KST에 Node의 JavaScript heap 약 1,021MB 한도 초과와 종료 코드 134가 확인됐습니다. Render가 자동 재시작했으며 리포트 선택 목록 요청의 502와 메모리 세션 만료가 관측됐습니다. 당시 업체 원본은 89.8MiB, 이력은 156.1MiB였습니다. 종료 로그만으로 특정 요청이 유일한 원인이라고 판정하지 않습니다.

- 공개 `catalog()`와 선택 목록의 새 생성도 같은 읽기 대기열을 사용합니다. 검증된 저장 선택 목록 조회는 원본을 재구성하지 않으므로 대기열 밖에서 실행합니다. 이미 대기열 안에 있는 집계는 내부 목록 읽기를 직접 실행해 자기 작업을 기다리는 교착을 방지합니다.
- 선택 목록과 업체별 대상 발견은 먼저 필요한 필드만 남기고 이력을 읽습니다. 날짜 목록을 찾기 위해 큰 상품·객실 원문을 계속 보유하지 않습니다.
- 저장 리포트 목록은 보고서를 하나씩 검증하고 즉시 요약 정보로 바꿉니다. 겹친 목록 요청은 같은 읽기를 공유하며, 완료 후 결과를 상시 캐시하지 않습니다. 개별 발행본의 무결성 검증은 유지합니다.
- 비JSON 서버 오류는 짧은 오류문과 HTTP 상태로 안내합니다. HTTP 200의 비JSON 응답도 자료로 채택하지 않습니다. 정상 JSON의 실제 0과 오류를 구분합니다.

이 보호는 단일 대형 파일의 최대 크기나 다른 모든 서버 경로의 메모리 사용을 제한하는 기능은 아닙니다. 운영에서 선택 목록·저장 집계 조회와 자연 발생하는 집계 작업이 함께 있을 때 프로세스 재시작 여부를 별도로 확인합니다.

## 선택 목록 저장과 원본 검사 재사용

`monthly_reports/selector_cache/`에는 업체 ID·이름·지역, 키워드, 지역 목록과 실제 자료가 있는 월만 저장합니다. 객실·상품 원문, 예약 이력, 검수 기준이나 미리보기 토큰은 저장하지 않습니다. 목록 생성에서 객실 수 준비와 전체 업체 복제를 생략합니다. 현재 코드의 목록 1개, 최대 8MiB이며 원자적으로 교체합니다. 서버·목록 코드가 달라지면 별도 버전으로 다시 생성합니다.

저장 목록은 파일의 형식·조건 키·내용 해시를 검증한 뒤 수행한 새 원본 검사와 저장된 버전이 같을 때만 반환합니다. 목록 검사는 업체 DB·관측 이력·지역 참조, 공개 수집 목록과 같은 규칙에 맞는 결과 폴더의 이름·직접 파일 목록·매니페스트를 확인합니다. 예약 상세 원문·객실 검수값·공휴일·API 자료는 목록을 바꾸지 않으므로 목록 검사에서 제외하고, 예약·매출 집계의 전체 변경 검사에서는 계속 확인합니다. 새 목록을 만들 때의 전후 검사와 동시 요청 각각의 새 검사는 유지합니다. 읽기 중 변경이면 최신 원본으로 다시 만들 수 있으며, 검사 오류나 생성 중 재변경은 기존 저장본을 유지한 채 오류로 알립니다. 확인 실패를 빈 목록이나 최신 자료로 바꾸지 않습니다. 새 목록 생성만 기존 원본 대기열에 넣어, 큰 집계 진행 중에도 변경 없는 저장 목록은 조회할 수 있습니다. 한국시간 오늘과 현재 월·기본 월은 매 응답 계산하므로 월이 바뀌어도 저장된 가상 월이 남지 않습니다.

선택 목록은 전체 원본 검사와 독립된 검사 대기열을 사용합니다. 매 호출마다 필요한 파일은 `lstat`, 결과 최상위와 각 대상 폴더는 직접 `readdir`와 검사 전후 `lstat`을 수행합니다. 일부 파일시스템은 자식 추가 직후에도 폴더 변경 시각이 같을 수 있어 목록 검사에서 폴더 이름 캐시로 탐색을 생략하지 않습니다. 예약 상세 하위 폴더에는 내려가지 않습니다. 파일 추가·삭제·교체, 권한 오류, 심볼릭링크와 검사 중 변경을 계속 감지하고, 메타데이터 동시 조회는 기본 16개, 직접 이름은 전체 100,000개로 제한합니다. 검사 도중 들어온 요청은 그 요청 뒤에 시작하는 후속 검사로 묶습니다. 시간 제한만으로 ‘변경 없음’을 판단하지 않습니다. 예약·매출 집계의 전체 검사와 기존 메모리 보호 대기열은 유지합니다.

배포에 포함된 작은 지역 참조 JSON만 파일 내용의 SHA-256으로 비교합니다. 목록 검사는 `region_master.json`, 예약·매출 집계 검사는 여기에 `tourism_region_map.json`까지 포함합니다. 내용이 같은 재배포에서 수정시각·inode가 바뀌었다는 이유만으로 저장 결과를 다시 계산하지 않습니다. 매 검사마다 새 `lstat`과 파일 열기·읽기를 수행하며, 열린 파일의 신원과 읽기 전후 경로·파일 메타데이터가 일치해야 합니다. 읽기는 64KiB 단위, 파일당 최대 4MiB로 제한하고 읽는 중 증가도 감지합니다. 읽기 오류·권한 오류·심볼릭링크·교체·검사 중 변경이면 최신으로 인증하지 않고 오류로 알립니다. 업체 원본·관측 이력·검수 기준·수집 결과·공휴일 등 운영 자료의 기존 메타데이터 검사와 새 폴더 목록 검사는 그대로 유지합니다.

화면을 다시 열면 선택 목록과 저장 리포트 목록을 동시에 조회하고 사용자가 정한 기간·검색어·유효한 대상을 유지합니다. 두 응답의 성공 여부를 각각 확인한 뒤 반영하고, 최신 화면 요청만 결과를 적용합니다. 한쪽 실패가 다른 쪽의 정상 결과를 지우지 않으며 두 조회가 끝나기 전 중복 작업을 막습니다. 삭제·병합된 대상은 해제하고 그 대상의 이전 미리보기는 무효화합니다. 목록 확인 실패 시 기존 목록을 최신으로 안내하지 않고 새 미리보기를 막습니다. 저장 목록 재사용 여부와 확인 시간을 조건 아래에 표시합니다.

이 변경은 월간 리포트의 목록에 적용됩니다. 업종분석의 최초 목록은 별도의 전체 카탈로그 확인이 남아 있으며, 이번 개선만으로 모든 분석 화면의 최초 조회가 빨라졌다고 보지 않습니다. 운영 2초 목표는 배포 후 실제 자료와 배경 집계가 함께 있는 조건에서 측정해야 합니다.

화면은 숫자·날짜 표시 도구와 같은 스냅샷의 마크업을 재사용합니다. 숨겨진 지역분석 메뉴의 선택 목록은 리포트로 이동할 때 다시 만들지 않으며, 숨겨진 화면의 조회 중지는 계속 적용합니다. 이 최적화는 저장 자료·합계·권한·화면 조건을 바꾸지 않습니다. 최초 진입, 저장 목록 재사용, 저장 집계 미리보기를 구분해 측정하며, 저장 집계가 없는 새 조건의 원본 계산 시간을 2초 조회 실적으로 보고하지 않습니다.

## 초기 조회와 새 화면 선택의 경합

로그인 직후 초기 자료를 읽는 동안에도 메뉴를 사용할 수 있습니다. 초기 조회가 끝났을 때 사용자가 이미 다른 화면을 선택했다면, 시작 시 기록된 과거 화면을 다시 복원하지 않습니다. 브라우저 이전·다음 이동도 새 선택으로 취급합니다. 사용자가 이동하지 않았을 때의 화면 복원과 역할별 접근 제한은 유지합니다.

월간 리포트가 열린 동안 늦게 도착한 시작 자료는 상태에 반영하되, 숨겨진 수집 결과·업체 DB·운영 홈 전체를 다시 그리는 작업은 미룹니다. 홈과 DB는 각각 현재 본문만 최신 상태로 표시하고, 다른 숨긴 화면의 갱신 필요 표시는 유지합니다. 수집·설정 등 기존 화면을 실제로 열 때에는 기존 갱신 경로로 최신 자료를 복원합니다. 같은 관리자 탭 안의 세부 메뉴로 직접 이동하는 경우도 포함합니다. 초기 조회에서 이미 함께 기다리는 회원·삭제요청·보안 조회는 최신 결과 조회가 중복 요청하지 않으며, 이후 사용자가 다른 수집 결과를 직접 선택할 때에는 기존처럼 갱신합니다. 원본 수집·예약 설정·집계 계산·결측 판정은 변경하지 않습니다.

홈 버튼의 탭 전환과 세부 메뉴 동기화가 연달아 실행돼도 운영 요약은 한 번만 만듭니다. 홈에서는 업체 DB·회원·연동·지역·보안·기존 업체 도구를 숨겨진 상태로 다시 만들지 않습니다. 홈으로 돌아온 뒤 도착한 DB 저장·상세 응답도 받은 상태는 보존하고 홈 요약에만 반영합니다. DB 첫 진입도 DB 본문을 한 번만 만듭니다. 업체 목록·검토에서는 지역관리 형제 영역을 숨기고 준비 작업을 중지하며, 지역 DB를 열면 기존 지역자료 연결을 유지합니다. 업체 통합관측은 본문을 만든 뒤 한 번 연결하고, 세부 메뉴 동기화로 같은 조회를 재시작하지 않습니다. 늦게 도착한 DB 상세 응답은 현재 DB·홈에서만 표시하고 다른 메뉴의 숨은 DB를 다시 만들지 않습니다. 초기 조회의 재개, 지도·업체 통합 화면의 정지와 해제, 브라우저 이력 복원, 관리자와 고객보기의 권한은 유지합니다. 다른 메뉴의 기존 전체 갱신을 모두 분리한 변경은 아닙니다.

월간 리포트가 열리면 초기 최신 수집의 상세·이력·업체 요약 후속 조회도 아직 보내지 않은 단계부터 미룹니다. 이미 보낸 요청을 취소했다고 표현하지 않으며, 받은 원본은 보존합니다. 월간 화면을 나가면 미뤄 둔 수집 ID를 먼저 비우고 관리자 권한에서 한 번 재개합니다. 다시 월간 화면으로 돌아오면 다음 조회 경계에서 멈춥니다. 직접 선택한 수집 ID는 초기 자동 선택보다 우선하며, 오래된 목록·이력·업체 요약 응답이 새 선택을 덮거나 이전 작업을 재등록하지 않도록 요청 순서를 확인합니다. 수집 결과가 없는 경우의 업체 요약은 별도 재개합니다. 복원할 이력에 수집 ID가 명시되면 그 ID를 우선하고 초기 최신 ID를 중복 조회하지 않습니다. 실패하면 기존 자료와 오류를 남기며 자동 재시도하지 않습니다.

월간 화면의 진입·미리보기 완료 진단은 DOM 속성으로만 기록합니다. 저장 자료·리포트 문구를 변경하지 않으며, 도구가 클릭을 전달한 시간과 실제 화면 처리 시간, 이전 화면의 `aria-busy` 상태를 구분해 검수합니다.

## 홈·DB의 앱 전환시간 검수

`admin-transition-timing.js`는 홈·DB 진입의 앱 처리 시작부터 동기 갱신 완료, 이후 두 번의 애니메이션 프레임을 거친 표시 준비 시점까지를 `#appMain`의 `data-app-transition-*` 속성에 남깁니다. 메모리와 현재 문서에 마지막 한 건만 유지하며 서버 전송·영속 저장은 하지 않습니다.

| 속성 | 의미 |
| --- | --- |
| `seq`, `destination`, `source`, `started-at` | 새 전환 번호, 대상(`admin:overview` 또는 `admin:database`), 진입 경로, 시작시각 |
| `sync-ms` | 앱 진입 처리부터 동기 화면 갱신까지의 경과시간 |
| `display-ms` | 같은 시작부터 두 프레임 뒤까지의 경과시간. 물리적인 픽셀 표시를 확정하는 값은 아님 |
| `input-wait-ms` | 입력 이벤트 시각의 시간축이 검증될 때만 기록하는 보조 대기시간. 도구의 전체 입력 전달시간은 아님 |
| `status`, `reason` | `pending`, `waiting`, `ready`, `error`, `hidden`, `invalidated`, `unavailable` 및 안전한 사유 코드 |

새 메뉴를 열면 이전 숫자를 지우며, 전환 번호·대상·권한·가시성이 일치할 때만 완료로 기록합니다. 자료 대기 중이면 `waiting`이고 같은 전환에서 자료가 도착하면 처음 시작시각부터 최종 준비시간을 이어서 측정합니다. 오류·미계측·숨김은 정상 0ms와 구분합니다. DB 목록·기본 상세의 표시를 검수하는 값이며 통합관측·지역자료 등 각 모듈의 추가 비동기 조회 완료와는 구분합니다. 검수 시 새 번호와 `ready`, 활성 패널·현재 조건·실제 표시 수치를 함께 확인하고, 클릭 도구 왕복시간·스크린샷 확인시간을 별도로 기록합니다.

## 로그인 직후 업체 기본자료 우선 표시

관리자 로그인 확인과 이벤트 연결이 끝나면 `/api/company-master/bootstrap`으로 업체 기본자료를 먼저 조회합니다. 업체자료를 홈 또는 DB의 현재 본문에 표시하고 두 프레임의 표시 기회를 준 뒤, 수집 목록·누적이력·회원·연동 상태 조회를 시작합니다. 홈과 DB 기본 화면에서는 큰 최신 수집 결과의 상세 읽기를 미루고 결과 화면에서 재개합니다. 업체 상세 이력은 업체 선택 후 조회합니다. 기본자료 저장·변경 검사와 전체/축약 자료의 검수 기준은 [업체 DB 초기 조회 분리](company-bootstrap.md)를 참고합니다.

- 초기 조회와 업체 직접 링크가 겹치면 같은 진행 중 GET을 공유합니다. 완료한 초기 업체자료는 같은 세션의 후속 bootstrap에서 재사용합니다. 사용자 수집 결과 선택은 명시적인 새 조회로 기존 요청 순서를 무효화합니다.
- 세션·역할·요청 순서와 요청 시작 당시 업체 객체 및 업체 배열 원소를 확인합니다. 보정·검수·상세 병합이 먼저 적용되면 오래된 GET 성공·실패가 이를 덮지 않습니다.
- 재수집 시간 추정은 첫 표시 이후 준비하며, 최신 수집이 없거나 월간 리포트가 열려 있으면 후속 bootstrap에 맡깁니다. 추정 응답도 세션·업체·수집 결과·최신 요청 검사를 통과해야 적용합니다. 추정값을 보여주는 현재 검토 화면만 갱신하며 홈과 DB 목록은 다시 만들지 않습니다.
- 최초 조회 중에는 ‘업체 기본자료를 불러오고 있습니다’로 표시합니다. 정상 0개는 조회 완료로 재사용할 수 있고 오류는 정상 빈 자료로 저장하지 않습니다. 기존 정상 자료가 있으면 초기 조회 오류에서도 보존합니다.

`node --test scripts/test_company_master_priority.cjs scripts/test_app_bootstrap_navigation.cjs`는 실제 함수와 지연 응답을 사용해 우선 표시·요청 공유·권한·이전 응답 방지·후속 준비를 검증합니다. 운영의 2초 달성 여부는 새 로그인 직후 아직 업체자료가 대기 중인 상태에서 DB를 열고, 같은 전환 번호의 `waiting → ready` 최종 시간을 실제 업체 수와 함께 다시 측정합니다. 로컬 모의자료의 빠른 결과를 운영 달성 근거로 사용하지 않습니다.
