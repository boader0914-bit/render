# 객실 총량·예약 수량·데이유즈 산출 기준

적용 기준일: 2026-09-24. **DB 보정값 우선 → 보정값이 없으면 최대 관측 수량** 기준을 모든 업체에 동일하게 적용한다. 계산 버전은 `inventoryEvidence.version=4`이며, 방막기 가격 정책은 `phoneValuationPolicy=same_product_observed_price_v1`이다. 수집 원문은 보존하고 공개 예약과 방막기(전화·타채널 예약 추정)를 따로 기록한다.

## 1. 객실 총량의 우선순위

1. 활성 상태인 **업체 DB의 객실 수 보정값**이 있으면 그 값을 총량으로 사용한다. 관측 최대값보다 크거나 작아도 보정값이 우선이다. 보정값을 수정하거나 해제하면 다음 조회에 현재 기준을 다시 적용한다.
2. 보정값이 없으면 동일 업체의 날짜별 숙박 수량 합계 중 **최대 관측 수량**을 기본 추정값으로 사용한다. 반복해서 나온 수량이나 기간 합계를 일수로 나눈 값을 쓰지 않는다. 다른 날짜의 상품별 최대값을 무조건 합산하지 않는다.
3. 플레이스 객실 안내의 전체 객실 수는 **객실 안내 참고**로 출처와 함께 표시한다. 이 값 자체로 총량을 늘리거나 줄이지 않는다. 검토 후 DB 보정값으로 저장한 경우에만 1순위가 된다. 안내가 없어도 수집 근거로 총량을 추정할 수 있다.

같은 업체에서 이전에 관측한 최대 수량은 `inventoryCapacityBaseline.lodging`으로 전달한다. DB 보정값은 별도 `lodgingOverride.count`로 전달하며, 이전의 안내·보정 기반 계산값을 관측 최대값에 섞지 않는다. 데이유즈 상품 수량은 숙박 총객실 수에 더하지 않는다.

예를 들어 민트 표본의 수집 최대값이 27실이고 객실 안내가 28실이면 보정값이 없는 계산 기준은 27실, 안내 참고값은 28실이다. 검토한 28실을 DB에 보정값으로 저장하면 총량은 28실이 된다. 안내가 없는 시즌도 같은 규칙을 적용한다.

글램핑으로 확인된 업체의 **미보정 최대 관측 수량이 40실을 초과**하면 객실 수와 상품 구성 검토 표시를 남긴다. 40실은 검토 기준이지 상한이 아니므로 수량을 40으로 자르지 않는다. DB에서 검토한 50실처럼 관측값과 모순 없는 예외는 그대로 사용한다.

DB 보정값보다 같은 날짜의 관측 총량 또는 `예약 가능 + 공개 예약`이 크면 보정 총량과 수집값을 모두 보존하고 수량 충돌로 표시한다. 그 날짜에는 전화·타채널 예약 추정과 예약률을 계산하지 않는다. 관측된 공개 예약을 지우거나 임의로 줄이지 않는다.

객실이 아닌 안내상품은 계산에서 분리한다. 현재 적용 조건은 공백을 제거한 이름이 정확히 `현장예약및전화예약`이고 모든 관측 가격이 없거나 0이며 별도의 정상 유료 숙박 상품이 있는 경우다. 또한 DB 검수 총량과 A/B 번호가 있는 개별 객실 상품 수가 일대일로 정확히 일치하는 경우에만, 개별 객실의 1실 초과 수량을 계산용으로 1실로 정규화한다. 안내상품 제외 및 수량 정규화 근거를 별도 보존하며 원문은 변경하지 않는다. 총량만 맞추기 위해 일반 객실 타입의 수량을 잘라내지는 않는다.

기간 총량은 `고정 총객실 수 × 조회 일수`이다. 총 10실이고 31일을 조회하면 **310객실·박**이다. 객실·박은 객실 1실을 1박 이용하는 단위이며 예약 건수와 다르다. 누락 날짜가 있더라도 객실 총량은 유지하되 수집 완료 범위와 미확인 수량을 표시하며 전체 기간 예약률을 확정하지 않는다.

화면에는 총량의 기준을 **DB 보정** 또는 **최대 관측(추정)**으로 표시한다. **객실 안내 참고**는 별도 보조 근거이며 총량의 확정 출처로 표시하지 않는다.

## 2. 공개 예약과 전화·타채널 예약 추정

계산 단위는 `업체 + 이용일 + 수집 실행`이다. 같은 이용일의 상품 수량을 합산한 뒤 아래 식을 적용한다.

```text
C = 고정 총객실 수
A = 네이버에서 예약 가능한 수량
B = 네이버 공개 예약 수량(bookingCount)
U = max(0, C - A - B)       # 예약 불가 수량 중 공개 예약으로 설명되지 않은 부분
D = 같은 객실을 사용하는 데이유즈의 해당 날짜 공개 예약 수량
E = min(U, D)               # 숙박 예약 추정에서 제외할 데이유즈 수량
P = max(0, U - E)           # 전화·타채널 예약 추정
숙박 예약 추정 합계 = B + P
예약률 = (B + P) / C
```

데이유즈가 없거나 별도 객실 사용이 확인됐으면 E=0이다. 예약 가능한 수량 A는 이 계산으로 늘리지 않는다. 공개 원문의 `stock`, `bookingCount`, `occupiedBookingCount`, 판매 상태도 변경하지 않는다.

**공개 예약이 0이라는 이유만으로 전 객실을 전화예약으로 만들지 않는다.** 예약 가능한 객실은 남겨둔다. C=10, A=10, B=0이면 전화예약 추정은 0이다. C=10, A=0, B=0이면 이 운영 기준에서 전화·타채널 예약 추정 10실이다. 판매 중지 사유나 거래 내역까지 확인했다는 의미는 아니다.

| 사례 | 총객실 C | 예약 가능 A | 공개 예약 B | 데이유즈 제외 E | 전화·타채널 추정 P | 숙박 예약 추정 합계 |
|---|---:|---:|---:|---:|---:|---:|
| 전 객실 예약 가능 | 10 | 10 | 0 | 0 | 0 | 0 |
| 공개 수량 3실·공개 예약 3실 | 10 | 0 | 3 | 0 | 7 | 10 |
| 전 객실 판매 닫힘·공개 예약 0 | 10 | 0 | 0 | 0 | 10 | 10 |
| 공개 예약 2·잔여 4·공유 데이유즈 3 | 10 | 4 | 2 | 3 | 1 | 3 |

금·토·일 여부만으로 계산 계수를 바꾸지 않는다. 모든 요일에 같은 규칙을 적용한다.

## 3. 데이유즈와 같은 객실을 쓰는 경우

- 같은 업체·이용일에 관측한 **데이유즈 예약 수량**만 제외한다. 데이유즈 전체 재고나 다른 날짜의 예약을 빼지 않는다.
- 공유 객실이 확인되면 공유 규칙을 적용한다. 숙박·데이유즈를 병행하지만 공유 여부가 미확인이면 함께 쓴다고 가정하며 `assumed_shared`로 설명한다. 별도 객실 사용이 확인되면 제외하지 않는다.
- 차감 대상은 전화·타채널 예약으로 추정하려는 부분 U뿐이다. 숙박의 공개 `bookingCount`를 줄이지 않는다.
- 고정 총객실 수를 사용하므로 데이유즈가 네이버 숙박 `stock`에서 이미 빠졌더라도 해당 차이가 U에 포함될 수 있다. 같은 날짜의 데이유즈 예약만큼 한 번만 제외한다.
- 데이유즈가 3회여도 숙박 추정 대상이 1실이면 최대 1실만 제외한다. 음수 예약이나 추가 예약 가능 수량을 만들지 않는다.
- 데이유즈 일정 수집이 실패하거나 일부 상품이 누락되면 총량의 설명되지 않은 차이는 미확인으로 남긴다. 단, **정상 숙박 상품 응답에서 직접 관측한 방막기**는 사용자 요청에 따라 별도 추정 매출에 포함한다. `명시 방막기 = 관측 수량 - 예약 가능 - 공개 예약`이며, 확인된 같은 날짜 공유 데이유즈 예약은 여기서 한 번만 제외한다. 데이유즈 미확인·부분 수집 표시는 그대로 유지한다.

공유 여부와 제외 수량은 추정 설명에 남긴다. 같은 입력으로 재계산해도 두 번 차감되지 않아야 한다. 당일 이용의 매출·예약은 별도 합계로 유지하며, 당일 상품의 판매 중지를 전화예약으로 합성하지 않는다.

## 4. 누락과 수량 0은 다르다

네이버가 실제로 `stock=0, bookingCount=0`을 반환한 경우와 응답 실패로 값이 없는 경우를 구분한다. 수집 실패·누락 상품·수량 충돌에서 생긴 미확인 수량을 전화예약 추정으로 만들지 않는다. 일부 상품이 누락돼도 별도 정상 상품에서 확인한 공개 예약과 명시 방막기는 부분 금액으로 남길 수 있다.

`collectionFailed`, `stockObserved`, `inventoryObserved`, 판매 상태를 상세 기록에 보존한다. 관측된 공개 예약이 있으면 그대로 남기고 누락 부분을 별도로 표시한다. 일부 날짜가 빠졌다는 이유로 남은 날짜만 전체 기간인 것처럼 보여주지 않는다.

## 5. 예상 매출

```text
예상 매출 = 공개 예약 수량 × 해당 상품·이용일의 공개 가격
          + 전화·타채널 예약 추정 수량 × 근거가 있는 해당 상품·이용일의 가격
```

전화·타채널 예약은 실제 결제나 전화 통화를 확인한 값이 아니므로 매출에도 **추정**을 표시한다. 공개 예약 기준 금액과 전화·타채널 추정 금액을 구분한다.

상품별 과거 최대 수량은 부족분을 어떤 상품에 배분할지 판단하는 보조 근거다. 이를 합산하여 업체 총객실 수를 임의로 늘리지 않는다. 방막기의 당일 가격이 없으면 같은 상품의 정상 응답 중 같은 요일, 가장 가까운 날짜 순으로 가격을 보완하고 출처 날짜·수량·금액을 기록한다. 같은 상품에서도 가격을 찾지 못하거나 수량을 특정 상품에 배분할 수 없으면 가격 미확인으로 남긴다. 다른 상품 평균 가격으로 채우지 않는다. 확인된 공유 데이유즈의 객실을 특정할 수 없으면 명시 방막기 중 단가가 높은 수량부터 차감하여 매출을 낮게 추정하며, 차감 수량에는 숙박 매출을 붙이지 않는다.

공개 가격은 할인·환불·수수료·실제 결제액을 확인한 장부가 아니며 `actualRevenue`를 확정하지 않는다.

## 6. 표시와 저장

카드 첫 항목은 **객실 총량 10실**처럼 숙소 규모를 보여준다. 공개 예약은 녹색, 방막기 추정은 보라색으로 구분하고 수량·금액·범례를 함께 표시한다. **공개 예약 / 방막기 추정 / 숙박 예약 추정 합계**를 분리하고 접힌 설명에 고정 분모·예약 가능 수량·데이유즈 제외·미확인 수량을 제공한다. 가격 보완 금액은 따로 표시한다.

기간에 대한 310객실·박은 총객실 수와 다른 항목이다. 특정일 네이버 공개 수량이 3실로 줄어도 업체 총객실은 10실로 유지한다.

| 경로 | 역할 |
|---|---|
| `scripts/inventory_estimation.cjs` | 공통 v4 산식과 수량·가격 근거 분리 |
| `scripts/gyeongnam_glamping_crawl.cjs`의 `compactNaverScheduleDetail` | 상품·날짜별 관측 수량과 실패 상태 보존 |
| 같은 파일의 `applyCrawlerInventoryEvidence` | 숙박·데이유즈를 모두 받은 뒤 공통 산식으로 저장 집계 계산 |
| `scripts/glamping_app_server.cjs` | 동일 업체의 이전 최대 수량을 전달하고 저장 원문 기준으로 조회 결과 재계산 |
| `web/app.js` | 고정 총량과 공개·전화 추정을 같은 기준으로 표시 |

`weeklyProductDetails`의 stock, bookingCount, occupiedBookingCount, available은 관측 근거다. v4의 `inventoryEvidence.lodging.rows`와 기간 집계에는 `publicBookings`, `phoneBookings`, `sharedDayUseExcluded`, `unknownUnavailable`을 따로 둔다. `capacityBasis`는 적용 총량과 출처, `roomGuideReference`는 객실 안내 참고, `capacityReview`는 검토 사유를 기록한다. 상세 관측 근거와 추정 합계가 서로 다른 수량을 갖는 것은 의도된 구조다.

과거 원문과 회사 DB의 기록을 일괄 덮어쓰지 않는다. 현재 조회에서는 같은 원문을 v4로 재계산하고, 원문이 없으면 과거 합계만으로 새로운 추정값을 확정하지 않는다. 수집 결과·업체 상세·추세는 같은 총량과 산식을 사용해야 한다.

2026-09-24부터 정상 응답의 명시 방막기는 추정 매출로 표시한다. 이를 실제 전화예약 확인이나 수집 전체 완료로 바꾸지 않는다. 과거 이력과 월간 달력도 같은 일별 부분 금액을 합산하고, 수집이 불완전하면 예약률을 확정하지 않는다.

## 7. 검증 사례

1. 시즌처럼 최대 10실인데 특정일 공개 총량 3·공개 예약 3이면 고정 총량 10, 전화 추정 7, 숙박 추정 합계 10.
2. 최대 10·공개 예약 0·예약 가능 10이면 전화 추정 0.
3. 최대 10·판매 닫힘·공개 예약 0·예약 가능 0이면 전화 추정 10과 추정 근거를 표시.
4. 같은 날 공유 데이유즈 3·숙박 공개 예약 2·예약 가능 4라면 데이유즈 3 제외, 전화 추정 1, 숙박 추정 합계 3. 공개 숙박 예약 2와 예약 가능 4 보존.
5. 공유 데이유즈가 숙박 추정 대상보다 크면 대상 수량까지만 제외.
6. 응답 실패·누락 상품·재고 모순이 있으면 부족분을 예약으로 만들지 않음.
7. 전화 추정 수량은 있지만 상품별 가격을 확인할 수 없으면 가격 미확인으로 남김.
8. 두 번째 조회나 재계산에서도 총량·예약·데이유즈 제외·매출이 같으며 원문은 변하지 않음.
9. 호수도도글램핑 사용자 검수 17실(A동 10 + B동 7), 2026-09-24 정상 응답에서 공개 8실 × 259,000원 = 2,072,000원, 명시 방막기 9실 × 259,000원 = 2,331,000원, 합계 4,403,000원. 전화예약 안내상품은 제외하고 데이유즈 미조회 표시는 유지.
10. 같은 업체 2026-09-24 수집의 14일 원문 252행을 계산하면 공개 예약 22,397,000원 + 방막기 추정 15,158,000원 = 37,555,000원이다. 원문 재수집 없이 DB 17실 검수값과 현재 정책으로 검산한 값이며 실제 결제 매출은 아니다.

## 8. 후속 검토: 데이유즈 사전 확인과 상세 수집 선택 (미구현)

2026-09-23 사용자 제안에 따른 설계안이다. 현재 구현 완료 기능을 뜻하지 않는다.

1. 업체 검색 후 상품 목록과 명시된 이용 유형을 먼저 확인한다. 이 단계에서 선택 기간 전체의 날짜별 재고·예약 요청을 실행하지 않는다.
2. `데이유즈 있음 / 없음 / 확인 불가`로 구분하고, 숙박 상품도 확인해 `숙박 전용 / 숙박·데이유즈 병행 / 당일 이용 전용 / 확인 불가` 유형을 표시한다. 전체 상품 목록을 정상적으로 확인한 경우에만 없음으로 표시한다. 목록 일부 누락, 응답 실패, 애매한 상품명은 확인 불가다. 이름만으로 객실 공유 여부를 확정하지 않는다.
3. 사용자가 유형별 선택과 업체별 체크박스로 상세 수집 대상을 선택한다. 확인 불가 업체는 별도 표시하고 포함 여부를 선택할 수 있게 한다. 당일 이용 전용 업체는 숙박 객실·매출 집계에 섞지 않는다.
4. 병행 업체를 상세 수집할 때는 숙박과 데이유즈의 같은 이용일 수량을 함께 수집한다. 공유 여부가 미확인인 경우에는 그 상태를 명시한다. 데이유즈를 생략하고 부족한 숙박 수량을 전화예약으로 채우지 않는다.
5. 상세 수집을 생략한 업체는 `사용자 선택으로 상세 미수집`으로 기록한다. 수량 0, 매진, 정상 수집 완료로 처리하지 않는다. 과거 재고·예약을 오늘의 관측값처럼 재사용하지 않는다.
6. 신뢰도 비교용 기본 수집군은 유지하고 선택 수집군과 구분한다. 그렇지 않으면 데이유즈 병행 업체를 제외한 효과를 지역 매출 변화로 잘못 해석할 수 있다.

시간 절감은 상품 목록 확인에 드는 추가 요청을 포함해 실제 요청 수, 성공한 업체·상품·이용일 수, 총 소요시간으로 검증한다. 사전 단계에서 확인한 상품 목록은 같은 실행 내 상세 단계에서 재사용하도록 설계한다. 기존 당일 중복 방지와 워커 차단 감지 규칙을 유지한다.
