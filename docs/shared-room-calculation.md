# 숙박·데이유즈 공유 객실 산출 기준

작성일: 2026-09-20. 이 문서는 수집 원문을 보존하면서 계산·표시에 적용할 기준이다. 과거 저장 파일의 숫자를 확정 매출로 재해석하거나 덮어쓰지 않는다.

## 1. 서로 다른 네 가지 수량

| 구분 | 의미 | 사용 방법 |
|---|---|---|
| 실제 보유 객실 수 | 숙소가 물리적으로 보유한 객실. 객실 안내·운영자 확인 등 출처와 확인일이 필요하다. | 숙소 규모로 표시한다. 채널 재고보다 크다는 이유로 차이를 판매에 더하지 않는다. |
| 채널 관측 재고 | 특정 이용일·상품·관측 시점에 공개 채널이 반환한 `stock`, `available` | 그 관측 범위의 공급·잔여를 계산한다. 실제 객실 수와 같다고 단정하지 않는다. |
| 공개 예약 필드 관측 | 공개 응답의 `bookingCount` | 예약 관측 수량으로 보존한다. 결제 완료·취소 반영·실수령 매출을 뜻하지 않는다. |
| 차단·판매 중지·미확인 | `occupiedBookingCount`, 판매 불가, 기준 재고와의 차이, 수집 실패 등 | 원인별로 분리한다. 추가 예약·오프라인 판매·매출로 합성하지 않는다. |

`occupiedBookingCount`는 이름만으로 결제 예약에 합산하지 않는다. 공개 응답의 별도 점유 필드로 보존하고 의미가 확인되지 않으면 `unverifiedOccupied`로 표시한다. `stock`이 판매 전 총량인지 남은 수량인지도 수집 경로의 의미를 먼저 확인한다. 이미 잔여 수량인 필드에서 예약 수량을 다시 빼지 않는다.

민트글램핑의 확인된 객실 안내는 민트 1~21번과 라벤더 1~7번, 합계 **28실**이다. 9월 20일 공개 재고는 16+5=**21**이다. 28은 실제 객실 수이고 21은 그날 채널 관측 수량이다. 차이 7을 자동으로 판매 7건으로 만들지 않는다. 기간에 자주 반복된 21, 최대 관측 27도 각각 관측 기준이며 실제 보유 객실 수를 대체하지 않는다.

## 2. 날짜별 계산 순서

계산의 최소 단위는 `숙소 + 이용일 + 상품 + 수집 실행/관측 시점`이다. 서로 다른 이용일이나 관측 실행을 섞지 않는다.

1. 원문의 `stock`, `available`, `bookingCount`, `occupiedBookingCount`, 영업·판매 상태, 가격, 상품 ID를 보존한다. 누락·실패는 0과 구분한다.
2. `bookingCount`가 명시되어 있으면 그 수량을 공개 예약 관측으로 사용한다. `soldOut`나 `total - available`에 포함된 미확인 점유가 예약 필드를 덮지 못하게 한다.
3. `open=false`, `stock=0`, 예약 필드 0인 날은 판매 중지 또는 미오픈으로 남긴다. 객실별 리스트라는 이유로 `total=1, sold=1`을 만들지 않는다. 기준 재고를 채우기 위한 가상 판매도 추가하지 않는다.
4. 운영 기준·실제 객실 수와 채널 재고의 차이는 `inventoryShortfall`로 별도 표시한다. 이 값에 가격을 곱하지 않는다.
5. 예약 근거가 없는 잔여 감소는 재고 변화 또는 미확인 차단으로 표시한다. 판매 추정이 필요한 분석에서는 관측 예약과 다른 항목으로 드러내고 근거·추정 규칙을 함께 남긴다.
6. 판매 중지 상태에서도 명시적 예약 필드가 양수라면 그 원문을 삭제하지 않는다. 상태 불일치로 표시한다. 공급이 0이거나 불명확할 때 예약률은 계산 불가로 둔다.

기간 공급은 동일한 기준의 **날짜별 유효 공급 합계**다. 기간 판매·예약 관측도 해당 날짜 합계다. 목록과 상세가 동일한 합계를 사용해야 한다. `반복 기준 × 날짜 수`로 저장 합계를 다시 덮지 않는다. 전체 기간 비율은 `기간 예약 관측 합계 ÷ 같은 기간 공급 합계`이며 일별 비율의 단순 평균과 구분한다.

민트 기존 자료의 날짜별 공급 합계 675와 화면이 다시 만든 21×31=651은 서로 다른 분모다. 28×31=868 역시 전 객실을 31일 운영한다는 별도 가정의 공급량이다. 이 세 수치를 교환하여 사용하지 않는다. 근거 없는 판매 수량을 제거하면 과거 분자 159도 그대로 확정값으로 유지할 수 없다.

수정 후 민트의 31일 공개 수량 합계는 **667객실·박**, 숙박 예약 필드 합계는 **151**이다. 기존 675에는 기준 수량에 맞추려고 만든 8개가 포함되어 있었다. 당일 이용은 공급 합계 **81회**, 예약 필드 합계 **3회**다. 실제 28실은 이 분모와 별도로 표시한다.

## 3. 공유 객실 중복 차감 조건

민트 데이유즈는 14~22시 이용, 민트 또는 라벤더 랜덤 배정 안내가 있어 숙박과 같은 객실을 사용하는 구조는 확인된다. 이 안내만으로 개별 날짜의 숙박 예약 필드와 데이유즈 예약 필드가 같은 예약이라는 사실까지 확인되지는 않는다.

중복 차감은 다음 조건이 모두 충족될 때만 적용한다.

- 같은 숙소·이용일·공유 객실군·관측 실행에서 비교한다. 상품군 연결과 관측 시점이 불명확하면 차감하지 않는다.
- 해당 날짜의 데이유즈가 숙박의 차단 또는 추정 판매에 이미 포함되었다는 근거가 있다. 단순히 숙박과 데이유즈 수량이 같거나 같은 방을 쓴다는 안내만으로는 부족하다.
- 차감 대상은 숙박의 **추정 차단·추정 판매 부분**이다. 명시적인 `bookingCount`는 차감하지 않는다.
- 데이유즈가 이미 숙박 `stock`에서 제외되어 현재 숙박 추정 판매에 들어 있지 않으면 추가 차감하지 않는다.
- 같은 차단을 다른 데이유즈 상품이나 재계산에서 두 번 차감하지 않는다. 보정 근거와 적용 수량을 저장한다.

계산식은 다음과 같다.

```text
B = 숙박의 명시적 공개 예약 관측 수량
I = 숙박 추정 판매에 포함되어 있는 차단·미확인 추정 수량
D = 같은 날짜·공유 객실군·관측에서 확인된 데이유즈의 중복 차단 수량
E = I에 이미 들어 있음이 확인되고, 이전에 차감되지 않은 중복 차단 수량
C = min(I, D, E)
보정 후 숙박 추정 수량 = B + max(0, I - C)
```

각 수량은 0 이상이며 `C`는 `I`를 넘지 못한다. `D` 또는 `E`가 미확인이면 `C=0`으로 처리하고 미확인 상태를 남긴다. 이 보정은 물리적 객실 수·원문 재고·공개 예약 필드를 바꾸거나 예약 가능 수량을 늘리지 않는다. 근거 없는 차단을 기본 매출에서 제외하는 계산에서는 이미 `I=0`이므로 데이유즈를 추가로 뺄 항목도 없다.

평일은 검토 범위를 정하는 조건일 뿐 중복의 증거가 아니다. 현재 요일 구분의 평일은 월~목이고 공휴일 예외는 없으므로 운영 달력과 동일하다고 가정하지 않는다. **10월 5일 숙박 예약 필드 2, 데이유즈 예약 필드 2**는 각각 보존한다. 공유 구조만으로 숙박을 0으로 만들지 않는다.

## 4. 예상 매출과 가격 보완

```text
가격 확인 예상액 = Σ(판매/예약 관측 근거가 있는 수량 × 해당 상품·이용일의 공개 가격)
가격 미확인 수량 = 판매/예약 관측 근거가 있으나 해당 가격이 없는 수량
```

이는 공개 가격을 이용한 예상액이다. 실제 결제액·할인·환불·수수료를 확인한 매출 장부가 아니다. `actualRevenue`는 별도 결제 근거가 없으면 `null`이다.

현재 적용 버전은 가격이 없는 예약에 평균 가격을 임의로 넣지 않는다. 가격 미확인 수량만 따로 표시한다. 민트 검증 자료의 숙박 예상액은 **35,699,000원**, 당일 이용은 **297,000원**, 합계 **35,996,000원**이다. 기존 39,176,000원에서 근거 없는 숙박 8×249,000원과 당일 이용 12×99,000원, 합계 **3,180,000원**이 빠진다.

가격 보완은 수량 근거를 먼저 확정한 뒤 별도 추정액으로 표시한다. 판매 중지·미오픈·재고 부족·수집 실패는 가격 누락 판매 수량에 넣지 않는다. 근거 없는 수량을 먼저 만든 뒤 평균 가격을 곱하면 안 된다. 보완 가격은 상품·이용일 또는 명시된 동질적인 가격군의 출처를 남기고, 숙박 가격과 데이유즈 가격을 섞지 않는다. 가격 근거가 없으면 금액은 미확인으로 남긴다.

중복 차감으로 추정 수량이 줄면 그 수량에 연결된 추정 매출·가격 누락 수량도 함께 줄인다. 관측 예약에 연결된 금액을 일괄 차감하거나 총액에서 임의 평균 단가를 빼지 않는다.

민트의 기존 데이유즈 오류는 다음과 같다.

| 항목 | 기존 계산 | 적용 기준 |
|---|---:|---|
| 공개 예약 필드 관측 | 3회 | 3회 보존. 결제 확정이라는 뜻은 아님 |
| 가격이 확인된 관측 예상액 | 3×99,000=297,000원 | 공개 가격 기준 예상액으로 구분 |
| 판매 중지 4일 | 4일×3회=12회 가상 판매 | 예약 근거가 없으므로 판매·가격 보완 수량에서 제외 |
| 가상 수량의 가격 보완 | 12×99,000=1,188,000원 | 제외 |

9/26, 10/3, 10/10, 10/17은 `stock=0, bookingCount=0, occupiedBookingCount=0, price=0, open=false`로 저장되어 있다. 이 12회의 예상액을 제거하더라도 남은 전체 금액이 확정 매출이 되는 것은 아니다. 기존 숙박 159에는 공개 예약 필드 합계 151 이외에 10/17 재고 부족 추정 8개가 포함되어 있으므로 별도로 분리해야 한다.

## 5. 코드 적용 경로와 과거 자료 처리

점검 기준 코드의 경로는 다음과 같다. 함수명은 줄 번호보다 오래 유지되는 참조 기준이다.

| 경로 | 확인할 내용 |
|---|---|
| `scripts/gyeongnam_glamping_crawl.cjs`의 `classifyNaverBookingList`, `scheduleQuantityProfile` | 재고 0인 날의 상품 유형 변경이 가상 1개 판매를 만들지 않는가 |
| 같은 파일의 `collectWeeklyNaverAvailability`, `summarizeOfflineProductRevenue` | 기준 재고 부족분을 오프라인 판매·매출에 합성하지 않는가 |
| 같은 파일의 `revenueProjectionFields` | 미확인 수량에 평균 가격이 붙지 않는가 |
| `web/app.js`의 `salesStats`, `itemRevenueStats`, `projectedRevenueFields` | 목록 분모 재정규화, 과거 보완 매출 복원, 수량·금액 불일치가 없는가 |
| `scripts/glamping_app_server.cjs`의 `historySeriesForItem`, `normalizeSignalRows` | 보정된 명시 수량을 `total - available`로 다시 덮지 않는가 |
| 같은 파일의 `productSnapshotObservation`, `compactProductSnapshotDaily` | 상품 원문·날짜별 보정 수량보다 과거 `soldOut`·매출 문자열이 우선하지 않는가 |
| 같은 파일의 `applyManualBasisToSalesSummary` | 물리적 객실 수 보정이 새로운 판매를 만들지 않는가 |
| 같은 파일의 `companyRevenueSnapshotFromItem`, `compactCompanyProductSnapshot`, `companySnapshotEstimatedRevenue` | 기업 DB·추세·합계에 동일한 산출 버전과 근거가 전달되는가 |
| 같은 파일의 `buildHistoryObservations`, `companyHistoryDailyFallback` | 이력 저장·복원에서 미확인 점유를 판매로 되살리거나 업체 대표가격으로 일별 매출을 덮지 않는가 |

새 계산에는 `inventoryEvidence.version=2`와 관측 예약·미확인 점유·재고 차이·중복 차감 근거를 전달한다. 수집 원문과 과거 스냅샷은 보존하며, 현재 조회에서 원문을 재해석한 결과와 과거 저장 집계를 구분한다. 원문이 없으면 과거 합계를 새 산식의 검증된 값으로 승격하지 않는다. 재계산은 같은 입력에서 같은 결과를 내고, 이미 보정된 값에 다시 보정을 적용하지 않아야 한다.

기업 상세 조회는 과거 상품 스냅샷이 이미 있어도 산출 버전이 오래되었으면 연결된 저장 수집 결과를 읽는다. v2 계산이 가능한 회차만 응답의 회사 재고·일별 합계·매출 추세·이력에 반영하고, 근거를 `source_recalculation`(저장 원문 기준 재계산)으로 표시한다. 이 조회는 원본 CSV, 회사 DB, 과거 이력 파일에 쓰지 않는다. 새 수집 결과 조회와 기업 상세 조회는 동일한 원문에서 같은 분자·분모·금액을 계산해야 한다.

## 6. 반드시 확인할 경계 사례

1. 실제 28실·채널 21·예약 3: 실제 객실 28과 관측 재고 21을 각각 표시하고, 재고 차이 7을 판매에 더하지 않는다.
2. 데이유즈 판매 중지 4일·기준 3·예약 0·가격 0: 가상 판매 12와 가격 보완 1,188,000원이 모두 발생하지 않는다.
3. 숙박 예약 2·데이유즈 예약 2·공유 구조만 확인: 숙박 예약 2를 보존한다.
4. 숙박 예약 4·추정 차단 1·근거 있는 중복 데이유즈 3: 최대 1만 차감하며 숙박 예약 4는 보존한다.
