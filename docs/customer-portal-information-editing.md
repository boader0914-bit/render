# 인사이트 매장 정보 수정 구조

2026-09-30 사용자 요청을 반영한다. 내 매장과 경쟁업체 모두 정보 수정 진입점을 제공한다.

## 구현 상태

- 로컬 검수본: 개인 별칭·메모 저장, 매장 정보 수정 요청, 요청 변경·철회·이력, 고객 예시별 분리와 동시 수정 충돌 검사.
- 운영 연결 계약: 고객 인증·영구 저장·관리자 승인·재계산·AWS worker 결과 수신은 후속 구현 대상이다. 미리보기 API를 운영 인증 API로 사용하지 않는다.
- 기존 공개 검수 사이트에 자동 배포하거나 실제 수집을 실행하지 않는다.

2026-09-30 지침 검토 결과와 개발 순서는 [운영 연결 개발 지침](customer-portal-development-guidance-20260930.md)을 따른다. 아래의 적용 기간·전체 이력·중앙 승인 모델은 후속 구현 계약이다. 현행 데이터랩 수동 보정 API가 이미 이 계약을 모두 충족한다는 뜻이 아니다.

## 수정 범위

| 구분 | 항목 | 적용 |
| --- | --- | --- |
| 개인 설정 | 별칭, 나만의 메모 | 해당 고객 계정에 즉시 저장. 공식 매장명과 공통 지표는 유지 |
| 공통 정보 수정 요청 | 매장명, 주소, 업종, 전체 객실 수, 데이유즈 운영·객실 공유, 시설·편의정보 | 내 매장과 경쟁업체 모두 근거를 첨부하여 검수 요청 |
| 분석·식별 정보 | companyId, placeId, 예약 수량, 가격 관측, 매출, 검수 상태 | 고객 입력으로 직접 변경하지 않음. 업체 변경은 관계 교체, 관측 오류는 별도 검토 |

내 매장 등록은 소유 확인 완료와 다르다. 본인 매장 확인 상태와 정보 수정 승인 상태를 각각 관리한다. 경쟁업체의 공통 정보를 한 고객이 바꾸어 다른 고객에게 즉시 적용할 수 없다.

## 데이터랩 관리자 진입점

관리자는 **이용자(현행 회원) → 이용자 상세 → 등록 업체 → 업체 등록·정보 수정**에서 작업한다. 해당 화면과 기존 업체 DB는 동일한 `companyId`와 공통 편집·저장 기능을 사용한다. 이용자별 별칭·메모·등록 관계·검수 요청과 중앙 공통 객실 기준을 구별하며, 고객마다 별도 객실 원장을 생성하지 않는다.

공통 검수값은 그 업체를 보는 여러 고객의 미발행 분석에 영향을 줄 수 있으므로 승인 전에 대상 필드·기간·변경 전후·영향 범위를 보여준다. 고객 제출값은 기존 검수값을 자동 덮어쓰지 않는다.

## 값의 보존과 우선순위

1. 수집값은 출처·runId·관측시각·숙박일과 함께 보존한다.
2. 관리자 DB 검수값은 필드별로 값·근거·검수자·검수시각·적용기간·버전을 저장하고 최우선 적용한다.
3. 검수값이 없을 때 유효한 수집값을 사용한다. 객실 수는 기존 최대 관측 기준을 유지하며 40실 제한을 추가하지 않는다.
4. 고객 제출값은 검수 대기로 분리한다. 승인 전 예약률·공급량·매출을 바꾸지 않는다. 개인 별칭·메모는 분석 계산에 쓰지 않는다.
5. 새 AWS worker 결과는 수집 관측만 갱신한다. 검수값·고객 메모·수정 요청·변경 이력을 덮어쓰지 않는다. 수집값과 검수값이 다르면 차이를 표시한다.
6. 오류·차단·누락의 0은 정상 응답 0과 구분하며, 고객 수정으로 정상 수집 상태로 바꾸지 않는다.

## 저장 모델과 처리

- `CustomerCompanySettings(customerId, companyId, nickname, note, revision, updatedAt)`는 고객별로 저장한다.
- `CompanyCorrectionRequest(requestId, customerId, companyId, relationship, baseCompanyRevision, baseValues, proposed, reason, status, submittedAt, closedAt)`는 변경 전후와 근거를 보존한다.
- `CompanyReviewedOverride(companyId, field, value, reason, effectiveStayFrom, effectiveStayTo, revision, reviewerId, reviewedAt, sourceRequestId)`는 중앙 DB 검수값으로 별도 저장한다.
- 승인 시 회사 기준 버전과 요청 기준 버전을 다시 비교한다. 수집 또는 다른 검수가 그 사이 기준을 바꾸었으면 현재값과 제출값을 비교하도록 하고 자동 승인하지 않는다.
- 요청 상태는 검수 대기 → 승인/반려/철회 또는 새 요청으로 대체이다. 기존 요청을 삭제하거나 과거 근거를 새 값으로 덮어쓰지 않는다. 같은 내용을 저장하면 중복 요청을 만들지 않는다.
- 경쟁업체 해제·내 매장 교체 후에도 수정 이력은 보관한다. 이전 업체의 보정·메모를 새 업체로 복사하지 않는다.
- 실제 물리적 객실 증감은 적용 숙박일을 지정한다. 과거 수집 오류의 보정은 관리자가 영향 기간과 예약·매출 변화를 미리 확인한 뒤 재계산한다. 가격 관측이나 객실 수 수정은 예약 결제를 확정하는 행위가 아니다.
- 미발행 분석은 검수 버전으로 재계산하고, 이미 발행된 리포트는 원본을 보존하여 필요할 때 수정본을 새 버전으로 발행한다.
- 현행 수동 보정의 객실 유형 8개 절삭과 최근 이력 30건 보관을 새 계약에 그대로 가져오지 않는다. 전체 이력 저장소를 추가하고 객실 유형 입력을 누락 없이 보존한다. 일부 필드 수정 시 기존 상품 보정·가격 기준·객실 유형 등 미제출 필드를 유지한다.
- 승인 상태 저장, 중앙 DB 반영, 재계산 완료는 별도 단계로 관리한다. 고유 변경 ID로 재시작 후 처리 상태를 복구하며 같은 보정이 중복 적용되지 않도록 한다.

## 신규 운영 API 계약

다음 경로는 설계이며 현재 예시 API와 다르다.

| 경로 | 역할 |
| --- | --- |
| `PATCH /api/customer/v1/companies/:companyId/settings` | 개인 별칭·메모 저장 |
| `GET /api/customer/v1/companies/:companyId/corrections` | 본인이 제출한 요청·상태·검수 결과 조회 |
| `POST /api/customer/v1/companies/:companyId/corrections` | 필드별 수정 요청 등록·대체 |
| `POST /api/customer/v1/corrections/:requestId/withdraw` | 본인의 대기 요청 철회 |
| `POST /api/admin/company-corrections/:requestId/review` | 관리자 승인·반려 및 적용 기간·재계산 범위 지정 |

고객 신원은 서버 세션에서 결정하며 본인 등록 관계·현재 권한을 검사한다. 타인의 메모·수정 요청·검수자 개인정보·내부 메모는 반환하지 않는다. 수정은 revision 및 중복 방지 키로 보호하고 허용 필드 외 입력은 거절한다. 요청 ID를 알아도 다른 고객의 요청을 수정하거나 조회할 수 없어야 한다.

업체 검색·수집 연결은 `인사이트 고객 API → 데이터랩 작업 배정 → AWS worker → 중앙 DB → 허용된 고객 조회` 경로로 구현한다. 워커 자격증명을 고객 브라우저에 전달하지 않는다. 정보 수정·조회·리포트 열기는 수집 실행을 유발하지 않는다. 실제 정보 갱신 요청은 별도 작업으로 중복 여부·범위·실패 사유를 관리한다.

## 검수 UI

- 내 매장 카드와 경쟁업체 카드의 **정보 수정**에서 같은 화면을 사용한다.
- 위쪽에는 개인 설정, 아래에는 현재 기준과 수정 요청 값을 나란히 확인할 수 있는 입력란을 둔다.
- 데이유즈는 확인 전 / 없음 / 별도 객실 / 숙박과 공유를 구분한다.
- 검수 대기 배지와 변경 전후·사유·시각·상태를 표시한다. 원래 값으로 돌려 저장하면 대기 요청을 철회한다.
- 향후 운영 화면에는 수집값·검수값·적용값·마지막 수집일을 함께 표시하며 관리자 승인 기능은 데이터랩에 둔다.

검증은 개인 설정과 공통값 분리, 다른 고객 및 미등록 대상 차단, 중복·오래된 수정 거절, 요청 대체·철회 이력, 리포트 불변, 40실 초과 요청, HTTP 저장·재조회에 집중한다. 실제 고객 인증과 AWS worker 연동 검증이 완료됐다는 의미는 아니다.
