# 배경 집계의 메모리와 수집 후처리 검수

## 구현

- 업체 기본자료는 회사 한 개씩 JSON을 검증하며 읽는다. 업체 계산에 다른 업체의 전체 관측행을 보관하지 않고, 읽기 전용 객실 근거는 같은 계산 안에서 공유한다. 객실수·품질·제외 기준은 유지한다.
- 업체의 월별 계산, 월간 리포트, 업종 계산, 수집 DB 후처리는 하나의 공통 실행권을 쓴다. 실행권은 원본 조회부터 계산·저장 완료까지 유지한다. 업체 배경 계산은 월 경계에서 실행권을 반납한다.
- 수집 후처리를 우선하며 실행권을 받은 뒤 쓰기 잠금을 취득한다. 대기 중 수집 완료 상태와 보관함 연결은 유지한다. 실행 대기 시간은 `analyticalWaitMs`로 실제 DB 실행시간과 구분한다.
- 작업 대기열은 호출 시점의 워커 컨텍스트를 복원한다. 배경 작업의 비동기 시작은 이전 작업의 실행권을 이어받지 않는다. 공유 카탈로그의 재구성 작업도 실행권 취득 후 생성해 교착을 방지한다.
- 저장된 업체 카드·보관함·정상 집계 조회는 무거운 작업의 대기열을 거치지 않는다. 미완료·원본 오류·변경 중인 계산은 마지막 정상 결과를 덮어쓰지 않는다. 화면의 선택 월은 변경하지 않는다.
- 업종 완료 원본 캐시는 기본 8MiB로 제한한다. 큰 원본은 계산 후 해제하므로 다음 계산에서 재조회할 수 있다.
- 배경 작업의 시작 전 메모리를 검사한다. 실행 중 강제 GC, 메모리 제한 변경, 피크 초기화는 하지 않는다. 높은 사용량 또는 검사 오류는 배경 작업만 대기시키고 저장 조회는 허용한다. 낮은 사용량을 두 번 확인하면 재개한다.
- 관리자 읽기 전용 `GET /api/analytical-work`로 대기 사유·실행 종류·메모리 검사값을 확인한다. 메모리 비율은 배경 작업 허용을 위한 추정치다. 파일 캐시를 포함한 cgroup 전체 사용량·익명 메모리·프로세스 RSS와 구분해 검수한다. 단일 작업의 추가 할당이 안전하다고 보장하는 값은 아니다.

## 로컬 검증과 한계

### 실행 중인 업종 집계의 조회 양보

운영 서버의 `cooperativeYield`는 배경 `industry-build`에만 적용한다. 업체 조회가 기다리면 저장 원본 체크포인트에서 현재 시도를 중단하고, 스트림·내부 읽기 슬롯·큰 자료 참조를 정리한 뒤 공통 실행권을 반환한다. 호출자는 같은 완료 대기를 유지하며 업종 작업은 `failed`가 아닌 `yielded`로 기록하고 다시 대기열에 들어간다. 메모리를 보유한 채 두 계산을 병행하지 않는다. 상품 근거 발행은 중간 양보를 허용하지 않는다.

업종용 `recalculated_run_rows/industry_rows`는 업체 캐시와 별도로 최대 512개·64MiB의 완료된 수집 단위만 보관한다. 원본 변경값·업체 범위·관측 당시 객실 근거·체크섬을 다시 확인하며, 중단된 단위는 정상 값으로 발행하지 않는다. 단일 단위가 6MiB를 넘거나 전체 예산을 넘으면 기존 원본 계산으로 복귀할 수 있다. 원본·발행 리포트는 이 캐시가 아니다.

재시도는 단계·수집 단위·단위 내부 체크포인트 순서로 진행값을 전진시켜 같은 지점에서 무한히 양보하지 않게 한다. 콜드 카탈로그나 수집 단위가 캐시로 재사용되어 체크포인트 수가 줄어도 다음 단계·수집 단위의 진행을 인정한다. `GET /api/analytical-work`의 `cooperative`, `timing.yielded`, `timing.restarted`, `timing.maximumCheckpointGapMs`와 `monthlyRecalculation.industryRunRowBuilds/industryRunRowCacheHits`를 사용해 실제 조회 대기와 재계산을 구분한다. 250ms 최소 실행 간격은 응답시간 보장이 아니며, 체크포인트 사이의 동기 작업·발행·메모리 검사 대기는 남을 수 있다.

`npm run test:background-memory`는 동시 작업·메모리 대기·호출자 워커 유지·교착 방지·카드 수치와 월 유지·오류 시 정상 결과 보존·원본 불변을 확인한다. 실제 HTTP 검증도 포함한다.

`npm run benchmark:background-memory -- --output <별도 JSON 경로>`는 539개 업체, 약 115MB 기본자료, 세 달의 모의 관측으로 이전 `3f49cc6` 원본 어댑터와 개선 어댑터를 각각 별도 프로세스에서 비교한다. 전체 이전 서버나 실제 예약 실행 비교는 아니다.

2026-10-21 첫 로컬 시험에서 최고 RSS는 970.809MiB → 472.820MiB, 계산시간은 2468.691ms → 5767.739ms였다. 월별 산출물·범위별 품질 및 제외 결과는 같고 원본 내용·수정시각은 유지됐다. 메모리 감소와 읽기·계산시간 증가를 함께 기록한다. 이 결과를 운영 DB 처리시간이나 화면 2초 목표 달성으로 표현하지 않는다.

## 다음 정상 예약의 운영 검수

배포 커밋·Render Live·공개 health가 일치해야 검수한다. 기존 일정에서 실행되는 첫 정상 예약의 정확한 slotId/runId를 기준으로 수집 품질, 보관함·예약/통합 이력 연결, DB 후처리 완료, 관측행의 실제 개수와 중복 없는 ID를 확인한다. 수집 종료→완료 표시, 분석 실행권 대기, DB 이력 실행, 수집 종료→DB 완료를 각각 보고한다.

수집 전부터 DB 완료까지 동일 인스턴스의 RSS/HWM, cgroup current·anon·file·OOM 카운터를 낮은 빈도로 기록한다. 프로세스나 인스턴스가 바뀌면 연속 관측으로 표현하지 않는다. 웹 종료시각은 웹 상태·게시 시각 근거이며 BG의 독립 broker 종료 영수증과 구분한다.

새 수집·재수집·예약 변경·보호 해제·원본/객실수 수정 없이 검수한다. `GET /api/runs/{id}`의 재가공 경로 대신 보관함 목록과 순수 읽기 전용 이력 조회를 사용한다. 기존 정상 수집 결과는 개선 버전의 실제 처리속도 증거로 재사용하지 않는다.
