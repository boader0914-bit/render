# Insight 로그인 확인 지연 개선

## 원인

기존 로그인·`/me`·관리자 고객화면 시작 응답은 업체 목록을 만들 때
`monthlyReportSources.catalog`를 호출했다. 이 경로는 전체 업체 파일과 실행 목록을
읽고 객실 기준을 준비하며, 월간 분석과 같은 단일 분석 작업권을 기다린다.
따라서 실행 중인 분석이 길어지면 로그인 확인도 대기하고 Insight 중계 서버의
20초 제한에 도달할 수 있었다. 수집 완료 여부를 확인하는 작업도 같은 응답에서
기다렸다. HTTP 503만으로 네이버 접근 제한이나 비밀번호 오류를 뜻하지 않는다.

2026-10-23 개선 전 운영 측정에서는 로그인 확인에 6.565초가 걸렸으며,
앞선 검수에서는 20.128초 후 중계 서버 시간 초과도 관측했다.
운영 분석 진단에는 실행 중인 `company-month` 작업과
`verified-company-catalog`의 작업권 대기 및 실행 시간이 기록되어 있었다.

## 변경

- `insight_catalog.cjs`는 로그인·업체 검색에 필요한 공개 기본정보만 별도 구성한다.
  실행 목록, 예약 상세, 관측 이력, 객실 재산출, 분석 작업권을 사용하지 않는다.
- 업체 원본, 지역 기준, 고정 객실 기준 파일의 상태를 매번 확인한다.
  세 파일이 같으면 메모리 또는 체크섬이 있는 저장 결과를 재사용한다.
  변경 시 업체를 한 곳씩 읽어 공개 필드만 남기며, 동시 요청은 같은 준비를 공유한다.
- 현재 DB 검수 객실값을 우선한다. 검수값이 없으면 저장된
  `observed_locked` 기준만 사용한다. 이전 `db_review` 값을 현재 검수로 승계하지 않는다.
  기준이 없으면 객실 수를 미확인으로 남기며 상세 조회의 기존 계산 경로에서 준비한다.
- 시군구는 업체 DB의 지역 보정, 명확한 주소, 지역 기준표를 사용한다.
  같은 이름의 다른 시군구나 잘못된 명시 보정값을 추측해 연결하지 않는다.
- 로그인 상태의 수집 결과 확인은 응답 후 공유 작업으로 수행한다.
  완료 검증 전에는 마지막으로 확인한 상태만 표시한다.
  실제 업체 결과 조회와 수집 명령의 검증·작업 배정은 기존 경로를 유지한다.
- 세션, 회원 이용 상태와 현재 등록 관계는 매 요청 및 상태 응답 직전에 검증한다.
  인증 성공을 일정 시간 저장해 재사용하지 않는다.

로그인용 저장 결과는 `DATA_DIR/insight_catalog/catalog.json`에 있으며 원본 자료와
독립된 파생 자료다. 원본 삭제·손상·읽기 실패나 연속 변경 시 마지막 성공값을
최신 자료인 것처럼 반환하지 않는다. 소스 규칙 또는 검수 콜백이 바뀌어도 재생성한다.

Render/운영 환경은 이 경량 조회를 기본 사용한다. 로컬 주입 어댑터의 기존 계약은
유지하며 `INSIGHT_METADATA_READ_ENABLED=1`로 같은 경로를 검증할 수 있다.
긴급 비교가 필요하면 `0`으로 기존 조회 경로를 선택할 수 있으나, 원래 지연도 돌아온다.
이 설정은 수집 일정이나 수집기의 선택을 바꾸지 않는다.

앱 본체와 월간 계산 코드를 수정하지 않아 무관한 월간 집계의 코드 해시를
변경하거나 전체 집계를 강제로 무효화하지 않는다.

## 계측과 검수

중앙 상태 응답의 `Server-Timing`에는 `state_catalog`, `state_total`만 숫자로 표시한다.
Insight 중계 서버는 `upstream_headers`, `upstream_body`, `snapshot`, `total`과
허용한 중앙 시간만 전달한다. 계정·업체·토큰·쿠키·쿼리·원문 오류는 헤더에 넣지 않는다.
중계 시간 초과는 `504 UPSTREAM_TIMEOUT`과 로그인 확인/자료 조회 단계로 구분하며,
실제 401·403 응답과 세션 정책은 유지한다. POST 요청은 자동 재시도하지 않는다.

검수는 외부 수집 없이 다음을 확인한다.

1. 긴 분석 작업권을 잡아도 최초·동시·재시작 후 로그인 기본자료 조회가 끝난다.
2. 검수 객실·소재지 변경, 삭제·병합, 원본 손상과 읽기 중 변경을 구별한다.
3. 느린 읽기 도중 세션 해제·회원 중지·등록 해제 결과가 최종 응답에 반영된다.
4. 완료 확인이 지연되어도 로그인은 끝나며, 업체 결과 조회는 검증 완료를 기다린다.
5. 운영 동일 계정에서 새로고침의 로그인 응답 시간과 실제 A·B·C 연결을 확인한다.

운영 `/api/analytical-work`는 관리자 인증으로 대기열·카탈로그 읽기 횟수를 확인하는
읽기 전용 진단이다. 진단을 위해 수집을 실행하거나 원본을 삭제하지 않는다.
최종 배포 커밋과 운영 전후 실측은 별도 배포 검수 기록에 보관한다.

## 저장된 업체·월 자료 먼저 표시

`GET /api/insight/v1/companies/:companyId/collection?month=YYYY-MM&savedOnly=1`
은 해당 업체·월의 저장된 정상 계산 파일 한 개를 검증해 반환한다. 관리자 고객보기는
같은 경로 앞에 `/admin/customer-view`를 사용한다. 월은 명시해야 하며 중복 쿼리,
다른 플래그, `savedOnly=0` 등은 허용하지 않는다. 일반 조회의 계산 경로는 유지한다.

지원 계산 버전은 v1, v2, v3와 현재 `company-integrated-v4-product-max-room-reuse`의
정확한 이름만이다. v4도 파일 체크섬·업체·월·관측 범위·수량을 검증한 뒤 기존
고객용 필드 투영을 사용한다. 저장된 가격 보완 근거와 가격 미확인을 그대로 유지하고,
관측 공백을 0으로 만들지 않는다. 현재 검수 객실 기준이 달라졌으면 이전 수량을
새 기준의 결과처럼 표시하지 않는다.

이 경로에서는 수집 실행·수집 영수증 갱신·상품 원문·전체 업체 상세·관측 이력·분석
작업권·재계산을 호출하지 않는다. 파일을 읽기 전과 반환 직전에 로그인·회원 이용 상태와
현재 등록 관계를 검증한다. 저장 결과가 없거나 검증되지 않으면 다른 업체나 월로
대체하지 않는다. 응답의 `calculation.mode=saved_only`, `responseCache.state=preview`,
`preview=true`는 최신 재검증 전의 표시임을 뜻한다. 이 응답만으로 최신 확인 완료 또는
신규 검수 보관본으로 기록하지 않는다.

상품·예약채널은 이 월간 파일에 포함되어 있지 않다. 그래서 `referenceLoading=true`로
추가 연결이 필요함을 표시하고 권위 있는 빈 목록을 만들지 않는다. 같은 로그인 범위에서
이미 조회한 A·B 자료는 화면에서 유지할 수 있지만, 다른 월의 C 예약·매출을 선택한
월의 자료로 사용해서는 안 된다.

신원 응답에서 공개 목록 또는 최종 회원 확인이 1초 이상 걸리면 `insight_identity`
로그에 단계·소요 시간·완료 여부와 무작위 추적 번호만 남긴다. 계정·업체 번호,
토큰·쿠키·원본 오류는 기록하지 않는다. 이 진단은 인증 결과를 재사용하거나
20초 제한을 늘리지 않으며, 향후 지연의 발생 구간을 구분하는 보조 자료다.
