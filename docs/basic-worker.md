# 기본워커: 운영 웹서버 직접 수집

관리자 수집 화면의 `실행할 수집기`에 `기본워커 · 운영 웹서버`를 추가한다. 기존 0922 수동워커와 0923 예약워커도 그대로 선택할 수 있다. 처음 선택값은 기존 수동워커를 유지하고, 예약 설정은 예약워커 전용이다. Render의 웹 서비스 이름이나 실행 모드는 바꾸지 않는다.

## 실행과 속도

- `workerKey=web`을 명시한 요청만 운영 웹서버에서 직접 실행한다. 다른 수집기의 연결 실패를 이유로 웹서버로 자동 전환하지 않는다.
- 웹서버는 수집 작업을 한 번에 하나씩 처리한다. 같은 작업 안에서는 기존 수집 코드의 기본 동시 처리 수를 사용한다.
- 이번 점검에 임시 적용했던 전역 최소 200ms 간격과 HTTP 동시 1개 제한을 적용하지 않는다. 과거 속도 설정 환경변수가 상속되지 않도록 제거한다. 기본값은 업체 상세 2개, 예약 일정 4개, OTA 2개이며, 이는 전체 HTTP 동시 요청 수를 뜻하지 않는다.
- 403, 429, HTTP 200의 요청량 제한, 실제 캡차 요구 응답은 감지한다. 일반 페이지에 포함된 캡차 라이브러리 참조만으로 중단하지 않는다. 차단 감지 이후 새 네이버 요청을 중단하며 이미 전송한 요청을 회수했다고 간주하지 않는다.
- 어느 수집기에서든 접근 제한을 감지하면 기존 공통 보호를 세 수집기에 적용한다. 속도 복원은 보호 해제를 뜻하지 않는다.

## 결과와 중복 방지

웹 실행도 기존 비동기 접수 기록, 진행 상태, 당일 중복 확인을 거친다. 다른 수집기가 같은 조건의 자료를 이미 정상 수집했으면 재사용하며, 실패 또는 조건 차이가 있으면 기존 재수집 검토 절차를 유지한다.

`webCollection=true`, `workerKey=web`, `executionHost.role=operating_web`, `collectorEngine=operating-web-v2`와 작업별 고유 번호를 결과에 기록한다. 개별 작업의 임시 보관 위치에서 날짜·조건·파일·상품별 응답을 검증한 후 결과를 게시한다. 부분·실패·차단 자료는 정상 매출 이력이나 업체 DB에 반영하지 않는다. 웹서버 재시작으로 미확정된 작업은 자동 재실행하지 않는다.

## API

- `POST /api/crawl?async=1`: `workerKey:"web"` 선택, 기존 관리자 인증과 요청 번호 사용.
- `GET /api/collector-status`: 세 수집기의 상태. 기본워커는 외부 워커의 연결 신호를 기다리지 않고 웹서버 자체 상태를 표시한다.
- `GET /api/crawl-status?workerKey=web`: 기본워커의 진행·대기 상태.
- `GET /api/crawl-requests`: 기본워커를 포함한 접수·완료·실패 기록.

이번 개발은 자동수집 일정 활성화, 실제 네이버 재수집, Render 요금제 또는 서비스 이름 변경을 포함하지 않는다. 운영 반영 여부는 배포 기록과 운영 빌드 번호로 별도 확인한다.

## 검수

`npm run test:operating-web`은 실제 앱 서버와 모의 수집 자식으로 기본워커 선택, 기본속도 환경, 단일 작업 실행, 세 수집기 사이의 당일 재사용, 양방향 차단 전파, 부분 결과 반영 방지, 요청 기록의 재시작 복원을 검사한다. 테스트의 외부 HTTP와 실제 수집기 실행은 차단한다. 기존 원격 수집기 및 예약 통합검사도 함께 실행한다.
