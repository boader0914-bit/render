# 월별 키워드 상세 조회 안정화 두 번째 묶음

2026-11-15 개발. 운영 기준 커밋 `aed4990eac12a2b55fbb5b5bef2bc6bea476a6c7`에서 별도 작업했다. 이 문서는 개발 검증이며 운영 배포·자료 전환 완료를 뜻하지 않는다.

## 변경 목적

목록보다 느린 상세 조회에서 같은 원본 검증·현재월/이전월 계산을 반복하던 비용을 줄이고, 새로고침 후 마지막 적용 조건을 복원한다. 접속 종료·시간초과 때 요청자만 정리하고 공유 계산이나 영속 게시 작업을 중복 실행하지 않는다. 계산식·객실 검수값·수집 속도·보호·예약 설정은 변경하지 않는다.

## 저장 결과 게시와 조회

- 명시적 빌드의 `--prepare-results 1`, 기존 증분 갱신 및 완료 수집의 게시 경로에서 최종 상세 응답을 준비한다. GET은 수집·게시·강제 재계산을 시작하지 않는다.
- schema2 catalog는 최종 결과의 파일·바이트 수·SHA, 정확한 키워드/숙박월/마감일, 원본 projection과 계산 코드 지문을 연결한다. 계산 코드 지문은 줄바꿈을 정규화하므로 Git LF와 Windows CRLF 차이는 무시한다.
- 게시 포인터를 바꾸기 전에 결과를 한 건씩 계산·검증·저장한다. 마지막 안전 구간의 intent는 실제 schema2 catalog SHA와 별도의 기존 scope plan SHA를 함께 고정한다. 실패 시 이전 포인터와 정상 결과가 유지된다.
- 준비된 GET은 포인터/catalog/index/결과 파일의 무결성과 계산 지문을 확인하고 최종 결과를 읽는다. 현재월·조회시점 관련 상태만 다시 판정한다. 읽는 동안 결과나 포인터가 바뀌면 채택하지 않는다.
- 매 GET에서 원본 projection 전체를 다시 읽지는 않는다. `sourceRevalidated:false`, `originalFreshnessVerified:false`를 유지한다. 저장 결과 조회 성공과 최신 원본 반영 완료는 별도 증거다.
- schema1은 호환 읽기를 유지한다. 해당 조건의 준비 결과가 진짜 없는 경우 기존 계산 경로로 읽지만, 손상·계산 지문 불일치는 조용히 재계산하여 덮지 않고 확인 필요로 반환한다.
- 기존 운영 세대는 자동 변환하지 않았다. 배포만으로 기존 세대의 모든 상세 조회가 빨라지는 것은 아니다. 전환은 승인된 별도 게시 절차와 실제 보존 검증이 필요하다.
- 증분 게시도 노출되는 모든 조건의 최종 결과를 준비한다. 기존 경로도 전체 조건을 분석해 검증했으므로 추가 전체 계산을 한 번 더 겹치지는 않지만, 준비 시간·세대 저장 용량은 운영 자료로 따로 측정해야 한다.

## 조회 조건 복원

`sessionStorage`에 마지막 **적용한** 키워드·월·관측 마감·상품·업체·목록 검색/페이지·모바일 보기·펼침 상태만 최대 12KiB 저장한다. 결과 자료·인증값·비밀번호는 저장하지 않는다. 현재 로그인 계정/역할/로그인 생성시각의 불투명 지문과 만료를 확인하고 같은 로그인에서만 복원한다. 다른 계정·새 로그인·만료·고객 보기·401/403·로그아웃에서는 이전 조건을 폐기한다. URL 등 명시적 진입 조건이 우선한다. 옵션에 없는 업체를 다른 업체로 몰래 바꾸지 않는다.

`loadSession()`에서 configure를 기다린 뒤 화면을 연다. 암호화/저장소가 막히거나 지연되면 복원만 끄고 로그인과 조회는 진행한다.
