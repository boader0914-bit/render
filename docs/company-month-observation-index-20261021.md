# 업체·월별 관측 색인과 변경분 갱신

2026-10-21 개발. 운영 배포 및 운영 실제 자료 검수는 별도 단계다.

## 처리 원칙

- `history/observations.jsonl`은 원본이다. 기존 행을 수정·삭제·정렬하지 않는다. 정상 수집의 새 관측만 기존 공유 쓰기 잠금 안에서 추가한다.
- `history/indexes/observations.sqlite`는 재구축 가능한 파생 자료다. 원래 물리행 순서, 원시 업체 ID·병합 참조·플레이스, 월, 실행 ID, 행 본문과 자료형을 구분한 관측 ID를 저장한다.
- 월간 집계는 기존의 업체·실행·상품유형·숙박일 마지막 행 우선 규칙을 유지한다. 정상 0과 미관측·부분·실패·잘못된 날짜를 구분하며, 전역 진단도 유지한다. 원시 이름으로 업체를 새로 합치지 않는다.
- 업체 ID·병합·플레이스 소유권은 조회 시 현재 마스터로 해석한다. 무관한 업체나 미래 키워드 추가는 과거 월을 무효화하지 않는다. 연결 충돌·미식별·손상 진단이 실제로 달라지는 경우는 필요한 범위를 다시 검사한다.

## 저장 및 조회

| 사용 경로 | 변경 후 처리 |
|---|---|
| 수집 관측 중복 확인 | 후보 ID의 색인 조회. 숫자와 문자열을 구분 |
| 업체·월 집계 입력 | 해당 월·업체 참조의 본문만 읽고, 전체 월의 진단은 파티션별 식별자·행 수로 확인 |
| 업종·지역·키워드 입력 | 요청한 월의 관측만 읽음 |
| 업체·월 변경 검사 | 저장된 원시 업체·월 파티션의 변경 토큰 사용. 추가된 행이 속한 파티션만 다시 해시 |
| 선택 가능한 월·업체 | 색인의 월 목록과 작은 식별 헤더 재사용 |
| 과거 객실 관측 최대치 | 원시 파티션별 검증 수량을 별도 저장. 변경 파티션만 다시 읽고 현재 실행 품질·병합을 적용 |
| 월별 정상 집계 | 변경 검사와 실제 입력·현재 계산 결과가 모두 같으면 원래 파일·수정시각·계산시각 보존 |

객실 기준 보조 색인은 `company_integrated/capacity-history-index.json`에 저장한다. 원본 관측과 관리자 확정 객실수는 수정하지 않는다. 변경된 실행 품질, 실패·부분 응답, 증거 버전 누락을 정상 객실 최대치로 바꾸지 않는다.

새 수집은 원본의 기존 식별값을 확인하고 추가분을 쓰고 `fsync`·닫기까지 성공한 뒤 꼬리와 변경 파티션을 갱신한다. 원본 저장이 불확실하면 명시적으로 실패한다. 저장 완료 후 파생 색인만 실패하면 원본을 다시 추가하지 않고 다음 검증에서 복구한다. 프로세스 중단·외부 추가·앞부분 수정·축소·파일 교체는 검증된 전체 스트리밍 재구축으로 처리한다. 파일 크기 증가만으로 추가분이라고 가정하지 않는다.

재구축은 SQLite 트랜잭션으로 공개한다. 실패하면 이전 정상 파생 자료와 월별 결과를 보존하며, 오래된 색인으로 정상 0건이나 최신 집계 재사용을 인증하지 않는다. SQLite·헤더·파티션 손상, 원본 소실, 읽는 중 변경은 오류로 구분한다.

## 기존 월별 결과의 보존

코드·색인 방식 전환 시 최초 한 번 입력을 재검증한다. 이전 캐시 무결성과 계산 버전·기준일·마감 상태·객실 검토값을 확인하고, 입력 해시가 같아도 **현재 엔진으로 계산한 전체 결과**가 기존과 같아야 재사용한다. 계산시각·발행 표시를 제외한 수치·품질·비교·근거·제외 사유가 달라지면 정상 갱신한다.

동일 결과는 `<month>.reuse-proof.json`에 현재 변경 토큰과 기존 파일 해시를 연결한다. 원래 월 파일과 계산시각은 유지된다. 새 변경 검사와 작업 세대 확인 후에만 근거를 공개한다. 근거가 손상되거나 다른 월·업체·파일을 가리키면 다시 검증한다. 계산 버전명을 바꾸지 않은 수치·품질·비교 로직 변경도 이전 결과를 무조건 재사용하지 않는다.

## 검증

관련 단위·연결 시험에서 다음을 확인한다.

- JSONL과 색인의 동일 수치·순서·BOM·잘못된 행·병합·플레이스 충돌·전역 진단
- 신규 업체·키워드·미래 월 추가, 특정 9월 변경과 10월 비교 의존, 타 업체 불변
- 재시작 시 원본 본문 재조회 없이 색인·객실 최대치·집계 재사용
- 실패·변경 경합·손상·미종결 꼬리·CR/LF·동시 쓰기·저장 불확실성 처리
- 변경 없는 월 파일의 내용·수정시각·계산시각 보존
- 상세 응답 도착 시 선택 월·통합카드·선택 상태를 보존하는 기존 화면 회귀 시험
- 네트워크와 수집 실행을 차단한 로컬 서버에서 20업체·21일·420관측 처리, 보관함·예약 이력 연결, 원본 보존

주요 단위·연결 시험 156개, 배경 작업·상세 표시 관련 회귀 시험 70개와 전체 `check` 81명령을 확인했다. 로컬 HTTP의 업체 통합·재시작·수집 후처리·월간 리포트·업종분석·읽기 전용 진단도 통과했다. 20업체 후처리 시험의 이력 단계는 448ms, 보관함 GET은 13.5·25.5ms였다. 모두 모의 자료 결과다.

별도 월간 리포트 시험에서 최초 준비는 2,603.5ms였고, 그중 작업 대기는 2,541.9ms, 당월·전월 자료 조회는 10.3·11.2ms였다. 저장 결과 재사용은 13.9ms였다. 따라서 이번 색인 시험만으로 앱 전체의 최초 표시 2초 달성을 선언하지 않는다. 최초 준비 대기와 실제 운영 화면은 별도 검수 대상이다.

## 남는 비용과 운영 적용

- 최초 파생 색인 구축과 외부 원본 교체 시 재구축은 전체 원본을 한 번 읽는다. 재시작의 SQLite 무결성 확인도 누적 크기에 따라 증가한다.
- 변경된 업체·월 파티션 내부는 재해시한다. 대상 월 발견, 실행 품질·현재 업체 연결, 전역 진단에는 작은 헤더·파티션 목록 확인이 남는다. 모든 작업이 추가 행 수에만 비례한다고 주장하지 않는다.
- 전체 마스터 읽기·저장 및 결과 파일 목록 검사, 기존 별도 상세 reader의 전역 ID 중복 처리는 이번 색인 경로와 구분한다. 상세 reader에 업체 참조 필터를 바로 적용하면 다른 업체의 동일 ID 행이 앞선 관측을 지우는 규칙이 깨지므로 그렇게 바꾸지 않았다.
- SQLite 파생 파일과 재구축 저널·임시 공간이 필요하다. 모의 15만 행에서 파생 DB는 약 200MiB였다. 운영 배포 전 실제 디스크 여유와 실행 중 수집 여부를 확인해야 한다. 원본 삭제로 공간을 만들지 않는다.
- 기존 수집·예약·보호·운영 배포는 변경하지 않았다. 다음 단계는 배포 전 보존 기준을 기록하고, 승인된 운영 배포 후 최초 전환·재시작·정상 예약수집에서 단계별 시간, 메모리, 원본 재조회량과 실제 화면 2초 목표를 확인하는 것이다.
- 관리자 전용 `GET /api/analytical-work`의 `observationIndex`는 세대·행 수·원본 바이트·구축/추가분/조회 카운터만 반환한다. 이 조회 자체가 색인을 만들거나 원본을 읽지 않는다.

실행 명령: `npm run test:history-observation-index`, `npm run benchmark:history-observation-index`.
