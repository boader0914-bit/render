# 구형 상품 원본으로 업체·숙박일 복구

관리자 `POST /api/company-master/recover-saved-products`는 저장된 상품 응답을 다시 검증하는 경로다. 외부 조회나 수집 프로세스를 시작하지 않는다. 입력은 `confirm: recover-saved-products`, `month: YYYY-MM`, `companyIds` 1~10개만 허용한다.

- 기존 수집 상태가 `unknown`인 회차만 검토한다. `blocked/failed/interrupted` 회차를 정상으로 전환하지 않는다.
- 업체명 대신 Place ID와 예약사업자 ID의 유일한 연결을 확인한다.
- manifest의 기록된 시각, CSV의 전체 상품 개수, 상품별 날짜·유형·재고·공개예약·운영중지·오류 표시를 대조한다. 파일 수정시각으로 관측 시점을 추정하지 않는다.
- 데이유즈 상품이 있으면 날짜별 응답도 함께 확인한다. 실패·누락 날짜의 가격이나 최대 재고를 다른 정상 날짜의 보정에 사용하지 않는다.
- 현행 객실 DB 보정과 재고 산식을 재사용한다. 수집 후 숙박일, 마감일 이후 관측, 모수 충돌과 가격 누락은 기존 월간 검증을 그대로 적용한다.

검증 근거는 `history/saved_product_recoveries/<업체 해시>/<숙박월>/<영수증 해시>.json`에 별도로 보관한다. 영수증은 원본 manifest·CSV·JSON의 SHA-256, 원래 수집시각과 품질, 검증된 날짜를 기록한다. 같은 원본에 대한 반복 복구는 같은 영수증을 반환한다. 원본 history·SQLite 색인·manifest·CSV·상품 JSON·업체 검수값은 수정하지 않는다.

월간 소스는 매번 영수증과 원본 해시를 검사하고 현재 객실 보정값으로 재계산한다. 회사·회차·숙박일·상품유형·시각·행 해시가 맞는 관측만 별도 증명 경로로 합산한다. 원 회차의 품질과 키워드 순위는 그대로 남긴다. 원문이 변경되거나 영수증이 손상되면 갱신을 실패 처리하여 마지막 정상 집계를 보존한다.

회사·월별 변경 감지에 복구 영수증과 원본 회차를 연결한다. 인사이트에는 원본 경로나 상품 원문 대신 업체번호·회차번호·복구 영수증과 증거 해시만 전달하며, 발행본은 수정하지 않고 새 검수본·발행본을 추가한다.

검증: `test_saved_product_recovery.cjs`, `test_saved_product_recovery_server.cjs`, `test_company_integrated_api.cjs` 및 월간 소스·변경 감지·인사이트 보관 회귀검증.

## 복구한 월의 즉시 운영 반영

대규모 과거 자료 복구가 기존 전체 월 재계산 대기열 뒤에 있는 경우, 관리자 `POST /api/company-master/refresh-saved-products`로 지정한 월만 먼저 영속 저장할 수 있다. 입력은 `confirm: refresh-saved-products`, `month: YYYY-MM`, 활성 `companyIds` 1~10개다. 해당 업체·월에 저장된 복구 영수증이 없으면 `skipped/SAVED_RECOVERY_NOT_FOUND`를 반환한다. 업체별 실패는 안전한 오류코드로 분리하고 나머지 업체를 계속 처리한다.

각 업체의 자료를 공유 계산 스케줄러의 foreground 슬롯에서 순차적으로 읽고, 기존 복구 영수증·원본 SHA·현행 검수값·월간 산식으로 다시 검증한다. 결과가 재사용 가능한 경우에도 명시 반영에서는 원본 검증을 생략하지 않는다. 계산 전후 원본 revision 또는 대기열 generation이 바뀌면 게시하지 않는다. 저장 실패 시 이전 정상 월 집계를 유지한다. 외부 수집은 실행하지 않는다.

성공한 개별 결과의 `status: ready`는 지정 월의 저장 완료를 뜻하며, `backgroundStatus`는 기존 전체 작업의 상태다. 기존 `queued/processing` 작업과 다른 월·순서·generation은 수정하거나 소비하지 않는다. 따라서 일반 통합 조회의 전체 작업 표시는 계속 갱신 중일 수 있으며, 지정 월 반영 여부는 이번 응답의 월·계산시각·sourceRevision·확보율과 저장 월 파일을 확인한다. 기존 전체 작업은 이후 동일 월을 검증하여 재사용하고 남은 월을 계속 처리한다.

검증: `test_company_integrated_month_refresh.cjs`, 기존 DB·재시작 검증, 관리자 API 인증·same-origin·입력 제한·업체별 결과 분리 검증.

## 저장된 상품 분류와 제공자 내부 유형의 충돌

복구 검증 버전 2는 저장된 `saleType`이 정확히 `숙박` 또는 `데이유즈`인 경우 그 분류를 사용한다. 반대 의미의 제공자 `bizItemSubType`은 파생 계산용 복사본에서만 비워 검증과 기존 계산기가 같은 상품 유형을 처리하도록 한다. 모호한 명시 분류와 내부 유형 자체의 양종 충돌은 계속 제외하며, CSV에 기록된 숙박·데이유즈 각각의 전체 상품 ID 개수도 일치해야 한다.

영수증의 `classificationNormalizations`에 날짜·상품 ID·원분류·계산분류·사유를 기록하고 영수증 해시로 연결한다. 원본 파일과 기존 영수증은 수정하지 않는다. 버전 1 영수증은 새 분류 정규화가 필요 없는 경우 그대로 조회한다. 공유 재고·가격 계산식과 객실 검수값 우선순위는 변경하지 않는다.

## 구형 판매중지 응답의 파생 예약가능 수량

검증 버전 3은 정상 상품 응답에 저장된 `available`이 판매중지 여부를 반영하지 않은 구형 산식과 정확히 일치하는 경우를 구분한다. 상품 목록·날짜·수집시각·식별번호가 모두 검증되고, 원래 재고·공개예약·점유 수량이 정합하며, 판매중지 상품의 `available`이 `재고 - 공개예약 - 점유`와 정확히 일치할 때 계산용 복사본의 `available`만 0으로 정규화한다. 판매중지 사유를 실제 예약으로 확인한 것으로 바꾸지 않는다. 방막기 수량과 금액은 기존 추정 정책으로 계산한다.

응답 오류·차단·미관측 표시, 상품 누락, 모순된 재고·예약·총량·판매 수량은 계속 제외한다. 단순히 수량이 비슷하다는 이유로 정규화하지 않는다. 새 영수증의 `inventoryNormalizations`에 원래 상품 행 해시, 원래 값, 계산에 사용한 값과 사유를 남기고 원본 파일 SHA-256으로 연결한다. 버전 1·2 영수증은 당시 검증 규칙으로 다시 읽으며, 버전 3 영수증은 별도 파일로 추가한다.

## 숙박 응답은 있으나 데이유즈 수량이 없는 경우

데이유즈 존재 확인만 수행한 회차에서 데이유즈 날짜별 수량과 객실 공유 관계가 미확인이면 전체 숙박 예약·매출을 정상으로 승격하지 않는다. 저장된 정상 숙박 상품에서 검증된 부분금액은 별도 근거로 보존하며, 정상 매출과 합산하지 않는다. 정상 관측이 이미 선택된 같은 업체·숙박일의 부분금액은 추가 합산에서도 제외한다. 리포트는 미확인 수량과 전체 금액을 유지하면서 일부 상품 확인금액과 원인, 업체·수집번호·숙박일 근거를 구별해 전달한다.
