# 업체 DB 초기 조회와 상세 조회 분리

## 목적과 검수 기준

2026-10-17 운영 `317303e` 검수에서 실제 535개 업체의 기본자료 대기를 포함한 DB 첫 진입은 4.47초와 5.84초였다. 자료가 준비된 뒤 첫 진입은 1.37초, 홈 복귀는 0.16~0.17초였다. 기존 업체 요약의 JSON 응답 본문은 32,344,085바이트였다. 이 수치는 네트워크 압축 후 전송량이나 순수 계산시간을 뜻하지 않는다.

초기 화면에는 검색·분류·객실 기준·검토 요약에 필요한 자료만 제공한다. 상품 명세와 일자별 예약 근거, 누적 상세 이력은 업체를 선택한 뒤 기존 상세 API로 조회한다. 기존 전체 요약 API와 원본·예약·매출 계산 규칙은 유지한다.

목표는 관리자 세션과 화면 이벤트가 준비된 직후 DB를 선택했을 때, 실제 기본 업체 목록이 2초 이내에 준비되는 것이다. 로딩 문구가 나타난 시각을 완료로 취급하지 않는다. 새 계산이나 업체 통합 관측 전체 완료시간과 구분한다.

## 정확성

- 업체 수와 고유번호, 이름·주소·업종·지역 검색, 필터 결과가 기존 요약과 일치해야 한다.
- DB 검수 객실 수, 보정값의 우선순위, 최신 상태·예약·매출 요약과 검토 대상 판정을 유지한다.
- 정상 응답의 0, 누락·오류·차단의 미확인을 구분한다. 상세 자료를 아직 조회하지 않은 상태를 정상 빈 이력으로 표시하지 않는다.
- 초기 조회와 상세 조회의 늦은 응답은 새 로그인·역할·선택 업체·수정 내용을 덮을 수 없다. 실패한 상세 조회는 재시도할 수 있어야 한다.
- 원본 전체 이력은 축약하여 다시 저장하지 않는다. 조회용 결과만 따로 보관하며 원본 변경 후 무효화한다.

## 구현 계약

- 관리자 전용 `GET /api/company-master/bootstrap`이 기본 목록을 제공한다. 기존 `/summary`와 `/detail` 응답은 유지한다. 전체 검수 이력 CSV처럼 전체 이력이 필요한 작업은 명시적으로 실행할 때만 `/summary`를 읽는다.
- `company_master/bootstrap_read_model.json`에 조회용 결과를 저장한다. 소스 파일의 장치·파일번호·크기·수정 및 변경시각과 코드 버전을 확인해 재사용한다. 매 조회마다 큰 원본의 전체 내용 해시를 다시 계산하지 않는다. 저장 조회 결과 자체의 내용 해시는 별도로 검증한다.
- 같은 원본의 동시 요청은 한 번만 준비한다. 메모리와 저장본이 유효하면 JSON 및 gzip 응답을 재사용한다. 원본 변경 중이면 다시 준비하며 계속 변경되면 오류로 알린다. 캐시 쓰기 실패는 원본을 고치거나 삭제하지 않는다.
- 정상 업체 원본을 확인했던 뒤 원본이 사라지면 오류로 처리하고 마지막 저장본을 보존한다. 새 설치에서 원본과 저장본이 모두 없는 경우만 정상 빈 DB로 취급한다.
- 서버 시작 시 다른 큰 집계 준비 전에 기본자료를 순차 준비한다. 최초 준비시간은 서버 시작 대기로 별도 기록한다. 준비 실패 시 안전한 오류코드를 남기고 실제 조회에서도 오류와 0개를 구별한다.
- 홈·DB 기본 화면은 큰 최신 수집 결과의 상세 읽기를 미룬다. 수집 목록의 최근 기록은 유지하며 결과 화면이나 명시적인 수집 이력 선택에서 상세 조회를 재개한다. 업체 선택 시 해당 업체의 상세·통합 관측을 연결한다.
- 목록의 반복 파생 계산은 업체 배열·개별 업체·선택 수집 자료가 같은 경우만 재사용한다. 보정·검토 저장, 상세 병합과 수집 결과 전환으로 참조가 바뀌면 다시 계산한다.

검증 명령은 `npm run test:company-bootstrap` 및 `npm run test:navigation`이다. 새 테스트는 초기 조회 저장·재사용·오류, 관리자 권한, 상세 지연 응답과 재시도, 큰 이력의 분리, 전체/축약 응답의 실제 클라이언트 파생값 동등성을 다룬다.

## 확인 절차

1. 큰 예약·상품 이력이 있는 업체를 포함해 축약 전후의 목록·검토 계산을 비교한다.
2. 비로그인·일반 회원 접근을 차단하고, 초기 조회가 수집이나 외부 지표 호출을 만들지 않는지 확인한다.
3. 최초 생성, 같은 자료 재조회, 서버 재시작 후 재사용, 객실·기본정보·검토·채널 수정과 파일 교체 후 갱신을 확인한다.
4. 535개 업체의 로컬 화면에서 대기 포함 최초 DB, 재진입, 홈 전환을 각각 기록하고 업체 선택 전 상세 조회가 없는지 확인한다.
5. 운영 배포 후 동일한 실제 자료로 다시 측정한다. 로컬 모의자료 검수 통과는 운영 2초 달성의 증거가 아니다.

운영 검수에서는 검사 대상 원본·설정의 해시와 결과 폴더 수, 예약·보호 상태를 전후 비교한다. 속도 검수를 위해 수집 실행이나 보호 해제, 일정 변경을 하지 않는다.

## 초기 갱신 중 검색과 준비상태

초기 조회가 순차 완료되며 DB 본문이 다시 그려져도 입력 중인 검색어는 확정 필터와 별도로 보존한다. 같은 세션·검색 문맥에서 검색어, 자동완성 열림/닫힘, 포커스, 선택영역과 스크롤을 복원한다. 다른 업체·지역 선택, 검색 확정, 초기화, 로그아웃은 새 문맥으로 취급한다. 지연된 복원은 새 입력이나 메뉴·세션 변경을 덮지 않는다.

한글 조합 중에는 DB 본문 교체를 미루고 조합 종료 후 현재 문맥의 최신 자료를 그린다. 조합 확정 Enter는 업체 선택이나 검색 확정으로 처리하지 않는다.

상단 기준시각은 선택 결과가 있으면 그 결과를 우선하고, 없으면 최근 수집 시각을 사용한다. 수집 시각이 없을 때에는 `업체 DB 갱신`, `지역 집계 작성`, `기본자료 작성`처럼 출처를 구별한다. 집계 작성시각을 최신 관측시각으로 표시하지 않는다.

홈은 업체 기본자료와 수집 목록의 조회 상태를 추적한다. 기본자료 준비는 상세 분석 완료와 구별하며, 조회 중·갱신 중·기존 자료를 남긴 갱신 실패·정상 빈 자료를 구분한다. 다른 연동의 설정 조회까지 모두 완료됐다는 뜻은 아니다. 메타자료 도착 시에는 현재 관리자 화면의 상단과 홈 상태만 갱신하며, 이를 위해 전체 수집 결과나 업체 상세를 미리 읽지 않는다.

`test:company-bootstrap`에 검색·한글 조합·연속 렌더·늦은 복원과 준비상태 회귀검사를 포함한다. 로컬 화면 검수에서는 초기 설정 응답을 보류하고 검색 입력 후 해제해 실제 DOM 교체 전후를 비교한다. 모의 535개 업체만 사용하며 외부 수집·운영 자료 수정은 하지 않는다.

## 업체 선택 시 월별 통합카드 우선 표시

2026-10-18 운영 `be2e21e`에서 월명글램핑 최초 업체 선택은 36.97초였다. `/detail` 응답에 36.00초가 걸리고, 그 뒤 저장된 `/integrated`를 조회해 통합카드까지 기다리는 순서가 원인이었다. 같은 화면의 월 변경은 0.24초였다. 이 시간은 당시의 실제 자료·부하에서 관측한 값이며 보장값이 아니다.

업체 선택 직후 기본 목록의 업체명과 통합카드 영역을 먼저 표시한다. 저장된 월별 통합 응답을 그린 뒤 같은 DOM과 요청 세대가 두 번의 animation frame 동안 유지되는지 확인하고, 그 후 상품·기본정보·전체 상세이력을 조회한다. 별도의 고정 대기시간을 두지 않는다. 단순 로딩 문구를 자료 표시 완료로 취급하지 않으며, 집계 준비 중·실패·미확인은 그대로 구별한다.

상세자료가 도착해 본문을 갱신할 때 같은 세션·업체 원본·보정 기준이면 통합카드의 실제 DOM과 컨트롤러를 유지한다. 선택 월·탭·보기 방식과 내부 포커스를 보존하고 동일 업체·월 조회를 반복하지 않는다. 수동 상태 확인과 실제 집계 갱신 중 상태 조회는 유지한다. 업체 원본이나 객실 보정 기준이 바뀌면 이전 카드를 재사용하지 않는다.

초기 통합 조회 중 월을 바꾸면 최신 월의 표시를 기다린 뒤 상세 조회를 시작한다. 업체·메뉴·세션 변경, 화면 숨김과 종료 시 이전 표시 대기를 정리하고, 화면 복귀 후 필요한 상세 조회만 재개한다. 늦은 상세 응답은 변경된 자료·로그인 문맥을 덮지 않는다. 정상 0과 미관측·오류를 구별하는 계산 및 원본 보존 규칙은 유지한다.

검증 명령은 `npm run test:company-first-display`다. 실제 앱 함수와 통합 컨트롤러를 함께 실행해 조회 순서·중복 방지·DOM 보존·월 변경·검수 갱신·숨김 복귀를 검사한다. 로컬 브라우저에서는 상세 HTTP 응답을 보류한 채 통합카드 표시를 측정한다. 이 결과는 운영 2초 목표 달성의 증거와 구별하고, 배포 후 실제 업체 자료로 첫 선택부터 통합카드 표시까지 다시 측정한다. 상품·전체 상세이력 완료시간은 별도로 기록한다.

로컬 검수 결과: 모의 예약·매출이 있는 저장 집계의 첫 카드 표시는 183.7ms였다(선택 입력→실제 수치 DOM→같은 DOM 2프레임). 이때 상세 응답은 보류 중이었다. 다음 검수에서 상세 응답을 약 10.87초 보류한 동안 8월에서 7월로 바꾼 뒤 응답을 해제해도 동일 통합카드와 7월 선택이 유지됐고, 상세 도착 때문에 추가된 통합 조회는 없었다. 기준 불명확 자료의 별도 모의 검수에서는 예약·매출을 0으로 바꾸지 않고 미확인으로 표시했다. 라이트·다크 화면을 확인했으며, 관련 화면 검사 150개·자료 검사 30개와 기본/통합 API 검사 2개가 통과했다. 모의 서버 간 동일 호스트 쿠키 간섭은 첫 검수 탭을 닫고 독립된 세션으로 재확인했다. 운영 배포와 실제 자료의 첫 카드 표시 시간 재측정은 별도 단계다.
