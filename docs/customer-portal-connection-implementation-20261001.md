# SABUN Insight 연결 개발 현황 · 2026-10-01

이번 작업은 합의된 계획의 첫 구현 단계다. **로컬 구현·격리 검수 완료, 운영 미배포**다. 전체 고객 서비스가 완성됐다는 뜻은 아니다.

## 확정한 구조

- 고객 도메인: `insight.sabun.co.kr`. 별도 도메인을 새로 구매하는 대신 `sabun.co.kr`의 하위 도메인을 고객 서버에 연결한다. 이번에 DNS나 Render 설정을 변경하지 않았다.
- 고객 브라우저 → 같은 도메인의 고객 서버 → 인증된 데이터랩 전용 API → 중앙 업체 DB·고객 저장소 순서로 연결한다.
- 관측 원본, 업체 고유번호, 검수 객실 수와 리포트 원본은 데이터랩이 관리한다. 고객 서버는 중앙 파일/DB에 직접 접근하지 않는다.
- 내 매장 1곳, 경쟁업체 기본 3곳, 관심지역 기본 1곳. 경쟁업체·관심지역 한도는 관리자가 변경한다. 매장 준비 중으로도 시작할 수 있다.
- 데이터랩의 기존 **회원 → 인사이트 이용자·등록 업체 → 업체 DB 정보 수정**으로 관리한다. 기존 회원 관리 및 업체 편집기를 재사용한다.
- `AWS worker`는 현재 서비스 표시 이름이며, 작업 키는 `scheduled`다. 이번 작업에서 AWS 인프라를 새로 만들거나 이전하지 않았다.

## 수집 및 결과 상태의 의미

검색·등록·화면 조회로 외부 수집을 시작하지 않는다. `자료 준비 요청`을 누르면 관리자의 범위 확인 대기로 저장한다. 관리자 실행 화면에는 날짜·조회 기간이 필수이며, 업체명 검색·상세 1위·성인 2명·데이유즈 유무 확인·전체 상품 조건을 명시한다.

같은 업체·한국시간 당일·동일 조건의 인사이트 요청은 고객이 달라도 하나의 영속 작업을 공유한다. 접수 전 작업번호를 저장하며 전달 결과가 불명확하면 새 작업으로 재전송하지 않는다. 차단 후 다른 워커로 전환하지 않는다. 기존 수집기의 요청 속도 및 보호 설정을 변경하지 않는다.

`ready`는 요청 영수증의 정상 완료, 보관함 결과, 해당 업체 DB의 runId 및 주요 조회 범위 일치까지 확인한 상태다. `partial`·`blocked`·`failed`·`needs_review`를 정상 완료로 바꾸지 않는다. 현재 완료 상태 조회는 고객/관리자 화면 조회 시 기존 기록을 읽어 갱신한다. 자동 알림이나 수집 일정은 만들지 않았다.

**제한:** 다른 키워드로 수집한 동일 업체 관측을 범위별로 찾아 재사용하는 기능은 아직 완성하지 않았다. 현재 어댑터가 보장하는 것은 인사이트에서 접수한 동일 업체·당일·조건의 작업 공유다. 기존 수집 요청 계층의 키워드 재사용 검사도 유지한다. 두 기능을 동일시하지 않는다.

## 저장·접근 기준

- 중앙 회원: 기존 `customer_db/b2b_members.json`. 고객 저장소는 memberId로 연결한다.
- 고객 저장소: `${DATA_DIR}/customer_insight/insight.sqlite`, SQLite schema version 1, WAL 사용.
- 테이블: customers, sessions, commands, audit, corrections, preparations, preparation_jobs, attempts.
- 고객 변경은 트랜잭션·revision·requestKey로 보호한다. 동일 요청의 중복 저장과 오래된 화면의 덮어쓰기를 거부한다.
- 세션은 12시간, 저장소에는 토큰 해시만 저장한다. 운영 쿠키는 HttpOnly·Secure·SameSite=Lax·host-only다.
- 서비스 자격은 서버 사이에서만 사용한다. 브라우저에는 전달하지 않는다. 고객 서버에서 임의 관리자 API 주소를 대리 호출할 수 없다.
- 변경 API는 출처·CSRF·입력 항목·본문 크기를 검사한다. 고객 간 관계·메모·검수 요청을 분리하며, 중지된 중앙 계정은 기존 세션으로도 접근하지 못한다.
- 중앙 수동 보정 원본 이력은 자르지 않는다. 기존 요약 화면은 최근 8건만 표시하며 전체 보관 이력과 구분한다.
- 운영 공개 전에 영속 디스크, SQLite 일관성 있는 백업·복원, 로그 접근 및 보관 정책 검수가 필요하다. 가동 중 SQLite 파일 하나만 복사한 것을 완전한 백업으로 취급하지 않는다.

## 실행 설정

기존 검수본 `node customer-portal/server.cjs --preview`는 그대로 유지한다. 아래 연결 서버와 다른 실행 모드다.

데이터랩:

| 환경변수 | 용도 |
| --- | --- |
| INSIGHT_CONNECTION_ENABLED | `1`일 때만 고객 연결 API·저장소 활성화. 기본 비활성 |
| INSIGHT_SERVICE_TOKEN | 고객 서버와 공유할 충분히 긴 서비스 자격. 최소 32자, 코드·브라우저·문서에 값 기록 금지 |
| INSIGHT_SIGNUP_ENABLED | `1`일 때 가입 검토. 아래 실제 정책 설정이 없으면 가입 불가 |
| INSIGHT_TERMS_VERSION / INSIGHT_PRIVACY_VERSION | 인사이트에 실제 적용할 약관·개인정보 안내 버전 |
| INSIGHT_TERMS_URL / INSIGHT_PRIVACY_URL | 고객이 읽을 HTTPS 정책 문서 주소 |

고객 서버:

```text
node customer-portal/connected-server.cjs
```

`INSIGHT_PUBLIC_ORIGIN=https://insight.sabun.co.kr`, `INSIGHT_DATALAB_ORIGIN=https://staydatalab.kr`, 동일 `INSIGHT_SERVICE_TOKEN` 및 `PORT`를 설정한다. HTTPS 또는 로컬 개발 주소만 허용한다. Render 환경에서는 0.0.0.0, 로컬에서는 127.0.0.1에 바인딩한다. 기존 공개 검수 서비스의 시작 명령은 이번에 바꾸지 않았다.

개발 검수:

```text
node customer-portal/dev-connected.cjs
```

고객 `http://127.0.0.1:57951`, 관리자 `http://127.0.0.1:57950/admin`. 매번 별도 OS 임시 폴더에 **가상 업체**를 만든다. 개발 전용 계정은 스크립트 안에 표시되어 있으며 운영에서 사용하지 않는다. 운영 환경변수·워커 자격을 상속하지 않으며 외부 관광 수집 스케줄러도 끈다. 임시 검수 폴더를 자동 삭제하지 않는다.

## API 범위

- 고객 동일 출처: `/api/customer/v1/config`, `/auth/login`, `/auth/signup`, `/auth/logout`, `/me`, `/catalog/companies`, `/catalog/regions`, `/commands`.
- 데이터랩 내부 연결: 같은 경로의 `/api/insight/v1/*`. 서비스 인증 필수.
- 관리자: `/api/admin/insight-customers`, `/{customerId}`, `/{customerId}/commands`, `/correction-review`, `/preparation-dispatch`. 기존 관리자 인증 필수.
- 변경 명령: onboarding, add-company, archive-company, add-region, archive-region, settings, correction, withdraw-correction, prepare-data. 관리자 명령: entitlements, property-review, account-status.
- 이전 연결 계약의 REST 경로는 설계 초안이다. 이번 구현은 위 v1 commands 경로를 사용하며 아직 운영 소비자는 없다.

## 검증 결과

2026-10-01 격리 환경에서 아래 52개 테스트와 별도 중앙 객실 보정 통합 검증 통과:

```text
node --test scripts/test_insight_connection.cjs scripts/test_insight_app_integration.cjs scripts/test_monthly_report_sources.cjs customer-portal/test/*.test.cjs
node scripts/test_b2b_manual_correction_segments.cjs
```

52개는 신규 연결 17개, 기존 예시 화면 28개, 월간 자료 연결 회귀 7개다. 실제 데이터랩 서버 프로세스의 회원가입·정책 버전·관리자 한도 변경·재시작 후 세션/데이터 유지도 포함한다. 별도 객실 검증은 12개 유형, 35건 수정 이력, 원본 관측 보존, 충돌 거부를 확인했다.

추가로 기존 객실 보정·방막기 매출·월간 재계산 18개가 통과하여 총 70개 테스트를 확인했다. 기존 업체 수정 바로가기, 객실 근거 UI, 화면 대비 검사도 통과했다. 새 복제 함수 사용에 맞춰 기존 VM 테스트 환경에 `structuredClone`을 제공한 뒤 재검증했다. JavaScript 구문 검사 및 Git 공백 검사도 통과했다.

브라우저에서는 가상 업체의 내 매장 등록 → 관리자 승인 → 고객 수정 요청 → 공통 업체 DB 수정 → 반영 확인 → 고객 표시를 확인했다. 실제 고객 개인정보, 운영 DB, 네이버 요청을 사용하지 않았다. 모바일 390px와 다크모드에서 본문 가로 넘침·콘솔 오류 없이 표시됨을 확인했다.

## 남은 개발 순서

1. 업체 병합/고유번호 변경의 고객 관계 이전, 기존 경쟁업체를 내 매장으로 전환하는 처리, 중앙에 없는 신규 업체 등록 요청.
2. 객실·데이유즈 검수값의 적용 숙박기간 및 변경 버전, 공유 객실 구분을 중앙 산식과 연결. 현 단계에서 데이유즈 제안은 접수·보존만 하며 자동 확정하지 않는다.
3. 다른 키워드의 동일 업체 관측 재사용과 보존 결과의 범위별 품질 검증 강화. 승인된 한 업체·하루 범위에서 실제 워커 검증.
4. 고객별 허용 업체·지역 지표 조회, 발행된 월간 리포트 배정·철회·PDF 권한. 발행본은 현재 설정 변경으로 재작성하지 않음.
5. 주간 지표 계산·실제 가입부터 열람까지 통합 검수 후 고객 도메인 공개. 수집 주기·고객별 요청량·소유 확인·보관 정책은 운영 전 확정.

지역 분석·리포트 메뉴는 현재 연결 준비 상태다. 예시 수치나 미확보 값의 0 대체를 표시하지 않는다. 이 문서는 개발 상태 기록이며 배포·외부 수집 실행·일정 활성화의 증거가 아니다.
