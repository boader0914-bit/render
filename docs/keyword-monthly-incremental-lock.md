# 키워드 월별 증분 게시 잠금

이 변경은 증분 계산·게시의 잠금 수명과 읽기 전용 진단을 보완한다. 수집·예약 일정·보호, 원본·기존 발행본은 바꾸지 않는다. 운영의 기존 잠금을 지우거나 실패 회차를 재실행하지 않는다.

기존 schema1 잠금에는 프로세스 번호와 시각만 있다. 프로세스 번호는 다른 컨테이너나 재사용된 PID를 식별하지 못하므로, 오래됐다는 이유만으로 고아 잠금으로 간주하거나 해제할 수 없다. `KEYWORD_INCREMENTAL_WORKER_LOCKED`만으로 현재 작업과 중단 후 잔존 파일을 구별할 수 없었다.

새 schema2 잠금에는 프로세스 세션과 Linux의 부팅·PID 네임스페이스·호스트 조합의 지문, 프로세스 시작 tick을 함께 기록한다. 원문 호스트·네임스페이스·환경변수는 진단에 노출하지 않는다. Linux 정보를 읽을 수 없으면 잠금 획득 전 중단하며, 다른 플랫폼에서는 같은 프로세스 세션만 확인할 수 있다.

`inspectWorkerLock`는 최대16KiB를 읽고 상태를 분류할 뿐 어떤 파일도 수정하지 않는다. `WORKER_LOCKED` 오류의 `lockDiagnostic`에는 아래의 안전한 코드와 나이·동일 인스턴스 여부·프로세스 상태만 붙인다. PID·토큰·업체·키워드·원문 오류는 포함하지 않는다.

| reasonCode | 해석 |
|---|---|
| OWNER_ACTIVE | 같은 인스턴스에서 시작 식별자가 일치하는 프로세스가 관측됨 |
| OWNER_NOT_RUNNING | 같은 인스턴스에서 해당 프로세스가 관측되지 않음 |
| OWNER_PID_REUSED | 같은 인스턴스에 PID는 있으나 시작 식별자가 다름 |
| OWNER_OTHER_INSTANCE | 다른 인스턴스의 잠금이므로 로컬 PID로 판정하지 않음 |
| LEGACY_OWNER_UNVERIFIED | schema1이라 소유자 확인 근거 부족 |
| OWNER_STATE_UNAVAILABLE | 권한·읽기 실패 등으로 프로세스 상태 미확인 |
| OWNER_IDENTITY_UNAVAILABLE | 현재 또는 저장 소유자 식별 근거 미확인 |
| LOCK_INVALID / LOCK_READ_UNAVAILABLE | 형식·경로·읽기 검토 필요 |

어느 분류도 자동 해제·자동 재실행 승인이 아니다. 사라진 PID나 재사용된 PID도 잠금의 자동 삭제로 연결하지 않는다. 경주글램핑 기존 회차의 정확한 소유자 상태는 해당 운영 잠금의 별도 읽기 검증 전까지 미확정이다.

획득의 쓰기·동기화·닫기·읽기 검증 오류도 정리 범위에 포함한다. inode·전체 바이트 지문·토큰·sourceKey가 모두 자신의 파일임을 확인할 때만 제거한다. 부분 쓰기처럼 입증할 수 없는 파일과 관측된 대체 파일은 보존하고 `OWNED_LOCK_CLEANUP_NEEDS_REVIEW`를 붙인다. 작업과 정리가 함께 실패하면 작업의 원래 오류 객체·코드를 유지한다.

이 파일 프로토콜은 전용 디렉터리와 협조하는 단일 게시자라는 기존 신뢰 경계를 유지한다. Node 파일 API에는 compare-and-unlink가 없으므로 마지막 확인과 unlink 사이에 비협조적 프로세스가 악의적으로 경로를 바꾸는 경우까지 원자적 CAS를 보장한다고 주장하지 않는다. 그러한 경계가 필요하면 OS 잠금 프로토콜을 별도로 설계해야 한다.
